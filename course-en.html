Building with AWS Kiro

This course takes you from "I've heard of Kiro" to "I can run a feature through a spec, set up steering for our repo, wire an MCP server, and install a Power." It's written for developers who already ship code but are new to Kiro specifically.

MODULE 0

AI-DLC Foundations

Before the tool, the idea. AI-DLC — the AI-Driven Development Lifecycle — is the methodology Kiro is built to serve. This module is background: where it came from, what it actually says, and why the rest of this course (specs, steering) is AI-DLC in practice. No config here — just the mental model.

One-line version AI-DLC redesigns the software lifecycle around a simple loop: AI drafts the plan and the work, humans make the decisions, the team reviews. It is a methodology, not a product — published by AWS, and Kiro is its most direct implementation.

A short history — how we got here

  1. The hand-written era. The classic SDLC is built around long, human-driven processes: sprints, backlog grooming, estimation, hand-offs between specialised roles. AWS's framing is that teams spend most of their time on "non-core activities such as planning, meetings, and other SDLC rituals" rather than on the product.
  2. AI-assisted coding (≈2021–2023). GitHub Copilot and similar tools bring autocomplete-style help. AI speeds up individual tasks — completion, boilerplate, docs — but the process around it is unchanged. AI is a sidecar bolted onto a human-shaped workflow.
  3. "Vibe coding" (early 2025). Andrej Karpathy popularised the term in a post on X on 2 February 2025: "There's a new kind of coding I call 'vibe coding'" — describe what you want, accept the AI's changes without really reading them, paste errors back in. Karpathy meant it for throwaway weekend projects. It is fast and fun, and produces software with no requirements, no reviewed design, and no shared understanding — fine for a demo, a liability for anything a team maintains.
  4. An AI-native methodology — AI-DLC (mid-2025). AWS's position is that both existing strategies fall short: AI-assisted development is too timid (AI stays a helper), and AI-autonomous development removes human judgement entirely. In AWS's words, both "have produced suboptimal results in terms of velocity and software quality," and "simply retrofitting AI as an assistant not only constrains its capabilities but also reinforces outdated inefficiencies." AI-DLC's answer is to redesign the lifecycle itself around AI doing the work under continuous human direction.

Raja SP, a Principal Solutions Architect at AWS, published the founding description on the AWS DevOps blog on 31 July 2025, alongside a method-definition whitepaper. A follow-up walkthrough with Amazon Q Developer landed on 29 November 2025, and AWS Labs released an open-source workflow engine (awslabs/aidlc-workflows).

The core idea, as one loop

Every phase of AI-DLC runs the same cycle:

The non-negotiable part is the human decision point. AWS: "AI systematically creates detailed work plans, actively seeks clarification and guidance, and defers critical decisions to humans … only humans possess the contextual understanding and knowledge of business requirements needed to make informed choices." The AI keeps its own memory by writing plans, requirements, and design artifacts into the project repository, so work continues cleanly across sessions.

The nine principles

AWS Labs frames AI-DLC with a set of founding principles — the philosophy underneath the phases and the loop. They pull in three directions: redesign rather than bolt on, AI drives while humans decide, and design-first with few, gated phases.

PrincipleWhat it meansExample
1. Reimagine workflows for the AI era — don't retrofitRedesign the process to run at AI speed instead of squeezing AI into old rituals like the two-week sprint.Replace 2-week sprint planning with a bolt (hours–days): AI drafts the architecture and plan, the team validates on the spot.
2. AI orchestrates; humans keep controlAI proposes the plan and executes the steps; humans review, approve (human-in-the-loop), and own the direction.Asked to build a payments flow, the agent doesn't write code — it produces a plan and questions first. Only after you approve does it start.
3. Integrate design techniques into the coreDesign isn't an optional phase — it's how you build the context the AI needs to be accurate.Before any code, the agent always produces a domain model, NFR design (performance, security), and a component breakdown.
4. Balance AI capability with human expertiseLean on AI for the heavy lifting; stay honest about its limits and keep humans on the judgement calls.AI writes the test suite and most of the code; the person who understands the business defines and approves the acceptance tests.
5. Preserve proven practices, optimise for AI speedKeep what works — user stories, risk management — but adapt it to run smoothly at AI pace.You still write user stories; the AI breaks them into units of work in minutes instead of a grooming meeting.
6. Streamline roles to minimise hand-offsFlatten team roles and cut the document-passing between them, without losing the reviews that matter.Mob Elaboration / Mob Construction: product, dev and QA review the AI's plan and code together in one session instead of passing specs between departments.
7. Three phases with strategic validation gatesCollapse the lifecycle to Inception → Construction → Operations, with a validation gate in each.In Inception, once the AI reverse-engineers the legacy code and plans the work, a human must clear the gate before Construction starts.
8. Flexible, AI-recommended workflowsLet the AI recommend the workflow depth for the task, instead of forcing every job through a rigid template.A quick bug fix (minimal depth): the AI skips user stories and goes straight to root-cause + patch. Note on the list The counts vary by write-up. The method-definition paper actually names a 10th principle — "No Hard-Wired, Opinionated SDLC Workflows": rather than prescribing a path for new builds vs refactors vs defect fixes, the AI recommends the top-level plan from your stated intent. And the open-source engine team describes a tighter set of five design drivers — adaptive execution, human-in-the-loop, methodology-first (tool-agnostic), reproducible, no duplication (one source of truth). Treat all of this as the shape of the philosophy, not a fixed catechism.

Methodology vs the open-source engine

Keep two things apart. The methodology is the 3 phases and the loop above. The open-source engine — awslabs/aidlc-workflows, which the Kiro CLI can run — turns that into an execution pipeline: 5 phases and 33 stages (Initialization, Ideation, Inception, Construction, Operation), a 14-agent roster, and approval gates at every stage.

  • Stage selection is binary — each stage runs or is skipped based on the task. A known-cause bug fix skips user stories and application design; a new platform runs everything. Reverse Engineering only fires for brownfield (existing) code.
  • Depth is elastic. Within the stages that do run, a depth level — Minimal / Standard / Comprehensive — scales how much detail and reasoning each artifact carries, triggered by complexity and risk.
  • Test strategy is a separate dial. Also Minimal / Standard / Comprehensive, and independent of depth — so you can run a Minimal-depth bug fix while still demanding Comprehensive security and integration test coverage.
  • State lives in plain files. The engine writes an aidlc-docs/ folder with aidlc-state.md (session memory) and audit.md (a step-by-step trail). Because it's just files in the repo, you can start a bolt in one IDE and resume it in another — the agent reads the same state.

Where Kiro fits

Keep three levels straight:

  • AI-DLC is the methodology — the phases, the loop, the human-decides rule.
  • Spec-driven development is one way to structure the artifacts AI-DLC calls for.
  • Kiro is a tool built around that structure.

Kiro's requirements.md → design.md → tasks.md is exactly the artifact trail Inception and Construction assume; steering files carry the persistent context the loop depends on. The Kiro CLI can run AWS's aidlc-workflows directly. So Modules 3 and 4 of this course — Specs and Steering — are the Inception and Construction phases of AI-DLC, made concrete.

The numbers everyone quotes

  • Amazon Bedrock — "Mantle". Re-architecting the inference engine was scoped at ~40 engineers for a year; 6 engineers shipped it in ~76 days with Kiro — roughly 100,000 lines of production Rust, 40+ commits per week per developer. Rust partly because its precise compiler errors let the AI fix its own mistakes.
  • Wipro. At re:Invent 2025 (DVT214), AWS described compressing ~3 months of planned work into ~20 hours — five days of four-hour mob sessions.
  • A European financial-services institution. Went from 1 product owner + 12 developers delivering 15 features per sprint, to 1 product owner + 3 developers delivering 35 per sprint — 9 external contractor FTEs off the books.
Read this critically All of these are AWS's figures, from engagements AWS helped run, and nobody has published the failure cases. The nearest independent baseline: unstructured AI-assistant adoption buys roughly 10–15%, not 10–15×. Treat the numbers as directional — the transferable lesson is the shape: a small team, a very tight loop, and a language whose feedback the AI can act on.

In practice — one small feature through the loop

Scenario: "Add CSV export to the Reports page"

Inception. You give the agent the one-line intent. It comes back with questions a human has to answer: Which columns? Respect the current filters, or export everything? What time zone for the date column? Who is allowed to export — every role, or just admins? Nobody guessed — the team answered in a 15-minute mob. Output: a requirements.md with EARS lines like "WHEN an admin clicks Export THE SYSTEM SHALL download a CSV of the currently filtered rows, dates in the workspace time zone."

Construction. The agent proposes: reuse the existing ReportQuery, stream the CSV so a 200k-row export doesn't hold memory, add a reports:export permission check. One real decision surfaced — streaming vs building the file in memory — the team picked streaming in 2 minutes. The agent wrote the endpoint, the button, and tests, in one bolt.

Operations. The agent added a CloudWatch metric for export count and duration, and a note in the runbook. The team reviewed the dashboard change and merged.

The point: the rework-causing question ("just admins?") got asked in Inception, when the answer cost a sentence — not in code review, when it would have cost a rewrite of the endpoint and the button.

Honest caveats — and the governance holes

Most writing about AI-DLC so far is evangelism. The sharper critique: the classic SDLC quietly bakes in controls — peer review, audit trails, release gates — and running plan, code, and tests through in a single afternoon dissolves those controls faster than it replaces them. Two holes are worth naming.

  • "Verify and approve" is not a control. The methodology says humans approve at every gate, but doesn't say who, against what standard, recorded where. Fill it in: a named approver per unit of work — and not the person who prompted the plan — a one-page review checklist (data classifications touched, blast radius, rollback path, deviations from the steering files), and a decision log bound to the spec and steering-file versions. "The room agreed" satisfies no auditor.
  • The self-grading problem. In Construction the same agent writes the code and its tests. A green suite written by the code's author proves consistency, not correctness — an agent that misread a requirement writes tests that faithfully verify the misreading. At bolt speed the error compounds silently until production finds it. The fix: human-reviewed acceptance tests, frozen during Inception, before Construction — the agent implements against a bar it did not set.
  • Velocity is not stability. DORA's 2025 survey (AI-focused, ~5,000 respondents) found AI adoption now positively associated with delivery throughput but still negatively with delivery stability. Instrument only speed and you're measuring the axis that already turned in your favour. Track defect-escape rate next to cycle time, or you've just moved QA into production.
  • The productivity numbers are AWS's, not yours. Unstructured AI-assistant adoption buys roughly 10–15%; the claimed 10–15× is, in AWS's telling, the methodology. Treat vendor benchmarks as directional — nobody has published the failure cases yet.
  • Mob sessions cost senior attention. They demand your most senior people, synchronously, for hours. "The lifecycle spends less on typing and more on senior attention" — and rubber-stamp approval "decays into reflexive clicking within a week" without a real checklist.
  • AI-DLC is young (mid-2025) and still moving; it's a vendor methodology (AWS benefits when you adopt it). The underlying principles — requirements before code, humans on the decisions, short loops, context in the repo — hold up regardless of tool. Small or solo teams adapt the Mob model rather than run it as written.
Key takeaways
  • AI-DLC redesigns the lifecycle around AI does the work, humans decide, team reviews — not AI as autocomplete (too timid) and not AI autonomy (no judgement).
  • The loop: AI plans → AI asks → human validates → AI executes → team reviews → repeat.
  • Phases: Inception (Mob Elaboration) → Construction (Mob Construction) → Operations. Context compounds forward.
  • Vocabulary: Sprint → Bolt, Epic → Unit of work, solo/async → Mob.
  • AI-DLC is the methodology; spec-driven development structures its artifacts; Kiro is the tool. This course's Specs and Steering modules are AI-DLC in practice.
  • The 76-day / 100k-line-Rust story is a vendor anecdote — useful signal, not an audited result.
  • It removes SDLC controls faster than it replaces them — add a named approver per unit of work, freeze acceptance tests in Inception, and track defect-escape rate, not just speed.

🧪 Lab 0 — Map a real PR onto AI-DLC

Goal: feel where the Inception / Construction line falls in your own work, and find one decision that leaked into code review.

  1. Open the last non-trivial pull request you reviewed or authored. Read the description and the diff.
  2. On paper (or a scratch file), make three columns: Inception, Construction, Operations.
  3. List every distinct decision or change from the PR under the phase where it should have been settled. Examples: "export is admin-only" → Inception; "stream the CSV" → Construction; "add export metric" → Operations.
  4. Circle anything that was actually decided during code review or after merge. For each, write the one sentence that would have settled it in Inception.
  5. Count: how many review comments were really missing-Inception, not missing-code-quality?

Done when you have at least one circled decision and its one-sentence Inception version. That sentence is the shape of an EARS acceptance criterion — you'll write these for real in Module 3.

MODULE 1

What is Kiro & why

The problem Kiro is built around

Chatting with an AI until code appears — "vibe coding" — is great for exploration and terrible for anything a team has to maintain. You get a working demo, but the requirements only ever lived in the chat scrollback, nobody reviewed the design, and the next change breaks something because there was no shared understanding of what the feature was supposed to do.

Kiro's answer is to make the planning artifacts first-class: written requirements, a written design, and a task list the agent executes against — all stored in your repo, all reviewable like code. You still get to vibe when you want to; you just have a structured path for the work that matters.

One agent, every surface

Kiro is not just an IDE. It's a single agent "harness" exposed through several interfaces:

SurfaceWhat it's for
IDE (desktop app)The main experience — editor, chat panel, specs, steering, hooks UI.
CLIDrive the same agent from the terminal or scripts / CI.
WebBrowser-based agent; hand off long-running tasks.
MobileCheck in on tasks from your phone (no MCP).

The important part: your .kiro/ configuration is shared across all of them and travels with the repository. Set up steering once, and it applies whether a teammate is in the IDE or CI is running the CLI.

  1. Install the IDE (desktop), the CLI, or use the Web agent.

How the pieces connect

In practice — start in the IDE, finish in CI

Scenario: a bug fix that CI verifies

A developer opens the repo in the IDE, describes the bug, and the agent proposes a Bugfix Spec. They approve it and let the agent implement the fix — Supervised, so they eyeball each change.

They push the branch. In CI, a pipeline step runs kiro from the CLI against the same repo: it reads the committed .kiro/steering/security.md and runs a "review this diff against our security rules" prompt. Same agent, same rules, no extra configuration — because .kiro/ is in the repo the CI job checked out.

The reviewer later glances at the change from the Mobile app on the way home and leaves a comment. One agent, four surfaces, one source of truth.

MODULE 2

Vibe / Chat mode

The default agent

When you open the chat panel, you're talking to the Default agent — "vibe" mode. It's free-flow: describe what you want in natural language and Kiro responds with edits, explanations, or commands. There's no required structure and no generated documents. Use it for:

  • Questions about the codebase ("where do we validate the JWT?")
  • Debugging a specific failure
  • Small, local changes
  • Exploring an approach before committing to a spec

Vibe vs Spec — and the modes in between

ModeOutputUse when
Vibe (Default)Direct edits / answers, no docsQuestions, debugging, exploratory work
Specrequirements.md + design.md + tasks.mdFeature work that needs review or touches several files
PlanA plan only — no code changesYou want the approach written down before anything moves
Bug FixBug analysis → fixReproducible defect; you want regression protection
Quick SpecBrief clarification, then auto-generated specSmall feature, you trust the agent to fill in the gaps

Autopilot vs Supervised

Independently of the mode, you choose how much rope the agent gets:

  • Supervised — you approve every file change before it lands. Slower, safe, and the right default while you're learning a workflow.
  • Autopilot — the agent executes changes autonomously and you review the result. Good for narrow, well-scoped tasks you've seen it do reliably.
Rule of thumb Stay Supervised until you've watched the agent do this kind of task correctly a few times. Then move that specific task type to Autopilot — not everything at once.

Context providers — the # menu

Kiro only knows what's in its context. The # prefix pulls specific things in:

ProviderAdds
#codebaseKiro searches the repo and pulls in the files it judges relevant
#file / #folderA specific file or directory you name
#git diffYour uncommitted changes
#terminalRecent command output and history
#problemsDiagnostics / errors for a file
#url · #docs · #repository · #code · #mcpExternal page, docs, another repo, a code snippet, or an MCP resource

Combine them in one message: Fix the failing test in #problems using the pattern from #file:src/auth/session.ts.

You can also paste an image (a screenshot, a mockup, an error dialog) directly into chat as context.

Long sessions: checkpoints and compaction

  • Checkpoints / rewind — Kiro snapshots state as it works, so you can roll back to a known-good point instead of unpicking changes by hand.
  • Compaction — when a session gets long, Kiro summarises earlier context to stay within the model's limits without losing the thread.

Choosing a mode

In practice — a debugging session

Scenario: intermittent 500 on checkout

You stay in vibe mode — this is investigation, not a feature. First message:

The checkout endpoint 500s about 1 in 20 times.
Here's the failing request and stack: #terminal
Relevant code: #file:src/checkout/handler.ts #file:src/db/pool.ts
Recent changes: #git diff

With that context the agent spots that #git diff lowered the DB pool size while handler.ts opens two connections per request — under load the pool starves. You ask it to explain the fix, don't apply it yet. It does. You decide the real fix is a design change, so you close the vibe session and open a Bug Fix spec so the change is reviewed and the regression is captured.

The point: vibe found the cause fast because you fed it the three things that mattered; the fix graduated to a spec because it was going to be reviewed.

MODULE 3

Specs

What a spec is

A spec is a structured set of artifacts that formalises how a feature or bug fix gets built. Instead of one long chat, you get three files in .kiro/specs/<name>/, each gated by your approval:

FileContents
requirements.md (or bugfix.md)User stories + acceptance criteria (feature), or current / expected / unchanged behaviour (bug)
design.mdArchitecture, component breakdown, sequence diagrams, data flow, error handling, testing strategy
tasks.mdDiscrete, individually trackable implementation tasks with live status

The three-phase workflow

  1. Requirements — Kiro drafts user stories and acceptance criteria from your description. You edit and approve before anything else happens.
  2. Design — Kiro turns approved requirements into a technical design. Review it here; this is the cheapest place to catch a wrong approach.
  3. Tasks — Kiro breaks the design into an ordered task list, then implements task by task, updating status as it goes.
Why the gates matter Fixing a misunderstanding in requirements.md costs a sentence. Fixing it after the agent has written 12 files costs an afternoon. The approval gates exist to force the cheap conversation first.

The requirements gate, up close

In AI-DLC the requirements step has a specific shape that's worth copying even if you're just using vibe mode. The agent is told not to assume. Instead it writes a requirement-verification-questions.md with its open questions as multiple-choice, each with an "Other" option. You answer them inline, in the file, then type Done. The agent then checks your answers for contradictions and gaps, asks follow-ups if needed, and only then generates requirements.md. You never wrote the detailed spec — you answered a structured interrogation, and kept control of what gets built.

Do this in Kiro When a spec's requirements come back thin, don't approve. Reply: List every assumption you made as a multiple-choice question with an "Other" option. Don't proceed until I've answered.

EARS notation for requirements

Kiro writes acceptance criteria in EARS (Easy Approach to Requirements Syntax) — a small set of sentence templates that keep requirements testable and unambiguous:

WHEN <trigger> THE SYSTEM SHALL <response>
WHILE <state> THE SYSTEM SHALL <response>
WHERE <feature is included> THE SYSTEM SHALL <response>
IF <condition> THEN THE SYSTEM SHALL <response>

Example: WHEN a user submits the checkout form with an expired card THE SYSTEM SHALL reject the payment and display "Your card has expired". Each line becomes a test.

Design covers "what" and "how well"

A good design.md separates functional behaviour from non-functional qualities — the same split AI-DLC makes explicit, with a requirements pass and then a design pass for the non-functional side:

AspectFunctional — whatNon-functional — how well
PerformanceUsers can search productsSearch returns under 200 ms at p99
SecurityUsers can log inPasswords hashed with bcrypt; sessions expire in 24 h
ScalabilitySystem processes ordersHandles 10k concurrent orders at peak
ReliabilityData is storedZero data loss; RPO under 1 minute

AI-DLC runs this as two steps per unit of work: NFR Requirements Assessment (name the benchmarks, the security posture, the compliance boundary) then NFR Design (turn each into a concrete decision — a Redis cache and a CDN, multi-AZ with health checks, encrypt S3 at rest and tokenise card numbers). When you review a Kiro design.md, check both halves are there — the non-functional half is the one that quietly gets skipped.

Task execution in waves

Kiro analyses dependencies between tasks and builds a dependency graph, then runs them in waves:

  • Wave 1 — tasks with no dependencies, run concurrently.
  • Wave 2+ — tasks whose dependencies are now satisfied, run concurrently.
  • Waves run in sequence; tasks inside a wave run in parallel.

You don't configure this — it's automatic, and it's why a spec often finishes faster than issuing the same tasks one at a time in chat.

The whole workflow, end to end

In practice — a spec for rate limiting

Scenario: ticket PROJ-812 "Rate-limit the public API"

Requirements phase. You describe the ticket. Kiro drafts EARS criteria; you tighten two:

WHEN an unauthenticated client exceeds 60 requests in 60 seconds
THE SYSTEM SHALL respond 429 with a Retry-After header.

WHILE a client is rate-limited
THE SYSTEM SHALL NOT count further requests toward the window.

WHERE the client presents a valid API key
THE SYSTEM SHALL apply the key's plan limit instead of the default.

Design phase. Kiro proposes a token-bucket in Redis, a middleware ahead of routing, and a fallback to "fail open" if Redis is unreachable. You change one thing — fail closed for the payments routes — and approve.

Tasks phase. tasks.md comes out as: (1) Redis client + config, (2) token-bucket module + unit tests, (3) middleware, (4) wire into router, (5) integration tests, (6) dashboard metric. Waves: 1 and 2 run together; 3 waits on 2; 4 waits on 3; 5 and 6 run together at the end.

The PR contains the code and .kiro/specs/PROJ-812-rate-limiting/, so the reviewer sees why "fail closed for payments" was chosen without asking.

In practice — a whole small app, gate by gate

AWS's own walkthrough: a "river crossing" puzzle web app with Amazon Q + AI-DLC

You type one line: Using AI-DLC let's build a web application to solve the river crossing puzzle. Then every step is a gate you clear with Continue or Done:

  1. Workspace Detection — no existing code, so it's greenfield; Reverse Engineering is skipped. It creates aidlc-docs/ with aidlc-state.md and audit.md.
  2. Requirements Analysis — writes requirement-verification-questions.md: which puzzle variant (Classic farmer / fox / chicken / grain, or other)? scoring? a leaderboard? interaction style? You answer inline, type Done, it checks for contradictions, then produces requirements.md.
  3. Because it's a frontend-only page, it recommends skipping User Stories — you type Continue.
  4. Workflow Planning — execution-plan.md skips Application Design and Units-of-Work planning and jumps to Code Generation Planning.
  5. Code Generation Planning — an 8-step numbered checklist in <unit>-code-generation-plan.md: HTML structure → styling → game logic → docs.
  6. Code Generation — runs the plan, ticking boxes, and produces one index.html with embedded CSS and JS.
  7. Build & Test — a build-and-test instructions doc (unit / integration / UI checks) and a "ready to run" summary.

The point: you never wrote a spec — you answered a structured interview and approved plans. And the adaptive workflow skipped roughly half its stages because the task was simple; a platform migration would have run them all.

Referencing live files

  • Kiro also reads the cross-tool AGENTS.md standard — put one at the workspace root or in ~/.kiro/steering/. It has no inclusion modes; it's always included.
  • Custom agents don't get steering automatically. Add it explicitly: "resources": ["file://.kiro/steering/**/*.md"].

Best practices

  • One domain per file — api-rest-conventions.md, testing-unit-patterns.md, security-guidelines.md.
  • Explain the reasoning, not just the rule. Include before/after code snippets.
  • Never put secrets, keys, or passwords in steering files.
  • Review steering changes like code — they change agent behaviour for the whole team.

Steering as executable engineering policy

Steering is Kiro's name for something the wider AI-DLC world calls a rules file, and the framing is useful: it's not documentation the agent might read, it's policy the agent must follow.

  • The same rules, many tools. The content of a rules file is portable across coding agents — only the path changes: .kiro/steering/ for Kiro, .cursor/rules/ for Cursor, CLAUDE.md for Claude Code. Write your conventions once; they travel.
  • Encode policy before generation, not after. AWS's financial-services guidance puts security and regulatory rules into steering up front, so the agent generates compliant code the first time — plus end-to-end traceability from requirement to test. "Left-shifted QA": catch it before it compounds.
  • Blocking constraints, not warnings. Beyond plain steering, AI-DLC supports extensions that halt the workflow on a violation — HIPAA / PCI DSS / SOC 2 controls, mandatory coverage thresholds, microservice-boundary rules. Most linters warn and get ignored; a blocking rule stops the bolt.
  • A learning loop. When you correct the agent, that correction can be captured as a persistent rule, so the same mistake doesn't come back next session.

Which mode? — a decision tree

In practice — a real fileMatch file

.kiro/steering/code-style-ts.md 
---
inclusion: fileMatch
fileMatchPattern: ["**/*.ts", "**/*.tsx"]
---
# TypeScript conventions

## Errors
Never throw bare strings. Throw an `AppError` subclass with a `code`.
Rationale: the API error middleware maps `code` to an HTTP status and a
safe message; a bare string leaks internals and 500s.

// avoid
throw "user not found";
// prefer
throw new NotFoundError({ code: "user.not_found" });

## Async
No floating promises. Every `await`-able call is awaited or explicitly
`void`-ed with a comment saying why.

## Imports
Absolute imports from `src/` only (`@/db`, not `../../db`). Enforced by
eslint; steering exists so the agent writes them right the first time.

Because it is fileMatch, this only loads when the agent touches a .ts/.tsx file — the Python developers never pay its token cost, and it can be as detailed as it needs to be.

Agent Hooks

Automation on events

A hook runs a shell command or an agent prompt automatically when something happens in your session. Hooks are JSON files in .kiro/hooks/ and activate when a session starts — no manual registration.

Trigger types

CategoryTriggers
File (IDE)PostFileCreate, PostFileSave, PostFileDelete
ExecutionPreToolUse / PostToolUse (Pre can block), PromptSubmit (can block)
LifecycleSessionStart (IDE), AgentSpawn (CLI), AgentStop
Task (IDE)PreTaskExecution / PostTaskExecution — around spec tasks
Important File triggers only fire on agent-initiated changes — not when you edit and save a file yourself in the editor.

Hook file format

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}
FieldMeaning
triggerEvent type, PascalCase
matcherOptional regex to filter which events fire the hook
action.type"command" (run a shell command) or "agent" (inject a prompt)
timeoutSeconds before the hook is killed (default 60)

Common use cases

  • Run linters, formatters, or type checks after the agent changes files.
  • Auto-create tests, docs, or translations when a new source file appears.
  • Block a tool with PreToolUse unless a precondition is met.
  • Run a quality check before the agent finalises its changes.

Creating hooks

In the IDE: the + button in the Agent Hooks panel → "Ask Kiro to create a hook" → describe the automation in plain language and Kiro writes the JSON. Use kebab-case filenames (lint-on-save.json); related hooks can share one file.

Where triggers fire in a session

In practice — two hooks a team actually ships first

.kiro/hooks/dev-guardrails.json 
{
  "version": "v1",
  "hooks": [
    {
      "name": "Format on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx|js|jsx|json|css)$",
      "action": { "type": "command", "command": "npx prettier --write \"$KIRO_FILE\"" },
      "timeout": 30
    },
    {
      "name": "Scaffold a test for new source files",
      "trigger": "PostFileCreate",
      "matcher": "^src/.*(?<!\\.test)\\.ts$",
      "action": {
        "type": "agent",
        "command": "A new source file was just created at $KIRO_FILE. If it exports anything testable and no sibling *.test.ts exists, create one with a failing placeholder test and a TODO listing the cases to cover. Do not implement the tests."
      },
      "timeout": 120
    }
  ]
}

The first is a command action — pure shell, deterministic, safe. The second is an agent action — it hands a prompt back to the agent, so it can read the file and write a sensible test stub. Both are non-blocking: if Prettier fails, the workflow continues. No PreToolUse blocker until the team trusts these.

Kiro Powers

What a Power is

A Power is an installable package that bundles everything an agent needs to be good at a specific tool or framework:

PartProvides
plugin.jsonManifest + keywords that trigger automatic activation
skills/Agent Skills — task-specific instructions and reference material
mcp.jsonOptional MCP server(s) for tool access
dev.kiro/Kiro-specific extensions such as steering files

Powers are built on the Agent Plugins specification — an open, vendor-neutral standard backed by Amazon, Cursor, Microsoft, OpenAI, and Vercel — so a Power isn't locked to Kiro.

The two problems Powers solve

  • Expertise scattered across docs. Getting an agent to genuinely understand a framework's patterns means reading docs and tuning prompts by trial and error, repeated for every new tool. A Power ships that expertise upfront — and from the tool's own makers, not a third-party interpretation.
  • Context overload. Connecting more MCP servers doesn't automatically help; too much unstructured context slows the agent and lowers quality. Powers fix this with intelligent loading.

Intelligent loading

Rather than loading every installed Power's context upfront (which can be 50,000+ tokens), Kiro matches your task description against installed Powers and loads only the relevant ones. Mention "payment" and the Stripe Power activates; switch to database work and Supabase loads instead. You never toggle Powers manually.

Installing & managing

  • One-click install from the IDE / CLI, or the curated registry at kiro.dev/powers.
  • Import a community Power by pasting its GitHub repo URL.
  • Cloud-synced Powers appear in Settings → Powers in Kiro Web and sync to recent IDE versions.

Launch-partner Powers

Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora — each built by the company behind the tool. Examples:

  • Figma — fetch design specs, use Code Connect to map designs to existing components, apply design tokens instead of hard-coded values, validate the build matches the design.
  • Supabase — enforce Row Level Security on every table, generate TypeScript types from the schema, use correct auth patterns, review migrations for security issues.

The "portable across vendors" claim isn't marketing — AWS's open-source AI-DLC ships from a single harness-neutral core and runs natively in Claude Code, Kiro IDE, Kiro CLI, Codex CLI, Cursor, opencode, and GitHub Copilot. The deterministic parts — the stage protocol, the agent roster, the state machine and audit log — are byte-identical everywhere; only a thin shell per tool differs.

  • Use Quick Spec sparingly — the approval gates are what prevent expensive rework.

Guardrails — sensitive code

  • .kiroignore from day one: secrets, .env*, customer-data fixtures, anything under a compliance boundary, large generated dirs.
  • Permissions — restrict what the agent can read and run; default-deny outside the working repo.
  • MCP: only reviewed servers, pinned versions, in one committed workspace mcp.json. autoApprove read-only tools only — never one that writes or calls out.
  • Be deliberate about the Web / Mobile handoff — it sends context off your machine. Keep sensitive work in the IDE.
  • Hooks: non-blocking only until we trust them. No PreToolUse / PromptSubmit blockers early.

Governance to write down before the first bolt

AI-DLC removes the SDLC controls we rely on faster than it replaces them (Module 0). These are ours to add, and it's much cheaper to write them once, up front, than to retrofit onto a team already moving at bolt speed:

  • Named approver per unit of work. A specific person signs off on the AI-drafted plan — and it is not whoever prompted it. Recorded, not just spoken in the mob.
  • One-page review standard. What the approver actually checks: data classifications touched, blast radius, rollback path, and any deviation from the steering files. Without a checklist, sign-off "decays into reflexive clicking within a week".
  • Acceptance tests are an Inception exit criterion. Inception isn't done when requirements exist — it's done when the human-reviewed tests that will judge Construction exist. The agent then implements against a bar it did not set (kills the self-grading problem).
  • One change ticket per unit of work. Run every unit through our existing change process; the artifact trail the spec produces becomes the ticket's evidence. Bolts compress dev time, not change control.
  • Agent evals before scaling one team to more. A pilot team can cover a missing eval harness with attention; five teams can't, and by then agent-written code has outrun anyone's ability to read it.
  • Track defect-escape rate next to cycle time in the retro. 10× speed with 3× escaped defects is not faster.
  • Pilot on a low-blast-radius internal service — not the payments path — so a bad bolt costs embarrassment, not an incident report.

Security controls that run at bolt speed

Hand-typed code was never rate-limited by our scanners — a person can't out-type a nightly SAST job. Under AI-DLC that assumption is gone: velocity is now limited only by review, security, and governance capacity. If scanning runs on a nightly cron and the agent ships every hour, that gap is the exposure window. Security has to move at the cadence of the bolt.

The failure modes AI-DLC adds on top of ordinary appsec — name them so the pilot watches for them:

  • Code that passes lint but is wrong. Syntactically clean and plausible, with an insecure default or a hidden logic flaw. One analysis counted 4,241 CWE instances across a set of AI-generated files.
  • Dependency hallucination. Roughly 20% of AI package suggestions name a package that doesn't exist. Attackers register those names and wait — "slopsquatting". The agent picks dependencies without the human vetting step we used to have.
  • Secrets leak faster. Four of the five most common validated secrets found in public repos are AI-related — a key pasted into a prompt, then committed alongside the generated code.
  • One misconfig, many deploys. A public bucket or an over-broad IAM role in a generated IaC template gets replicated across every environment the agent touches before anyone notices.
  • The pipeline agent is over-privileged. It needs credentials to build, test and deploy; too broad, and a hallucinating or compromised agent does real damage across the environment.
  • Plausible-but-wrong security config. An IAM policy or a security-group rule that reads as correct and quietly allows more than intended.
Why "every scan passed" isn't enough

An agent generates a microservice, picks a base image with known CVEs, provisions a public load balancer, attaches a service account that can read a production data store, and ships it through the automated pipeline. Each artifact passes its own narrow scan. The combination — internet-exposed + vulnerable + over-permissioned + one hop from sensitive data — is a critical attack path, and it's only visible when you look at code, cloud, identity, and data together.

What we put in place for the pilot:

  • Scan every stage the agent touches, at its cadence. SAST, SCA, secrets, IaC and sensitive-data scanning in the IDE, at PR time, in CI, and continuously in production — not just nightly.
  • Least-privilege the agents themselves. Tightly scoped CI/CD and cloud credentials, plus a way to see what each agent can do and what it is doing. This is the .kiroignore + permissions rule above, extended to the pipeline.
  • Triage by exploitability, not by count. A finding is theoretical until you know whether the code is deployed, internet-exposed, what identity it holds, and what data it can reach. When the agent produces hundreds of findings a day, that context is what keeps the queue survivable.
  • Keep the provenance trail. Be able to trace a deployed artifact back to its repo, the agent that generated it, the person who approved it, and the steering / policy that governed it. NIST AI RMF, the EU AI Act and SOC 2 Type II all want a "machine-authored vs human-approved" audit trail — and AI-DLC's structured artifacts (specs, plans, tests, configs) give us one by default if we keep them.
  • Push the decisions that set the attack surface into Inception. Which cloud services, what data, which identity model — decided and reviewed at Inception. A security review there removes whole classes of risk before any code exists.

MODULE 9

AIDLC Collaborative — a managed, multi-user engine

What it is

Every harness in Module 7 is single-developer, git-native, and needs zero infrastructure — you drop a rules file into a repo and go. AWS also ships the opposite trade: AIDLC Collaborative, a hosted reference implementation of the same AI-DLC methodology, built so more than one person — and more than one agent — can work the same intent at once.

It imports the upstream AI-DLC stages, personas, and sensors unmodified, pinned to a ref, and runs them inside Amazon Bedrock AgentCore sessions instead of your terminal. The phases and gates from Module 0 don't change; what changes is where the state lives and who can see it.

Module 0's Principle 10 — "no hard-wired, opinionated SDLC workflow" — is a design constraint here too, not just upstream. The platform imports the methodology as data: a library of nine block types that compose into a workflow, instead of a process baked into the product.

Two namespaces keep this safe: SYSTEM is the vendor baseline, imported from the upstream awslabs/aidlc-workflows repo at a pinned commit and read-only; your own library holds customizations. You don't fork the whole methodology to change one rule — you shadow the one SYSTEM block you want different, and everything else stays on the vendor baseline. Every stage still gets the same three-axis check no matter who authored the block: a deterministic sensor, an LLM-judged reviewer, and a human gate.

How it's built

A React single-page app behind CloudFront talks to API Gateway + Lambda over REST and two WebSocket channels — one for agent progress, one for a Yjs server doing real-time collaborative editing of specs. Neptune (graph database) stores requirements, stories, tasks, reviews, and agent runs as connected, provenance-stamped vertices; DynamoDB holds the operational execution state that drives orchestration and recovery.

Each stage spawns a headless agent CLI — Kiro, Claude Code, or similar — inside a dedicated Bedrock AgentCore microVM with its own filesystem, talking to Neptune and DynamoDB only through a stdio MCP server. And unlike the CLI harnesses, the agent never touches git: the engine clones the repo, owns the aidlc/<title-slug> branch, and commits after every stage exit — success, park, or failure.

What's actually stored

The Neptune graph isn't a generic document store — it has an opinion about what a software project is made of. Authored vertices come straight from your work: Project, Intent, Artifact (the canonical markdown a stage produces) with immutable ArtifactVersion snapshots, Question, Steering (your course corrections), Discussion, PullRequest, and reusable TeamKnowledge / LearningRule nodes. Derived vertices are extracted automatically by parsing that markdown: Section from headings, Requirement, Story (with its persona and acceptance criteria), Persona, Component, Decision, Contract, and UnitOfWork.

Edges fall into three families — ownership (CONTAINS, HAS_SECTION, …), artifact flow (PRODUCES, CONSUMES, DEPENDS_ON, …), and traceability proper (COVERS, IMPLEMENTS, FOR_PERSONA, …) — which is what makes "which code answers this requirement" a graph query instead of a grep. Every write carries provenance: which execution, which stage instance, which parallel lane, and when.

The execution model

An intent moves through DRAFT → CREATED → RUNNING ↔ WAITING → SUCCEEDED / FAILED / CANCELLED. WAITING means it's parked at a human gate — after a short grace period the session itself stops, so a run waiting on you costs zero compute, and resumes with full conversation context the moment you answer.

After the first "walking skeleton" unit is approved, independent units of work fan out into parallel AgentCore sessions, each on its own branch; a failed unit halts and asks rather than cascading. Fan-in is a dependency-ordered, serialised merge back onto the intent branch. You can course-correct a gate answer, revise an earlier decision, rewind to any stage with new guidance, or retry a failure outright — every one of those actions is appended to an immutable, fully audited timeline, never edited in place.

Real-time collaboration, mechanically

Two sync systems do the work: a WebSocket channel broadcasts agent progress and discussion updates, and a Yjs (CRDT) layer handles simultaneous spec editing. Each teammate keeps a local copy that merges automatically — concurrent edits to the same line are both preserved, not last-write-wins — and everyone sees everyone else's cursor with a name label, like a shared doc.

Access is session-scoped: HMAC-signed tokens last 10 minutes, so removing someone from a project doesn't cut them off instantly — their open connection stays valid for at most the remaining token lifetime before the server closes it. Discussions are threaded and open to any member; only Owners and Admins can redact a message.

Git and tracker integration

Two independent axes: code hosts (GitHub, GitLab, Bitbucket) for cloning and opening PRs/MRs, and issue trackers (GitHub Issues, GitLab Issues, Jira Cloud) for starting an intent from an existing ticket — "selecting an issue seeds the intent" with its title, body, and comments as the prompt. An admin registers the OAuth app once per provider; each user then connects their own account (GitHub asks for repo, workflow, read:user; GitLab's api scope covers repo writes including CI config; tokens refresh automatically). Each project picks its own auth independently — one team can be on GitHub while another is on GitLab.

Delivery has the same two modes Module 0's engine offers: Intent PR (the engine merges every unit into the intent branch, one PR at the end) or PR per unit (draft reviews per repository, promoted to mergeable in dependency order). The agent still never holds git credentials — the engine owns the branch, the commits, and the PR.

How one intent flows through the engine

In practice — your first intent

Walkthrough, condensed from the platform's own "first intent" guide
