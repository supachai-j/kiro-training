Building with AWS Kiro

This course takes you from "I've heard of Kiro" to "I can run a feature through a spec, set up steering for our repo, wire an MCP server, and install a Power." It's written for developers who already ship code but are new to Kiro specifically.

Work through the modules in order. Each one is 15–20 minutes, ends with key takeaways and a short Try it task, and every config snippet is copy-pasteable.

The one-line version Kiro is one AI agent that works across IDE, CLI, Web, and Mobile, driven by a .kiro/ folder in your repo. Its headline idea is spec-driven development: agree on requirements and design before the agent writes code, so the output is reviewable and doesn't drift.
Freshness Kiro ships fast. Exact trigger names, flags, and the Powers catalogue can change — treat this course as the mental model and confirm specifics against kiro.dev/docs.
MODULE 0

AI-DLC Foundations

Before the tool, the idea. AI-DLC — the AI-Driven Development Lifecycle — is the methodology Kiro is built to serve. This module is background: where it came from, what it actually says, and why the rest of this course (specs, steering) is AI-DLC in practice. No config here — just the mental model.

One-line version AI-DLC redesigns the software lifecycle around a simple loop: AI drafts the plan and the work, humans make the decisions, the team reviews. It is a methodology, not a product — published by AWS, and Kiro is its most direct implementation.

A short history — how we got here

  1. The hand-written era. The classic SDLC is built around long, human-driven processes: sprints, backlog grooming, estimation, hand-offs between specialised roles. AWS's framing is that teams spend most of their time on "non-core activities such as planning, meetings, and other SDLC rituals" rather than on the product.
  2. AI-assisted coding (≈2021–2023). GitHub Copilot and similar tools bring autocomplete-style help. AI speeds up individual tasks — completion, boilerplate, docs — but the process around it is unchanged. AI is a sidecar bolted onto a human-shaped workflow.
  3. "Vibe coding" (early 2025). Andrej Karpathy popularised the term in a post on X on 2 February 2025: "There's a new kind of coding I call 'vibe coding'" — describe what you want, accept the AI's changes without really reading them, paste errors back in. Karpathy meant it for throwaway weekend projects. It is fast and fun, and produces software with no requirements, no reviewed design, and no shared understanding — fine for a demo, a liability for anything a team maintains.
  4. An AI-native methodology — AI-DLC (mid-2025). AWS's position is that both existing strategies fall short: AI-assisted development is too timid (AI stays a helper), and AI-autonomous development removes human judgement entirely. In AWS's words, both "have produced suboptimal results in terms of velocity and software quality," and "simply retrofitting AI as an assistant not only constrains its capabilities but also reinforces outdated inefficiencies." AI-DLC's answer is to redesign the lifecycle itself around AI doing the work under continuous human direction.

Raja SP, a Principal Solutions Architect at AWS, published the founding description on the AWS DevOps blog on 31 July 2025, alongside a method-definition whitepaper. A follow-up walkthrough with Amazon Q Developer landed on 29 November 2025, and AWS Labs released an open-source workflow engine (awslabs/aidlc-workflows).

The core idea, as one loop

Every phase of AI-DLC runs the same cycle:

AI drafts a detailed plan
      → AI asks clarifying questions
        → a human validates and decides
          → AI executes the approved plan
            → the team reviews the result
              → repeat

The non-negotiable part is the human decision point. AWS: "AI systematically creates detailed work plans, actively seeks clarification and guidance, and defers critical decisions to humans … only humans possess the contextual understanding and knowledge of business requirements needed to make informed choices." The AI keeps its own memory by writing plans, requirements, and design artifacts into the project repository, so work continues cleanly across sessions.

Three phases

PhaseAI producesThe team ritual
InceptionRequirements, user stories, "units of work" from business intentMob Elaboration — the whole cross-functional team validates the AI's questions and proposals together, in real time
ConstructionArchitecture, domain model, code, testsMob Construction — the same group clarifies technical decisions as they surface
OperationsInfrastructure as code, deployment and monitoring configurationThe team reviews outputs and keeps oversight through delivery

Each phase writes context that makes the next phase's AI suggestions sharper.

New vocabulary

Agile termAI-DLC termWhat changed
Sprint (≈2 weeks)Bolt (hours to days)AI does the heavy lifting, so a full validate → execute → review cycle compresses dramatically
EpicUnit of workThe container for a chunk of value, sized for a bolt or a few
Solo work + async hand-offsMob sessionsThe team converges in real time to decide, while AI handles the routine execution between decisions

Where Kiro fits

Keep three levels straight:

  • AI-DLC is the methodology — the phases, the loop, the human-decides rule.
  • Spec-driven development is one way to structure the artifacts AI-DLC calls for.
  • Kiro is a tool built around that structure.

Kiro's requirements.md → design.md → tasks.md is exactly the artifact trail Inception and Construction assume; steering files carry the persistent context the loop depends on. The Kiro CLI can run AWS's aidlc-workflows directly. So Modules 3 and 4 of this course — Specs and Steering — are the Inception and Construction phases of AI-DLC, made concrete.

The number everyone quotes

AWS talks repeatedly cite an internal re-architecture of an Amazon Bedrock service: originally scoped at roughly 18 months for about 30 developers, it was delivered by 6 engineers in about 76 days using AI-DLC with the Amazon Q CLI — on the order of 100,000 lines of production Rust, 40+ commits per week per developer. Rust was chosen partly because its precise compiler errors let the AI diagnose and fix its own mistakes.

Read this critically Those figures come from vendor presentations, not an independently audited benchmark — treat them as a directional signal, not proof. The transferable lesson is the shape: a small team, a very tight loop, and a language whose feedback the AI can act on.

Honest caveats

  • AI-DLC is young (mid-2025) and still moving. The AWS blog and whitepaper are the canonical description; tooling and case studies are catching up.
  • "Mob" sessions assume a real cross-functional team available at the same time. Small or solo teams adapt the model rather than run it as written.
  • It is a vendor methodology — AWS benefits when you adopt it. The underlying principles (requirements before code, humans on the decisions, short loops, context in the repo) hold up regardless of which tool you use.
Key takeaways
  • AI-DLC redesigns the lifecycle around AI does the work, humans decide, team reviews — not AI as autocomplete (too timid) and not AI autonomy (no judgement).
  • The loop: AI plans → AI asks → human validates → AI executes → team reviews → repeat.
  • Phases: Inception (Mob Elaboration) → Construction (Mob Construction) → Operations. Context compounds forward.
  • Vocabulary: Sprint → Bolt, Epic → Unit of work, solo/async → Mob.
  • AI-DLC is the methodology; spec-driven development structures its artifacts; Kiro is the tool. This course's Specs and Steering modules are AI-DLC in practice.
  • The 76-day / 100k-line-Rust story is a vendor anecdote — useful signal, not an audited result.
Try it Skim the AWS founding blog post (link below), then look at your last feature. Which parts were "Inception" (deciding what to build), and which were "Construction"? Where did a missing decision cost you rework? That gap is what the Inception phase exists to close.

MODULE 1

What is Kiro & why

The problem Kiro is built around

Chatting with an AI until code appears — "vibe coding" — is great for exploration and terrible for anything a team has to maintain. You get a working demo, but the requirements only ever lived in the chat scrollback, nobody reviewed the design, and the next change breaks something because there was no shared understanding of what the feature was supposed to do.

Kiro's answer is to make the planning artifacts first-class: written requirements, a written design, and a task list the agent executes against — all stored in your repo, all reviewable like code. You still get to vibe when you want to; you just have a structured path for the work that matters.

One agent, every surface

Kiro is not just an IDE. It's a single agent "harness" exposed through several interfaces:

SurfaceWhat it's for
IDE (desktop app)The main experience — editor, chat panel, specs, steering, hooks UI.
CLIDrive the same agent from the terminal or scripts / CI.
WebBrowser-based agent; hand off long-running tasks.
MobileCheck in on tasks from your phone (no MCP).

The important part: your .kiro/ configuration is shared across all of them and travels with the repository. Set up steering once, and it applies whether a teammate is in the IDE or CI is running the CLI.

What's in the box

AreaFeatureCovered in
PlanningSpecs, Bugfix Specs, Chat (vibe)Modules 2–3
ControlSteering, Hooks, MCP, Permissions, .kiroignoreModules 4–6
AdvancedCustom agents, Skills, Sub-agents, Checkpoints / rewind, CompactionModules 2 & 8
EcosystemPowers (installable capability packs)Module 7

The .kiro/ directory

Everything project-specific lives in one folder at the repo root. You commit it like any other source:

.kiro/
├── steering/          # persistent project knowledge (Module 4)
│   ├── product.md
│   ├── tech.md
│   └── structure.md
├── hooks/             # event-driven automation as JSON (Module 5)
│   └── lint-on-save.json
├── specs/             # one folder per feature / bugfix (Module 3)
│   └── checkout-refactor/
│       ├── requirements.md
│       ├── design.md
│       └── tasks.md
└── settings/
    └── mcp.json       # external tool connections (Module 6)

Getting started

  1. Install the IDE (desktop), the CLI, or use the Web agent.
  2. Sign in with the account your org uses.
  3. Import your VS Code settings when prompted — keybindings, theme, and extensions carry over, so the IDE feels familiar on day one.
  4. Open a real repo and run "Generate Steering Docs" (Module 4) so the agent has project context before you ask it anything.
Key takeaways
  • Kiro = one agent, many surfaces (IDE / CLI / Web / Mobile), one shared .kiro/ config in your repo.
  • Its core bet is spec-driven development: requirements + design as reviewable files, not chat history.
  • You still have free-form "vibe" mode for exploration and debugging.
  • .kiro/ holds steering/, hooks/, specs/, and settings/mcp.json.
Try it Install the IDE, open a small side project, import your VS Code settings, and run "Generate Steering Docs". Read the three files it produces — that's your first look at how Kiro sees your project.
MODULE 2

Vibe / Chat mode

The default agent

When you open the chat panel, you're talking to the Default agent — "vibe" mode. It's free-flow: describe what you want in natural language and Kiro responds with edits, explanations, or commands. There's no required structure and no generated documents. Use it for:

  • Questions about the codebase ("where do we validate the JWT?")
  • Debugging a specific failure
  • Small, local changes
  • Exploring an approach before committing to a spec

Vibe vs Spec — and the modes in between

ModeOutputUse when
Vibe (Default)Direct edits / answers, no docsQuestions, debugging, exploratory work
Specrequirements.md + design.md + tasks.mdFeature work that needs review or touches several files
PlanA plan only — no code changesYou want the approach written down before anything moves
Bug FixBug analysis → fixReproducible defect; you want regression protection
Quick SpecBrief clarification, then auto-generated specSmall feature, you trust the agent to fill in the gaps

Autopilot vs Supervised

Independently of the mode, you choose how much rope the agent gets:

  • Supervised — you approve every file change before it lands. Slower, safe, and the right default while you're learning a workflow.
  • Autopilot — the agent executes changes autonomously and you review the result. Good for narrow, well-scoped tasks you've seen it do reliably.
Rule of thumb Stay Supervised until you've watched the agent do this kind of task correctly a few times. Then move that specific task type to Autopilot — not everything at once.

Context providers — the # menu

Kiro only knows what's in its context. The # prefix pulls specific things in:

ProviderAdds
#codebaseKiro searches the repo and pulls in the files it judges relevant
#file / #folderA specific file or directory you name
#git diffYour uncommitted changes
#terminalRecent command output and history
#problemsDiagnostics / errors for a file
#url · #docs · #repository · #code · #mcpExternal page, docs, another repo, a code snippet, or an MCP resource

Combine them in one message: Fix the failing test in #problems using the pattern from #file:src/auth/session.ts.

You can also paste an image (a screenshot, a mockup, an error dialog) directly into chat as context.

Long sessions: checkpoints and compaction

  • Checkpoints / rewind — Kiro snapshots state as it works, so you can roll back to a known-good point instead of unpicking changes by hand.
  • Compaction — when a session gets long, Kiro summarises earlier context to stay within the model's limits without losing the thread.
Key takeaways
  • Vibe = free-form, no docs. Spec = structured docs. Plan / Bug Fix / Quick Spec sit in between.
  • Supervised vs Autopilot is a separate choice — start Supervised, graduate task types one at a time.
  • # providers are how you feed the agent: #codebase, #file, #git diff, #terminal, #problems, and more — combine freely.
  • Checkpoints let you rewind; compaction keeps long sessions coherent.
Try it In vibe mode, ask: Explain how #file:<some entry point> wires up the app, then list the top 3 risks in #git diff. Notice how the answer quality tracks exactly what you put in context.
MODULE 3

Specs

What a spec is

A spec is a structured set of artifacts that formalises how a feature or bug fix gets built. Instead of one long chat, you get three files in .kiro/specs/<name>/, each gated by your approval:

FileContents
requirements.md (or bugfix.md)User stories + acceptance criteria (feature), or current / expected / unchanged behaviour (bug)
design.mdArchitecture, component breakdown, sequence diagrams, data flow, error handling, testing strategy
tasks.mdDiscrete, individually trackable implementation tasks with live status

The three-phase workflow

  1. Requirements — Kiro drafts user stories and acceptance criteria from your description. You edit and approve before anything else happens.
  2. Design — Kiro turns approved requirements into a technical design. Review it here; this is the cheapest place to catch a wrong approach.
  3. Tasks — Kiro breaks the design into an ordered task list, then implements task by task, updating status as it goes.
Why the gates matter Fixing a misunderstanding in requirements.md costs a sentence. Fixing it after the agent has written 12 files costs an afternoon. The approval gates exist to force the cheap conversation first.

EARS notation for requirements

Kiro writes acceptance criteria in EARS (Easy Approach to Requirements Syntax) — a small set of sentence templates that keep requirements testable and unambiguous:

WHEN <trigger> THE SYSTEM SHALL <response>
WHILE <state> THE SYSTEM SHALL <response>
WHERE <feature is included> THE SYSTEM SHALL <response>
IF <condition> THEN THE SYSTEM SHALL <response>

Example: WHEN a user submits the checkout form with an expired card THE SYSTEM SHALL reject the payment and display "Your card has expired". Each line becomes a test.

Task execution in waves

Kiro analyses dependencies between tasks and builds a dependency graph, then runs them in waves:

  • Wave 1 — tasks with no dependencies, run concurrently.
  • Wave 2+ — tasks whose dependencies are now satisfied, run concurrently.
  • Waves run in sequence; tasks inside a wave run in parallel.

You don't configure this — it's automatic, and it's why a spec often finishes faster than issuing the same tasks one at a time in chat.

Spec types

TypeFlavoursNotes
Feature SpecRequirements-First, Design-First, or Quick Spec (auto-generated, no approval gates)New capability
Bugfix SpecAnalyse current vs expected vs unchanged behaviour, then fixSurgical; built to prevent regressions
Key takeaways
  • A spec = requirements.md → design.md → tasks.md, each behind an approval gate.
  • Requirements use EARS templates so every criterion is testable.
  • Tasks run in dependency-ordered waves with parallelism inside each wave — automatically.
  • Use a Bugfix Spec for defects: it explicitly records what must not change.
  • Keep specs small. One coherent feature per spec beats one giant spec.
Try it Pick a small feature you actually need. Start a Feature Spec, and stop at the requirements phase. Read the EARS criteria, tighten two of them, then approve and let it design.
MODULE 4

Agent Steering

Persistent project knowledge

Steering gives Kiro durable context about your project through markdown files, so you stop re-explaining the same conventions in every conversation. Steering files live in .kiro/steering/ and are plain markdown.

The three foundation files

"Generate Steering Docs" creates these, and they're included in every interaction by default:

FileCaptures
product.mdProduct purpose, target users, key features, business goals — the "why" behind technical decisions
tech.mdFrameworks, libraries, tools, constraints — so Kiro favours your stack over alternatives
structure.mdFile organisation, naming conventions, import patterns, architectural decisions

Scopes

ScopeLocationApplies to
Workspace.kiro/steering/Just this repo (wins on conflict)
Global~/.kiro/steering/All your workspaces
TeamGlobal, distributed via MDM / Group Policy / a repoEveryone in the org

Inclusion modes (YAML front-matter)

A front-matter block at the top of a steering file controls when it loads:

---
inclusion: always          # default — every interaction
---
---
inclusion: fileMatch
fileMatchPattern: ["**/*.tsx", "src/components/**/*"]
---
# loads only when you're working on matching files
---
inclusion: manual          # load on demand with #file-name in chat, or via /
---
---
inclusion: auto
name: api-design
description: REST API design patterns. Use when creating API endpoints.
---
# loads when your request matches the description

Referencing live files

Point a steering file at a real file in the repo so guidance stays in sync with source:

Follow the schema in #[[file:api/openapi.yaml]]
Match the component pattern in #[[file:components/ui/button.tsx]]

AGENTS.md and custom agents

  • Kiro also reads the cross-tool AGENTS.md standard — put one at the workspace root or in ~/.kiro/steering/. It has no inclusion modes; it's always included.
  • Custom agents don't get steering automatically. Add it explicitly: "resources": ["file://.kiro/steering/**/*.md"].

Best practices

  • One domain per file — api-rest-conventions.md, testing-unit-patterns.md, security-guidelines.md.
  • Explain the reasoning, not just the rule. Include before/after code snippets.
  • Never put secrets, keys, or passwords in steering files.
  • Review steering changes like code — they change agent behaviour for the whole team.
Key takeaways
  • Steering = markdown in .kiro/steering/ that gives Kiro persistent project context.
  • product.md / tech.md / structure.md load on every interaction.
  • Front-matter inclusion controls loading: always, fileMatch, manual, auto.
  • #[[file:path]] links guidance to live source; AGENTS.md is always included.
  • Commit steering to the repo and review changes — it's shared team behaviour.
Try it Add .kiro/steering/code-style.md with 5 real rules from your team (naming, error handling, imports) and one before/after example. Ask the agent to write a small function and check it obeys all five.
MODULE 5

Agent Hooks

Automation on events

A hook runs a shell command or an agent prompt automatically when something happens in your session. Hooks are JSON files in .kiro/hooks/ and activate when a session starts — no manual registration.

Trigger types

CategoryTriggers
File (IDE)PostFileCreate, PostFileSave, PostFileDelete
ExecutionPreToolUse / PostToolUse (Pre can block), PromptSubmit (can block)
LifecycleSessionStart (IDE), AgentSpawn (CLI), AgentStop
Task (IDE)PreTaskExecution / PostTaskExecution — around spec tasks
Important File triggers only fire on agent-initiated changes — not when you edit and save a file yourself in the editor.

Hook file format

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}
FieldMeaning
triggerEvent type, PascalCase
matcherOptional regex to filter which events fire the hook
action.type"command" (run a shell command) or "agent" (inject a prompt)
timeoutSeconds before the hook is killed (default 60)

Common use cases

  • Run linters, formatters, or type checks after the agent changes files.
  • Auto-create tests, docs, or translations when a new source file appears.
  • Block a tool with PreToolUse unless a precondition is met.
  • Run a quality check before the agent finalises its changes.

Creating hooks

In the IDE: the + button in the Agent Hooks panel → "Ask Kiro to create a hook" → describe the automation in plain language and Kiro writes the JSON. Use kebab-case filenames (lint-on-save.json); related hooks can share one file.

Key takeaways
  • Hooks = JSON in .kiro/hooks/; they run commands or agent prompts on events.
  • Triggers span file changes, tool use, session lifecycle, and spec tasks.
  • File triggers respond to agent edits only, not your manual saves.
  • PreToolUse and PromptSubmit can block — powerful, so introduce them carefully.
  • Use matcher regexes to keep hooks narrowly targeted.
Try it Create a PostFileSave hook that runs your formatter on \\.(ts|js)$. Ask the agent to add a function, then confirm the file comes back formatted without you touching it.
MODULE 6

MCP — Model Context Protocol

What MCP does

MCP is a protocol that lets Kiro talk to external servers to use specialised tools, prompts, and resources that aren't baked into the model — internal knowledge bases, ticketing systems, cloud APIs, docs search, and so on.

Where config lives

LevelHow to openScope
WorkspaceCommand palette → "Kiro: Open workspace MCP config (JSON)"This repo (commit it to share with the team)
UserCommand palette → the user MCP configAll your projects
AgentmcpServers in a custom agent, with includeMcpJson to inherit or notThat agent only

Server types

TypeIDECLIWebMobile
Local (stdio)✓✓✓—
Remote (HTTP / SSE)✓✓✓—

Config example

{
  "mcpServers": {
    "fetch": {
      "command": "uvx",
      "args": ["mcp-server-fetch"],
      "disabled": false
    },
    "aws-docs": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@latest"],
      "disabled": false,
      "autoApprove": ["search_documentation"]
    }
  }
}
FieldMeaning
command / argsHow to launch a stdio server
disabledToggle the server off without deleting the entry
autoApproveTool names allowed to run without a per-call prompt — keep this to read-only tools
envEnvironment variables (e.g. API keys) — reference secrets, don't hard-code them

The AWS Documentation MCP server is a common first server: it gives the agent direct access to search AWS docs and return current, cited guidance instead of relying on training data.

Managing & troubleshooting

  • Watch connection status in the MCP Servers tab; read logs in the Output tab.
  • Kiro shows a confirmation dialog before applying an install link, listing commands and env var names (values hidden).
  • Tool names must match ^[a-zA-Z][a-zA-Z0-9_]*$ and stay under 64 characters, or you'll get validation errors.
Security Only install MCP servers from sources you trust — a server can run code on your machine and see whatever context the agent sends it. Vet the package, pin versions, and never commit secrets.
Key takeaways
  • MCP connects Kiro to external tools / data via mcp.json at workspace, user, or agent level.
  • Local (stdio) and remote (HTTP/SSE) servers both work everywhere except Mobile.
  • disabled toggles a server; autoApprove should list read-only tools only.
  • Commit a vetted workspace mcp.json so the team shares the same servers.
  • Treat MCP servers as supply-chain risk: trusted sources, pinned versions, secrets via env.
Try it Add the AWS Documentation MCP server to a workspace mcp.json. Ask the agent a question that needs current AWS docs and watch it call the tool instead of guessing.
MODULE 7

Kiro Powers

What a Power is

A Power is an installable package that bundles everything an agent needs to be good at a specific tool or framework:

PartProvides
plugin.jsonManifest + keywords that trigger automatic activation
skills/Agent Skills — task-specific instructions and reference material
mcp.jsonOptional MCP server(s) for tool access
dev.kiro/Kiro-specific extensions such as steering files

Powers are built on the Agent Plugins specification — an open, vendor-neutral standard backed by Amazon, Cursor, Microsoft, OpenAI, and Vercel — so a Power isn't locked to Kiro.

The two problems Powers solve

  • Expertise scattered across docs. Getting an agent to genuinely understand a framework's patterns means reading docs and tuning prompts by trial and error, repeated for every new tool. A Power ships that expertise upfront — and from the tool's own makers, not a third-party interpretation.
  • Context overload. Connecting more MCP servers doesn't automatically help; too much unstructured context slows the agent and lowers quality. Powers fix this with intelligent loading.

Intelligent loading

Rather than loading every installed Power's context upfront (which can be 50,000+ tokens), Kiro matches your task description against installed Powers and loads only the relevant ones. Mention "payment" and the Stripe Power activates; switch to database work and Supabase loads instead. You never toggle Powers manually.

Installing & managing

  • One-click install from the IDE / CLI, or the curated registry at kiro.dev/powers.
  • Import a community Power by pasting its GitHub repo URL.
  • Cloud-synced Powers appear in Settings → Powers in Kiro Web and sync to recent IDE versions.

Launch-partner Powers

Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora — each built by the company behind the tool. Examples:

  • Figma — fetch design specs, use Code Connect to map designs to existing components, apply design tokens instead of hard-coded values, validate the build matches the design.
  • Supabase — enforce Row Level Security on every table, generate TypeScript types from the schema, use correct auth patterns, review migrations for security issues.

Powers vs Skills vs Steering

MechanismIs
SteeringKiro-specific behaviour shaping via markdown you write
SkillsStandalone instruction packages
PowersInstallable, context-aware packages that combine tools + knowledge + guidance
Key takeaways
  • A Power bundles skills/ + optional mcp.json + dev.kiro/ steering, described by plugin.json.
  • Built on the open Agent Plugins spec — portable across vendors.
  • Intelligent loading pulls in only the Powers relevant to your current task.
  • Install from kiro.dev/powers, the IDE, or a community GitHub URL.
  • You can package your team's own standards + internal MCP as a private Power.
Try it Install a Power relevant to your stack (e.g. Supabase or AWS Aurora). Start a task that mentions its domain and confirm the Power activates on its own — check the editor's Powers indicator.
MODULE 8

Team adoption playbook

This is our plan — a small team (2–5 devs) on GitHub, shipping TypeScript/Node/React, Python, and JVM/.NET/Go on AWS. It's not Kiro documentation; revise it as we learn.

Week 1 — everyone on board

  • The whole team is the pilot. We're small enough that a "subset first" phase would only add coordination overhead.
  • Everyone installs the IDE, signs in, imports VS Code settings.
  • Pick one active repo. Run "Generate Steering Docs", then hand-edit product.md / tech.md / structure.md in a PR until they're actually true. Merge it — steering lands through review from day one.

Steering for a polyglot team

Structure steering so each language's rules load only when relevant:

FileModeContents
security.md, structure.md, code-review.mdalwaysCross-cutting rules. Keep them short — they cost tokens every turn.
code-style-ts.mdfileMatch **/*.{ts,tsx}Naming, error handling, React patterns
code-style-python.mdfileMatch **/*.pyTyping, packaging, lint rules
code-style-jvm.mdfileMatch **/*.{java,kt,cs,go}Per-language conventions
infra-aws.mdfileMatch infra/**, **/*.tfTagging, IAM least-privilege, region rules

Each file holds the rules we already argue about in review, with one before/after example and the reason behind the rule.

When to use a spec — ticket-driven

Our rule of thumb If it has a ticket, it gets a spec folder named after the ticket: .kiro/specs/PROJ-1234-checkout-retry/. No ticket and trivial? Vibe it.
  • Feature ticket → Feature Spec. Read and tighten requirements.md before approving design.
  • Bug ticket → Bugfix Spec. It records what must not change — the regression protection reviewers ask for.
  • Commit the spec folder in the same PR as the code, so the reasoning ships with the change.

Cost discipline

  • Keep always steering short; push everything else to fileMatch / manual.
  • Let compaction handle long sessions instead of starting over.
  • Supervised by default. An Autopilot run that goes wrong burns the whole run plus your review time. Move a task type to Autopilot only after it's been boringly reliable.
  • Use Quick Spec sparingly — the approval gates are what prevent expensive rework.

Guardrails — sensitive code

  • .kiroignore from day one: secrets, .env*, customer-data fixtures, anything under a compliance boundary, large generated dirs.
  • Permissions — restrict what the agent can read and run; default-deny outside the working repo.
  • MCP: only reviewed servers, pinned versions, in one committed workspace mcp.json. autoApprove read-only tools only — never one that writes or calls out.
  • Be deliberate about the Web / Mobile handoff — it sends context off your machine. Keep sensitive work in the IDE.
  • Hooks: non-blocking only until we trust them. No PreToolUse / PromptSubmit blockers early.

MCP & Powers to start with

  • AWS Documentation MCP server in the shared mcp.json — the common thread across our stacks.
  • Install the AWS Aurora Power, plus any partner Power matching a service we lean on.
  • Once steering is stable, package our conventions + an internal MCP as a private Power so a new hire's agent is useful on day one.

Key takeaways
  • Small team: everyone pilots at once, on one active repo.
  • Steering: a tiny always set plus per-language fileMatch files, all via PR.
  • Every ticket gets a spec folder named after it; the spec ships in the code PR.
  • Sensitive code: .kiroignore + Permissions + Supervised + vetted read-only MCP; keep sensitive work off Web/Mobile.
  • Cost: short always steering, lean on compaction, don't let Autopilot run unwatched.
