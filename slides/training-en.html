0 · AI-DLC — the idea behind Kiro

AI-Driven Development Lifecycle: a methodology (not a product) that rebuilds the lifecycle around AI does the work, humans decide, the team reviews.

  • Hand-written SDLC → AI-assisted autocomplete → "vibe coding" (Karpathy, Feb 2025) → an AI-native lifecycle
  • Rejects both extremes: AI-assisted is too timid; AI-autonomous drops human judgement
  • Published by AWS (Raja SP), AWS DevOps Blog, 31 Jul 2025
Before we touch the tool, the idea. AWS looked at the two obvious options and said both fall short. Bolt AI on as a helper, and you keep the same slow process. Let it run loose, and you throw away the human judgement that matters. So they rebuilt the lifecycle around a middle path. AI does the work, you make the calls. Kiro is how you actually do that.

0 · The loop and the three phases

AI drafts a plan → AI asks questions → human validates
   → AI executes → team reviews → repeat
PhaseAI producesTeam ritual
InceptionRequirements, stories, units of workMob Elaboration
ConstructionArchitecture, code, testsMob Construction
OperationsIaC, deploy, monitoringTeam oversight
Every phase runs the same little loop. And there's one step you never skip: the human decision. AWS put it plainly. Only a person has the business context to make that call. The AI writes its plan and its requirements straight into the repo, so nothing's lost when you close the laptop. Each phase hands richer context to the next.

Methodology = AI-DLC · artifact structure = spec-driven dev · tool = Kiro. Kiro's requirements → design → tasks is the Inception/Construction trail.

Widely quoted: an Amazon Bedrock re-architecture, ~18 months / 30 devs → ~76 days / 6 engineers, ~100k lines of Rust. Vendor anecdote — signal, not proof.

Three words, three levels. AI-DLC is the method. Spec-driven development is how you shape the paperwork it asks for. Kiro is the tool. Those three spec files you'll see in a minute are the Inception and Construction trail, made real. Oh, and that hundred-thousand-lines-of-Rust story? It's from a vendor talk. Take it as a direction, not a benchmark.

1 · What is Kiro

One AI agent, exposed through IDE, CLI, Web, and Mobile — driven by a shared .kiro/ folder in your repo.

  • Core idea: spec-driven development — requirements & design as reviewable files, before code
  • Free-form "vibe" mode still available for exploration & debugging
  • Config travels with the repository — set up once, applies everywhere
Here's the one thing to hold onto. Kiro isn't just an editor. It's a single agent sitting behind several front doors: the IDE, your terminal, a browser, your phone. And its behaviour comes from a folder in your repo called dot-kiro. The headline? Your requirements and your design stop being chat messages and become real files you review.

1 · One agent, every surface

SurfaceFor
IDE (desktop)Main experience: editor, chat, specs, steering, hooks UI
CLISame agent from terminal / CI scripts
WebBrowser agent; long-running tasks
MobileCheck on tasks (no MCP)

Your .kiro/ config is shared across all of them.

Same brain, different doors. You might kick off a task in the IDE, glance at it from your phone on the train, and let CI run the command-line version against the exact same rules. Why does it stay consistent? Because dot-kiro is checked into git, right next to the code.

1 · The .kiro/ directory

.kiro/
├── steering/          # persistent project knowledge
│   ├── product.md  ·  tech.md  ·  structure.md
├── hooks/            # event-driven automation (JSON)
├── specs/            # one folder per feature / bugfix
│   └── <name>/ requirements.md · design.md · tasks.md
└── settings/
    └── mcp.json      # external tool connections

Commit it like any other source. Review changes like code.

This is the whole surface area, so get comfortable with it. Steering is markdown, that's project context. Hooks are little JSON automations. Specs are one folder per feature, three documents each. And mcp-dot-json wires in outside tools. Everything in here goes through pull request review, because it changes how the agent works for the whole team.

2 · Vibe vs Spec

ModeOutputUse when
Vibe (default)Direct edits / answersQuestions, debugging, exploring
Specrequirements + design + tasksReviewable feature work
PlanPlan only, no changesWrite the approach down first
Bug FixAnalysis → fixReproducible defect
Quick SpecAuto-generated specSmall feature, trust the agent
Vibe mode is the default. You just talk to your codebase. No documents, no ceremony. Spec is the structured route. Plan, Bug Fix and Quick Spec sit somewhere between. Here's the rule I use. If someone's going to review it, or ask why we built it this way later, it's a spec. Everything else? Vibe it.

2 · Autopilot vs Supervised

Supervised

  • Approve every change
  • Safe default while learning
  • Slower

Autopilot

  • Agent executes, you review the result
  • For narrow, proven task types

Stay Supervised until you've watched the agent do this kind of task right a few times — then graduate that one task type.

This is a separate dial from the mode. Start with Supervised on everything. You approve each change. Then, once you've watched the agent nail one specific kind of task a few times, say adding a test file, move that one task type to Autopilot. Just that one. Don't flip the whole thing at once and hope.

2 · Context providers — #

ProviderAdds
#codebaseKiro finds relevant files
#file / #folderA path you name
#git diffUncommitted changes
#terminalRecent command output
#problemsDiagnostics for a file
#docs · #url · #mcpExternal docs, a page, an MCP resource

Combine them in one message. You can paste images too.

Kiro only knows what you put in front of it. The hash menu is how you hand it things. Mix them freely. The failing test from hash-problems, plus the pattern in one file, plus your uncommitted diff. The answer is only as good as the context, so be picky about what you pull in. You can drop in a screenshot too.

3 · What a spec is

Three reviewable files in .kiro/specs/<name>/, each behind your approval:

FileContents
requirements.mdUser stories + acceptance criteria (EARS)
design.mdArchitecture, diagrams, error handling, test strategy
tasks.mdDiscrete tasks with live status
A spec swaps one endless chat for three short documents. You sign off on the requirements before any design gets written. You sign off on the design before any code runs. Each of those gates is a moment where fixing a misunderstanding still costs you a sentence, not a weekend.

3 · Three phases, three gates

  1. Requirements — edit & approve the user stories
  2. Design — review the approach; cheapest place to catch a wrong turn
  3. Tasks — agent implements task by task, updating status

A misunderstanding fixed in requirements.md costs a sentence. Fixed after 12 files, it costs an afternoon.

The gates are the entire point. It's really tempting to skim the requirements and hit go. Don't. Two minutes tightening the acceptance criteria will save you a rewrite. And the design review is your second-cheapest chance to steer the whole thing somewhere better.

3 · EARS notation

WHEN  <trigger>              THE SYSTEM SHALL <response>
WHILE <state>                THE SYSTEM SHALL <response>
WHERE <feature included>     THE SYSTEM SHALL <response>
IF    <condition> THEN       THE SYSTEM SHALL <response>

// Example
WHEN a user submits checkout with an expired card
THE SYSTEM SHALL reject the payment and show "Your card has expired"

Each line becomes a test.

EARS is just a handful of sentence shapes. When this happens, the system shall do that. The point is that every line is unambiguous, and you can turn it straight into a test. So when you're reviewing requirements, take any woolly sentence and force it into one of these shapes.

3 · Tasks run in waves

  • Kiro builds a dependency graph from the task list
  • Wave 1 — no-dependency tasks, run concurrently
  • Wave 2+ — tasks whose deps are now met, concurrently
  • Waves are sequential; tasks inside a wave are parallel
  • Automatic — no configuration

Why a spec often finishes faster than the same tasks typed one-by-one.

You don't set any of this up. Kiro looks at the task list, works out which ones don't depend on each other, and runs those together. Then the next batch. Then the next. That parallelism is a real speed-up over typing tasks one at a time into a chat.

4 · Agent Steering

Markdown in .kiro/steering/ that gives Kiro persistent project knowledge.

Foundation fileCaptures
product.mdPurpose, users, goals — the "why"
tech.mdStack, tools, constraints
structure.mdFile layout, naming, conventions

Generated by "Generate Steering Docs" · loaded on every interaction.

Steering is how you stop explaining your project from scratch every single conversation. Generate the three foundation files, then, and this matters, hand-edit them until they're actually true. What the generator gives you is a rough draft. Those three files load into every interaction, so they need to be right.

4 · Inclusion modes

---
inclusion: always            # default — every interaction
---
---
inclusion: fileMatch
fileMatchPattern: ["**/*.tsx", "src/components/**/*"]
---
---
inclusion: manual            # load with #file-name in chat
---
---
inclusion: auto
name: api-design
description: REST API patterns. Use when creating endpoints.
---
The front-matter at the top of a steering file decides when it loads. Always, for the rules that apply everywhere. fileMatch to scope guidance to one part of the codebase. Manual when you want to call it up by name. Auto when a description should trigger it. And keep the always-files lean. They cost you tokens on every single turn.

4 · References, AGENTS.md, practice

  • Link live files: #[[file:api/openapi.yaml]]
  • AGENTS.md (repo root or ~/.kiro/steering/) — always included, no modes
  • Custom agents need "resources": ["file://.kiro/steering/**/*.md"]
  • One domain per file · explain the why · no secrets · review like code
Point steering at real files, so it can't quietly drift from the source. Kiro also reads the cross-tool AGENTS.md standard, if you've got one. One thing people trip on: custom agents don't inherit steering automatically. You list it in their resources. And every steering change is a pull request, same as code.

5 · Agent Hooks

JSON in .kiro/hooks/ — run a command or agent prompt automatically on an event.

CategoryTriggers
File (IDE)PostFileCreate/Save/Delete
ExecutionPreToolUse/PostToolUse, PromptSubmit (can block)
LifecycleSessionStart, AgentSpawn, AgentStop
Task (IDE)PreTaskExecution/PostTaskExecution
A hook runs something when an event fires. A shell command, or a prompt back to the agent. They live as JSON and switch on when your session starts. The blocking ones, PreToolUse and PromptSubmit, are powerful. Save those for last, once the team trusts the gentle ones.

5 · Hook file format

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}

action.type: "command" (shell) or "agent" (inject a prompt). File triggers fire on agent edits only.

The matcher is a regex. It narrows down which events actually fire the hook. The action is either a shell command, or a prompt you hand to the agent. And the gotcha worth saying twice: file triggers respond to the agent's edits, not to you saving a file yourself.

5 · What hooks are for

  • Run linters / formatters / type checks after agent edits
  • Auto-create tests, docs, or translations for new source files
  • Block a tool with PreToolUse until a precondition holds
  • Quality check before the agent finalises

Create in IDE: + in Agent Hooks → "Ask Kiro to create a hook" → describe it.

Start with two, both low-risk. Format on save. And scaffold a test file when a new source file shows up. You describe what you want in plain English, Kiro writes the JSON, and then you review that JSON in a pull request, just like any other code.

6 · MCP — Model Context Protocol

Lets Kiro use tools, prompts, and resources from external servers.

LevelScope
Workspace mcp.jsonThis repo — commit to share
User mcp.jsonAll your projects
Agent mcpServersThat agent only

Local (stdio) & remote (HTTP/SSE) — everywhere except Mobile.

MCP is the plug for anything the model doesn't know on its own. Your internal wiki, your ticketing system, a cloud API, live docs search. The config sits at three levels. The one that matters for a team is a committed workspace file, so everybody's running the same servers you've actually checked.

6 · mcp.json example

{
  "mcpServers": {
    "aws-docs": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@latest"],
      "disabled": false,
      "autoApprove": ["search_documentation"]
    }
  }
}

disabled toggles without deleting · autoApprove = read-only tools only · secrets via env, never committed.

The AWS Documentation server is a great first one. Instead of guessing from training data, the agent searches the real docs and comes back with a link. Keep autoApprove to read-only tools only. Anything that changes state should still stop and ask you first.

6 · Treat servers as supply chain

Only install MCP servers from sources you trust — a server runs code on your machine and sees the context the agent sends it.

  • Vet the package · pin versions · secrets via env
  • Kiro confirms install links, showing env var names (values hidden)
  • Tool names: ^[a-zA-Z][a-zA-Z0-9_]*$, < 64 chars
This is the security slide. An MCP server is code running on your machine, and it can see whatever context the agent sends it. So we check every server before it goes in the shared file. We pin the version. And credentials live in environment variables that never get committed.

7 · Kiro Powers

Installable packages that make the agent good at a specific tool or framework.

PartProvides
plugin.jsonManifest + activation keywords
skills/Task-specific instructions
mcp.jsonOptional tool access
dev.kiro/Steering & Kiro extensions

Built on the open Agent Plugins spec (Amazon, Cursor, Microsoft, OpenAI, Vercel).

A Power is steering, plus skills, plus maybe an MCP server. Bundled so you install it in one click. It's built on a vendor-neutral standard, so the same bundle works in Cursor or Copilot too. Think of it as expertise for a framework, packaged by the people who actually built that framework.

7 · Two problems, one mechanism

Problem

  • Expertise scattered across docs
  • Context overload from too many MCP servers

Intelligent loading

  • Kiro matches your task to installed Powers
  • Loads only the relevant ones — not 50k+ tokens upfront

Say "payment" → Stripe activates. Switch to DB work → Supabase loads instead.

Here's the thing. Connecting more servers doesn't automatically make the agent smarter. Too much unstructured context actually buries it. Powers fix that by loading on demand. You never toggle anything. What you're working on decides which Power's knowledge shows up.

7 · Install & partners

  • One-click from IDE / CLI or the registry at kiro.dev/powers
  • Import a community Power by GitHub URL
  • Cloud-synced Powers in Settings → Powers

Launch partners: Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora

Each partner Power is built by the company behind the tool. Figma's own design-to-code guidance. Supabase's own security patterns. And once your steering has settled down, you can wrap your team's own conventions and your internal MCP server into a private Power of your own.

7 · Powers vs Skills vs Steering

MechanismIs
SteeringKiro-specific behaviour shaping — markdown you write
SkillsStandalone instruction packages
PowersInstallable, context-aware — tools + knowledge + guidance
Quick untangle. Steering is yours. Hand-written, Kiro only. A skill is a portable bundle of instructions. A Power wraps skills and MCP and steering together into one installable thing that loads itself when it's relevant. Powers are the distribution format.

8 · Adoption — week 1

  • Small team (2–5, GitHub) → everyone pilots at once, on one active repo
  • Everyone: install IDE, sign in, import VS Code settings
  • "Generate Steering Docs" → hand-edit in a PR until true → merge
  • Polyglot steering: tiny always set + per-language fileMatch files (code-style-ts.md, -python.md, infra-aws.md)
We're small, so there's no try-it-with-a-couple-of-people-first phase. Everyone starts, on one real repo. First thing you ship is foundation steering that's genuinely accurate. And since we work in a few languages, split the style rules into fileMatch files, so each one only loads when you're in that language.

8 · Ticket-driven specs, cost discipline

If it has a ticket, it gets a spec folder named after the ticket. No ticket and trivial? Vibe it.

  • Feature ticket → Feature Spec · bug ticket → Bugfix Spec
  • Commit the spec folder in the same PR as the code
  • Cost: short always steering, lean on compaction, Supervised by default
Every ticket gets its own spec folder, named after the ticket, committed alongside the code. So the reasoning travels with the change. On cost: an Autopilot run that goes wrong burns the whole run plus your review time. So we stay Supervised until a task type is genuinely boring.

8 · Guardrails — sensitive code

  • .kiroignore day one: secrets, .env*, customer data, compliance-scoped dirs
  • Permissions default-deny outside the working repo
  • MCP: reviewed + pinned only; autoApprove read-only tools
  • Keep sensitive work in the IDE — Web / Mobile send context off your machine
  • Start with AWS Docs MCP + AWS Aurora Power
Some of our code is sensitive. So kiroignore and Permissions go in on day one, and we never auto-approve a tool that writes or calls out. The Web and Mobile surfaces send context off your machine, so sensitive work stays in the IDE. AWS docs and the Aurora Power are where we start.
