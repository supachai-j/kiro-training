Welcome. Kiro is AWS's AI development environment, and today we're covering what it is, how spec-driven development changes the workflow, and the four control surfaces we'll actually configure in our repo: steering, hooks, MCP, and Powers. By the end you should be able to run a feature through a spec on your own project.

What we'll cover

  1. What is Kiro & why
  2. Vibe / Chat mode
  3. Specs — spec-driven development
  4. Agent Steering
  5. Agent Hooks
  6. MCP — external tools & data

…then Kiro Powers, and our team adoption plan.

Eight modules. The first three are about how you drive Kiro day to day. Modules four to six are the files we commit into dot-kiro to make the agent behave consistently for everyone. Then Powers, which bundle those pieces, and finally the concrete plan for rolling this out on one pilot project.

1 · What is Kiro

One AI agent, exposed through IDE, CLI, Web, and Mobile — driven by a shared .kiro/ folder in your repo.

  • Core idea: spec-driven development — requirements & design as reviewable files, before code
  • Free-form "vibe" mode still available for exploration & debugging
  • Config travels with the repository — set up once, applies everywhere
The thing to hold onto: Kiro is not just an editor. It's one agent behind several front doors, and its configuration lives in your repo as dot-kiro. The headline feature is that planning artifacts — requirements and design — become real files you review, instead of disappearing into chat history.

1 · One agent, every surface

SurfaceFor
IDE (desktop)Main experience: editor, chat, specs, steering, hooks UI
CLISame agent from terminal / CI scripts
WebBrowser agent; long-running tasks
MobileCheck on tasks (no MCP)

Your .kiro/ config is shared across all of them.

Same agent, different entry points. You might start a task in the IDE, check it from your phone on the commute, and have CI run the CLI against the same steering rules. The consistency comes from dot-kiro being version-controlled alongside the code.

1 · The .kiro/ directory

.kiro/
├── steering/          # persistent project knowledge
│   ├── product.md  ·  tech.md  ·  structure.md
├── hooks/            # event-driven automation (JSON)
├── specs/            # one folder per feature / bugfix
│   └── <name>/ requirements.md · design.md · tasks.md
└── settings/
    └── mcp.json      # external tool connections

Commit it like any other source. Review changes like code.

This is the whole surface area. Steering is markdown context. Hooks are JSON automation. Specs are per-feature folders with three documents. And mcp.json wires in external tools. Everything in here is reviewed in pull requests because it changes how the agent behaves for the whole team.

2 · Vibe vs Spec

ModeOutputUse when
Vibe (default)Direct edits / answersQuestions, debugging, exploring
Specrequirements + design + tasksReviewable feature work
PlanPlan only, no changesWrite the approach down first
Bug FixAnalysis → fixReproducible defect
Quick SpecAuto-generated specSmall feature, trust the agent
Vibe is the default agent — free conversation with your codebase, no documents. Spec is the structured path. Plan, Bug Fix, and Quick Spec are points in between. The rule of thumb: if someone will review it or ask why later, use a spec. Otherwise vibe it.

2 · Autopilot vs Supervised

Supervised

  • Approve every change
  • Safe default while learning
  • Slower

Autopilot

  • Agent executes, you review the result
  • For narrow, proven task types

Stay Supervised until you've watched the agent do this kind of task right a few times — then graduate that one task type.

This is a separate switch from the mode. Start Supervised on everything. When you've seen the agent handle a specific kind of task cleanly several times — say, adding a test file — move just that task type to Autopilot. Don't flip everything at once.

2 · Context providers — #

ProviderAdds
#codebaseKiro finds relevant files
#file / #folderA path you name
#git diffUncommitted changes
#terminalRecent command output
#problemsDiagnostics for a file
#docs · #url · #mcpExternal docs, a page, an MCP resource

Combine them in one message. You can paste images too.

Kiro only knows what's in context. The hash menu is how you load it. Combine freely: fix the failing test in hash-problems using the pattern from hash-file colon this path. Answer quality tracks context quality almost exactly, so be deliberate about what you pull in.

3 · What a spec is

Three reviewable files in .kiro/specs/<name>/, each behind your approval:

FileContents
requirements.mdUser stories + acceptance criteria (EARS)
design.mdArchitecture, diagrams, error handling, test strategy
tasks.mdDiscrete tasks with live status
A spec replaces one long chat with three documents. You approve requirements before design gets written, and design before tasks get executed. Each gate is a checkpoint where fixing a misunderstanding is still cheap.

3 · Three phases, three gates

  1. Requirements — edit & approve the user stories
  2. Design — review the approach; cheapest place to catch a wrong turn
  3. Tasks — agent implements task by task, updating status

A misunderstanding fixed in requirements.md costs a sentence. Fixed after 12 files, it costs an afternoon.

The gates are the whole point. It's tempting to skim requirements and let it run. Don't. Two minutes tightening acceptance criteria saves you a rewrite. Design review is the second-cheapest place to redirect the work.

3 · EARS notation

WHEN  <trigger>              THE SYSTEM SHALL <response>
WHILE <state>                THE SYSTEM SHALL <response>
WHERE <feature included>     THE SYSTEM SHALL <response>
IF    <condition> THEN       THE SYSTEM SHALL <response>

// Example
WHEN a user submits checkout with an expired card
THE SYSTEM SHALL reject the payment and show "Your card has expired"

Each line becomes a test.

EARS is just a handful of sentence templates. The value is that every criterion is unambiguous and directly testable. When you review requirements, rewrite any vague line into one of these shapes.

3 · Tasks run in waves

  • Kiro builds a dependency graph from the task list
  • Wave 1 — no-dependency tasks, run concurrently
  • Wave 2+ — tasks whose deps are now met, concurrently
  • Waves are sequential; tasks inside a wave are parallel
  • Automatic — no configuration

Why a spec often finishes faster than the same tasks typed one-by-one.

You don't set this up. Kiro works out which tasks are independent and runs those together, then the next wave, and so on. It's a real speed advantage over issuing instructions serially in chat.

4 · Agent Steering

Markdown in .kiro/steering/ that gives Kiro persistent project knowledge.

Foundation fileCaptures
product.mdPurpose, users, goals — the "why"
tech.mdStack, tools, constraints
structure.mdFile layout, naming, conventions

Generated by "Generate Steering Docs" · loaded on every interaction.

Steering is how you stop re-explaining your project every conversation. Generate the three foundation files, then hand-edit them until they're actually true — the generator gives you a draft, not gospel. These three load into every single interaction.

4 · Inclusion modes

---
inclusion: always            # default — every interaction
---
---
inclusion: fileMatch
fileMatchPattern: ["**/*.tsx", "src/components/**/*"]
---
---
inclusion: manual            # load with #file-name in chat
---
---
inclusion: auto
name: api-design
description: REST API patterns. Use when creating endpoints.
---
Front-matter at the top of a steering file controls when it loads. Always for universal rules. fileMatch to scope guidance to an area of the codebase. Manual when you want to pull it in by name. Auto when a description should trigger it. Keep always-files small — they cost tokens every turn.

4 · References, AGENTS.md, practice

  • Link live files: #[[file:api/openapi.yaml]]
  • AGENTS.md (repo root or ~/.kiro/steering/) — always included, no modes
  • Custom agents need "resources": ["file://.kiro/steering/**/*.md"]
  • One domain per file · explain the why · no secrets · review like code
Point steering at real files so it can't drift from source. Kiro also reads the cross-tool AGENTS.md standard. And remember custom agents don't inherit steering automatically — you add it in their resources list. Treat every steering change as a pull request.

5 · Agent Hooks

JSON in .kiro/hooks/ — run a command or agent prompt automatically on an event.

CategoryTriggers
File (IDE)PostFileCreate/Save/Delete
ExecutionPreToolUse/PostToolUse, PromptSubmit (can block)
LifecycleSessionStart, AgentSpawn, AgentStop
Task (IDE)PreTaskExecution/PostTaskExecution
Hooks fire on events during a session and activate automatically at session start. The blocking ones — PreToolUse and PromptSubmit — are powerful but introduce them last, once the team trusts the non-blocking ones.

5 · Hook file format

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}

action.type: "command" (shell) or "agent" (inject a prompt). File triggers fire on agent edits only.

The matcher is a regex that narrows which events fire the hook. The action is either a shell command or a prompt handed to the agent. The gotcha worth repeating: file triggers respond to the agent's edits, not to you saving a file yourself in the editor.

5 · What hooks are for

  • Run linters / formatters / type checks after agent edits
  • Auto-create tests, docs, or translations for new source files
  • Block a tool with PreToolUse until a precondition holds
  • Quality check before the agent finalises

Create in IDE: + in Agent Hooks → "Ask Kiro to create a hook" → describe it.

Start with two low-risk hooks: format on save, and scaffold a test when a new source file appears. You describe what you want in plain language and Kiro writes the JSON. Then review that JSON in a pull request like any code.

6 · MCP — Model Context Protocol

Lets Kiro use tools, prompts, and resources from external servers.

LevelScope
Workspace mcp.jsonThis repo — commit to share
User mcp.jsonAll your projects
Agent mcpServersThat agent only

Local (stdio) & remote (HTTP/SSE) — everywhere except Mobile.

MCP is the plug for anything the model doesn't know natively — internal wikis, ticketing, cloud APIs, docs search. Config lives at three levels. The one we care about for the team is a committed workspace mcp.json so everyone runs the same vetted servers.

6 · mcp.json example

{
  "mcpServers": {
    "aws-docs": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@latest"],
      "disabled": false,
      "autoApprove": ["search_documentation"]
    }
  }
}

disabled toggles without deleting · autoApprove = read-only tools only · secrets via env, never committed.

The AWS Documentation server is a great first one — the agent searches real AWS docs instead of guessing from training data. Keep autoApprove to read-only tools so anything that changes state still prompts you.

6 · Treat servers as supply chain

Only install MCP servers from sources you trust — a server runs code on your machine and sees the context the agent sends it.

  • Vet the package · pin versions · secrets via env
  • Kiro confirms install links, showing env var names (values hidden)
  • Tool names: ^[a-zA-Z][a-zA-Z0-9_]*$, < 64 chars
This is the one security slide for MCP. An MCP server is executable code with visibility into your context. We vet every server before it goes in the shared mcp.json, pin the version, and keep credentials in environment variables that are never committed.

7 · Kiro Powers

Installable packages that make the agent good at a specific tool or framework.

PartProvides
plugin.jsonManifest + activation keywords
skills/Task-specific instructions
mcp.jsonOptional tool access
dev.kiro/Steering & Kiro extensions

Built on the open Agent Plugins spec (Amazon, Cursor, Microsoft, OpenAI, Vercel).

A Power is steering plus skills plus optional MCP, packaged so you install it in one click. Because it's built on the vendor-neutral Agent Plugins standard, the same Power works beyond Kiro. Think of it as expertise for a framework, shipped by the people who built that framework.

7 · Two problems, one mechanism

Problem

  • Expertise scattered across docs
  • Context overload from too many MCP servers

Intelligent loading

  • Kiro matches your task to installed Powers
  • Loads only the relevant ones — not 50k+ tokens upfront

Say "payment" → Stripe activates. Switch to DB work → Supabase loads instead.

Connecting more servers doesn't automatically help — it can bury the agent in context. Powers fix that by loading on demand. You never toggle them; the task description decides which Power's knowledge comes into context.

7 · Install & partners

  • One-click from IDE / CLI or the registry at kiro.dev/powers
  • Import a community Power by GitHub URL
  • Cloud-synced Powers in Settings → Powers

Launch partners: Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora

Each partner Power is built by the company behind the tool — Figma's own design-to-code guidance, Supabase's own Row Level Security patterns. You can also package your team's conventions plus internal MCP as a private Power once your steering has stabilised.

7 · Powers vs Skills vs Steering

MechanismIs
SteeringKiro-specific behaviour shaping — markdown you write
SkillsStandalone instruction packages
PowersInstallable, context-aware — tools + knowledge + guidance
Quick disambiguation. Steering is yours, hand-written, Kiro-only. A Skill is a portable instruction bundle. A Power wraps skills and MCP and steering together into something installable that loads intelligently. Powers are the distribution format.

8 · Adoption — week 1

  • Small team (2–5, GitHub) → everyone pilots at once, on one active repo
  • Everyone: install IDE, sign in, import VS Code settings
  • "Generate Steering Docs" → hand-edit in a PR until true → merge
  • Polyglot steering: tiny always set + per-language fileMatch files (code-style-ts.md, -python.md, infra-aws.md)
We're a small team, so there's no subset-first phase — everyone starts on one real repo. The first deliverable is foundation steering that's actually accurate. Because we ship in several languages, split the style rules into fileMatch files so each only loads when you touch that language.

8 · Ticket-driven specs, cost discipline

If it has a ticket, it gets a spec folder named after the ticket. No ticket and trivial? Vibe it.

  • Feature ticket → Feature Spec · bug ticket → Bugfix Spec
  • Commit the spec folder in the same PR as the code
  • Cost: short always steering, lean on compaction, Supervised by default
Every ticket gets its own spec folder, named after the ticket id, committed with the code so the reasoning travels with the change. On cost: a wrong Autopilot run burns the whole run plus your review time, so we stay Supervised until a task type is boringly reliable.

8 · Guardrails — sensitive code

  • .kiroignore day one: secrets, .env*, customer data, compliance-scoped dirs
  • Permissions default-deny outside the working repo
  • MCP: reviewed + pinned only; autoApprove read-only tools
  • Keep sensitive work in the IDE — Web / Mobile send context off your machine
  • Start with AWS Docs MCP + AWS Aurora Power
Because some of our code is sensitive, kiroignore and Permissions go in from day one, and we never auto-approve a tool that writes or calls out. The Web and Mobile surfaces send context off the machine, so sensitive work stays in the IDE. AWS Docs MCP and the Aurora Power are the shared starting point.
