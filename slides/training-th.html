0 · AI-DLC — แนวคิดเบื้องหลัง Kiro

AI-Driven Development Lifecycle: methodology (ไม่ใช่ product) ที่สร้าง lifecycle ใหม่รอบ ๆ AI ทำงาน มนุษย์ตัดสินใจ ทีมรีวิว

  • SDLC เขียนมือ → AI-assisted autocomplete → "vibe coding" (Karpathy, ก.พ. 2025) → lifecycle แบบ AI-native
  • ปฏิเสธทั้งสองสุดขั้ว: AI-assisted ขี้อายเกินไป; AI-autonomous ตัดวิจารณญาณมนุษย์
  • เผยแพร่โดย AWS (Raja SP), AWS DevOps Blog, 31 ก.ค. 2025
ก่อนเครื่องมือ ต้องเข้าใจแนวคิด AI-DLC คือคำตอบของ AWS ต่อช่องว่างจริง การเอา AI มาแปะเป็นผู้ช่วยยังคงกระบวนการช้าแบบเดิม การปล่อยให้รันอิสระเต็มที่ทิ้งวิจารณญาณมนุษย์ AI-DLC ออกแบบ lifecycle เองใหม่ให้ AI ทำงานและมนุษย์อยู่บนทุกการตัดสินใจ Kiro คือวิธี ลงมือทำจริง

1 · Kiro คืออะไร

AI agent ตัวเดียว เปิดผ่าน IDE, CLI, Web และ Mobile — ขับเคลื่อนด้วยโฟลเดอร์ .kiro/ ร่วมกันใน repo

  • แนวคิดหลัก: spec-driven development — requirements & design เป็นไฟล์ที่รีวิวได้ ก่อนเขียนโค้ด
  • ยังมีโหมด "vibe" แบบอิสระสำหรับสำรวจไอเดียและ debug
  • config ติดไปกับ repository — ตั้งครั้งเดียว มีผลทุกที่
สิ่งที่ต้องจำ: Kiro ไม่ใช่แค่ editor แต่เป็น agent ตัวเดียวหลังหลายประตู และ config อยู่ใน repo ในชื่อ dot-kiro ฟีเจอร์เด่นคือเอกสารการวางแผน — requirements และ design — กลายเป็นไฟล์จริงที่รีวิวได้ แทนที่จะหายไปในประวัติแชต

1 · โฟลเดอร์ .kiro/

.kiro/
├── steering/          # ความรู้ถาวรของโปรเจกต์
│   ├── product.md  ·  tech.md  ·  structure.md
├── hooks/            # automation ตาม event (JSON)
├── specs/            # หนึ่งโฟลเดอร์ต่อ feature / bugfix
│   └── <name>/ requirements.md · design.md · tasks.md
└── settings/
    └── mcp.json      # การเชื่อมต่อเครื่องมือภายนอก

commit เหมือน source อื่น รีวิวการแก้เหมือนโค้ด

นี่คือพื้นที่ทั้งหมด steering เป็น context แบบ markdown hooks เป็น automation แบบ JSON specs เป็นโฟลเดอร์ต่อฟีเจอร์ที่มีเอกสารสามไฟล์ และ mcp.json ต่อเครื่องมือภายนอก ทุกอย่างในนี้รีวิวใน pull request เพราะมันเปลี่ยนพฤติกรรม agent ของทั้งทีม

2 · Vibe vs Spec

โหมดผลลัพธ์ใช้เมื่อ
Vibe (ค่าเริ่มต้น)แก้ไข / ตอบตรง ๆคำถาม, debug, สำรวจ
Specrequirements + design + tasksงานฟีเจอร์ที่ต้องรีวิว
Planแผนอย่างเดียว ไม่แก้เขียนแนวทางไว้ก่อน
Bug Fixวิเคราะห์ → แก้บั๊กที่ทำซ้ำได้
Quick Specสร้าง spec อัตโนมัติฟีเจอร์เล็ก ไว้ใจ agent
Vibe คือ agent เริ่มต้น — คุยกับ codebase อิสระ ไม่มีเอกสาร Spec คือเส้นทางมีโครงสร้าง Plan, Bug Fix, Quick Spec อยู่ตรงกลาง หลักคิด: ถ้ามีคนจะรีวิวหรือถามทีหลัง ใช้ spec นอกนั้น vibe ได้

2 · Autopilot vs Supervised

Supervised

  • อนุมัติทุกการเปลี่ยน
  • ค่าเริ่มต้นที่ปลอดภัยระหว่างเรียนรู้
  • ช้ากว่า

Autopilot

  • agent ลงมือ คุณรีวิวผล
  • สำหรับงานแคบ ๆ ที่พิสูจน์แล้ว

อยู่ Supervised จนกว่าจะเห็น agent ทำ งานประเภทนี้ ถูกต้องหลายครั้ง — แล้วค่อยเลื่อนงานประเภทนั้น

นี่เป็นสวิตช์แยกจากโหมด เริ่มที่ Supervised กับทุกอย่าง เมื่อเห็น agent จัดการงาน ประเภทหนึ่งได้เรียบร้อยหลายครั้ง — เช่นเพิ่มไฟล์ test — ค่อยย้ายเฉพาะประเภทนั้นไป Autopilot อย่าเปลี่ยนทุกอย่างพร้อมกัน

3 · spec คืออะไร

สามไฟล์ที่รีวิวได้ใน .kiro/specs/<name>/ แต่ละอันมีด่านอนุมัติของคุณ:

ไฟล์เนื้อหา
requirements.mduser story + acceptance criteria (EARS)
design.mdสถาปัตยกรรม, diagram, การจัดการ error, กลยุทธ์ test
tasks.mdtask ย่อยพร้อมสถานะ real-time
spec แทนแชตยาว ๆ ด้วยเอกสารสามอัน คุณอนุมัติ requirements ก่อน design ถูกเขียน และ design ก่อน tasks ถูกรัน แต่ละด่านคือ checkpoint ที่การแก้ความเข้าใจผิดยังราคาถูก

3 · สามเฟส สามด่าน

  1. Requirements — แก้และอนุมัติ user story
  2. Design — รีวิวแนวทาง; จุดถูกที่สุดในการจับทางที่ผิด
  3. Tasks — agent ทำทีละ task พร้อมอัปเดตสถานะ

ความเข้าใจผิดที่แก้ใน requirements.md ราคาหนึ่งประโยค ถ้าแก้หลัง 12 ไฟล์ ราคาทั้งบ่าย

ด่านคือหัวใจ มันเย้ายวนให้อ่าน requirements ผ่าน ๆ แล้วปล่อยรัน อย่าทำ สองนาทีที่ กระชับ acceptance criteria ประหยัดการเขียนใหม่ การรีวิว design คือจุดที่ถูกรองลงมา ในการเปลี่ยนทิศงาน

3 · EARS notation

WHEN  <trigger>              THE SYSTEM SHALL <response>
WHILE <state>                THE SYSTEM SHALL <response>
WHERE <feature included>     THE SYSTEM SHALL <response>
IF    <condition> THEN       THE SYSTEM SHALL <response>

// ตัวอย่าง
WHEN a user submits checkout with an expired card
THE SYSTEM SHALL reject the payment and show "Your card has expired"

แต่ละบรรทัดกลายเป็น test

EARS เป็นแค่เทมเพลตประโยคไม่กี่แบบ คุณค่าคือทุกเกณฑ์ไม่กำกวมและทดสอบได้ตรง ๆ ตอน รีวิว requirements ให้เขียนบรรทัดที่คลุมเครือใหม่ให้เป็นหนึ่งในรูปแบบเหล่านี้

3 · task รันเป็น waves

  • Kiro สร้าง dependency graph จากรายการ task
  • Wave 1 — task ไม่มี dependency รันพร้อมกัน
  • Wave 2+ — task ที่ dependency ครบแล้ว รันพร้อมกัน
  • waves เรียงลำดับ; task ใน wave เดียวกันขนานกัน
  • อัตโนมัติ — ไม่ต้องตั้งค่า

เหตุผลที่ spec มักเสร็จเร็วกว่าพิมพ์ task ทีละอัน

คุณไม่ต้องตั้งค่า Kiro หาว่า task ไหนเป็นอิสระต่อกันแล้วรันพร้อมกัน จากนั้น wave ถัดไป เรื่อย ๆ เป็นข้อได้เปรียบด้านความเร็วจริง ๆ เทียบกับสั่งทีละคำสั่งในแชต

4 · Agent Steering

markdown ใน .kiro/steering/ ที่ให้ความรู้ถาวรของโปรเจกต์แก่ Kiro

ไฟล์พื้นฐานบันทึก
product.mdจุดประสงค์, ผู้ใช้, เป้าหมาย — "ทำไม"
tech.mdstack, เครื่องมือ, ข้อจำกัด
structure.mdการจัดวางไฟล์, การตั้งชื่อ, convention

สร้างโดย "Generate Steering Docs" · โหลดทุกบทสนทนา

steering คือวิธีเลิกอธิบายโปรเจกต์ซ้ำทุกบทสนทนา สร้างไฟล์พื้นฐานสามไฟล์ แล้วแก้ด้วยมือ จนตรงความจริง — ตัว generate ให้แค่ร่าง ไม่ใช่คัมภีร์ ทั้งสามไฟล์นี้โหลดเข้าทุก interaction

4 · Inclusion modes

---
inclusion: always            # ค่าเริ่มต้น — ทุก interaction
---
---
inclusion: fileMatch
fileMatchPattern: ["**/*.tsx", "src/components/**/*"]
---
---

---
---
inclusion: auto
name: api-design
description: REST API patterns. Use when creating endpoints.
---
front-matter ที่หัวไฟล์ steering คุมว่าจะโหลดเมื่อไร always สำหรับกฎสากล fileMatch เพื่อจำกัดคำแนะนำให้กับพื้นที่หนึ่งของ codebase manual เมื่ออยากเรียกด้วยชื่อ auto เมื่อ description ควรจุดให้โหลด ทำไฟล์ always ให้เล็ก เพราะกิน token ทุกเทิร์น

4 · การอ้างอิง, AGENTS.md, แนวปฏิบัติ

  • ผูกไฟล์จริง: #[[file:api/openapi.yaml]]
  • AGENTS.md (root ของ repo หรือ ~/.kiro/steering/) — รวมเสมอ ไม่มีโหมด
  • custom agents ต้องมี "resources": ["file://.kiro/steering/**/*.md"]

ชี้ steering ไปที่ไฟล์จริงเพื่อไม่ให้หลุดจาก source Kiro อ่านมาตรฐานข้ามเครื่องมือ AGENTS.md ด้วย และจำไว้ว่า custom agents ไม่สืบทอด steering อัตโนมัติ — ต้องเพิ่มใน รายการ resources มองการแก้ steering ทุกครั้งเป็น pull request

5 · Agent Hooks

JSON ใน .kiro/hooks/ — รันคำสั่งหรือ prompt ให้ agent อัตโนมัติเมื่อมี event

กลุ่มTriggers
ไฟล์ (IDE)PostFileCreate/Save/Delete
การรันPreToolUse/PostToolUse, PromptSubmit (บล็อกได้)
LifecycleSessionStart, AgentSpawn, AgentStop
Task (IDE)PreTaskExecution/PostTaskExecution
hook ทำงานตาม event ระหว่าง session และเปิดใช้อัตโนมัติเมื่อ session เริ่ม ตัวที่ บล็อกได้ — PreToolUse และ PromptSubmit — ทรงพลังแต่ให้นำมาใช้ทีหลังสุด เมื่อทีมไว้ใจ ตัวที่ไม่บล็อกแล้ว

5 · รูปแบบไฟล์ hook

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}

action.type: "command" (shell) หรือ "agent" (แทรก prompt) · trigger ไฟล์ทำงานกับการแก้ของ agent เท่านั้น

matcher เป็น regex ที่จำกัดว่า event ไหนจุด hook action เป็นคำสั่ง shell หรือ prompt ที่ส่งให้ agent จุดพลาดที่ต้องย้ำ: trigger ไฟล์ตอบสนองต่อการแก้ของ agent ไม่ใช่ตอน คุณเซฟไฟล์เองใน editor

5 · hook ไว้ทำอะไร

  • รัน linter / formatter / type check หลัง agent แก้
  • สร้าง test, docs หรือคำแปลอัตโนมัติสำหรับไฟล์ source ใหม่
  • บล็อก tool ด้วย PreToolUse จนกว่าเงื่อนไขจะครบ
  • ตรวจคุณภาพก่อน agent ปิดงาน

สร้างใน IDE: + ใน Agent Hooks → "Ask Kiro to create a hook" → อธิบาย

เริ่มด้วย hook เสี่ยงต่ำสองอัน: format ตอนเซฟ และสร้างโครง test เมื่อมีไฟล์ source ใหม่ คุณอธิบายสิ่งที่ต้องการเป็นภาษาคน แล้ว Kiro เขียน JSON ให้ จากนั้นรีวิว JSON นั้นใน pull request เหมือนโค้ด

6 · MCP — Model Context Protocol

ให้ Kiro ใช้ tools, prompts และ resources จาก server ภายนอก

ระดับขอบเขต
Workspace mcp.jsonrepo นี้ — commit เพื่อแชร์
User mcp.jsonทุกโปรเจกต์ของคุณ
Agent mcpServersเฉพาะ agent นั้น

Local (stdio) & remote (HTTP/SSE) — ทุกที่ยกเว้น Mobile

MCP คือปลั๊กสำหรับอะไรก็ตามที่โมเดลไม่รู้เอง — wiki ภายใน, ระบบ ticket, cloud API, การค้นเอกสาร config อยู่สามระดับ ตัวที่ทีมสนใจคือ workspace mcp.json ที่ commit ไว้ เพื่อให้ทุกคนรัน server ที่ตรวจแล้วชุดเดียวกัน

6 · ตัวอย่าง mcp.json

{
  "mcpServers": {
    "aws-docs": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@latest"],
      "disabled": false,
      "autoApprove": ["search_documentation"]
    }
  }
}

disabled ปิดโดยไม่ลบ · autoApprove = tool อ่านอย่างเดียวเท่านั้น · secret ผ่าน env ห้าม commit

AWS Documentation server เป็นตัวแรกที่ดี — agent ค้นเอกสาร AWS จริงแทนการเดาจากข้อมูล training ให้ autoApprove เฉพาะ tool อ่านอย่างเดียว เพื่อให้อะไรที่เปลี่ยน state ยังถาม คุณอยู่

6 · มอง server เป็น supply chain

ติดตั้ง MCP server จากแหล่งที่ไว้ใจได้เท่านั้น — server รันโค้ดบนเครื่องคุณและเห็น context ที่ agent ส่งให้

  • ตรวจแพ็กเกจ · pin เวอร์ชัน · secret ผ่าน env
  • Kiro ยืนยัน install link โดยแสดง ชื่อ env var (ซ่อนค่า)
  • ชื่อ tool: ^[a-zA-Z][a-zA-Z0-9_]*$, < 64 อักขระ
นี่คือสไลด์ความปลอดภัยหนึ่งเดียวของ MCP MCP server คือโค้ดที่รันได้และมองเห็น context ของคุณ เราตรวจทุก server ก่อนใส่ใน mcp.json ที่ใช้ร่วมกัน pin เวอร์ชัน และเก็บ credential ใน environment variable ที่ไม่เคย commit

Power คือ steering บวก skills บวก MCP ทางเลือก แพ็กให้ติดตั้งคลิกเดียว เพราะสร้างบน มาตรฐาน Agent Plugins ที่ไม่ผูกเจ้า Power เดียวกันใช้นอก Kiro ได้ มองเป็นความเชี่ยวชาญ ของ framework ที่ส่งมาโดยคนที่สร้าง framework นั้น

7 · สองปัญหา หนึ่งกลไก

ปัญหา

  • ความเชี่ยวชาญกระจัดกระจายในเอกสาร
  • context ท่วมท้นจาก MCP server มากไป

Intelligent loading

  • Kiro จับคู่งานของคุณกับ Power ที่ติดตั้ง
  • โหลดเฉพาะตัวที่เกี่ยว — ไม่ใช่ 50k+ tokens ตั้งแต่ต้น

พูดว่า "payment" → Stripe เปิด เปลี่ยนไปทำงาน DB → Supabase โหลดแทน

ต่อ server มากขึ้นไม่ได้ช่วยอัตโนมัติ — มันฝัง agent ไว้ใน context Powers แก้ด้วยการ โหลด on demand คุณไม่ต้องสลับ; คำอธิบายงานเป็นตัวตัดสินว่าความรู้ของ Power ตัวไหนเข้ามา ใน context

7 · การติดตั้ง & partner

  • คลิกเดียวจาก IDE / CLI หรือ registry ที่ kiro.dev/powers
  • นำเข้า Power ของชุมชนด้วย URL GitHub
  • Power ที่ sync cloud อยู่ใน Settings → Powers

Launch partner: Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora

Power ของแต่ละ partner สร้างโดยบริษัทเจ้าของเครื่องมือ — คำแนะนำ design-to-code ของ Figma เอง, pattern Row Level Security ของ Supabase เอง คุณแพ็ก convention ของทีม บวก MCP ภายในเป็น Power ส่วนตัวได้เมื่อ steering นิ่งแล้ว

7 · Powers vs Skills vs Steering

กลไกคือ
Steeringกำหนดพฤติกรรมเฉพาะ Kiro — markdown ที่คุณเขียน
Skillsแพ็กเกจคำสั่งแบบ standalone
Powersติดตั้งได้ รู้บริบท — tool + ความรู้ + คำแนะนำ
แยกให้ชัดเร็ว ๆ steering เป็นของคุณ เขียนเอง เฉพาะ Kiro Skill คือชุดคำสั่งพกพาได้ Power ห่อ skills กับ MCP กับ steering เข้าด้วยกันเป็นสิ่งที่ติดตั้งได้และโหลดแบบ ฉลาด Powers คือรูปแบบการกระจาย

8 · นำไปใช้ — สัปดาห์ที่ 1

  • ทีมเล็ก (2–5 คน, GitHub) → ทุกคน pilot พร้อมกัน บน repo ที่ใช้งานจริงหนึ่งอัน
  • ทุกคน: ติดตั้ง IDE, ลงชื่อเข้าใช้, นำเข้าการตั้งค่า VS Code
  • "Generate Steering Docs" → แก้ ใน PR จนตรงความจริง → merge
  • steering หลายภาษา: ชุด always เล็ก + ไฟล์ fileMatch แยกภาษา (code-style-ts.md, -python.md, infra-aws.md)
เราเป็นทีมเล็ก จึงไม่มีเฟสเริ่มบางคนก่อน — ทุกคนเริ่มบน repo จริงอันเดียว ผลงานชิ้นแรก คือ steering พื้นฐานที่แม่นยำจริง เพราะเราส่งงานหลายภาษา แยกกฎ style เป็นไฟล์ fileMatch ให้แต่ละไฟล์โหลดเฉพาะตอนแตะภาษานั้น

8 · spec ตาม ticket, วินัยต้นทุน

ถ้ามี ticket ก็มีโฟลเดอร์ spec ตั้งชื่อตาม ticket ไม่มี ticket และงานเล็กจิ๋ว? vibe ได้

  • ticket ฟีเจอร์ → Feature Spec · ticket บั๊ก → Bugfix Spec
  • commit โฟลเดอร์ spec ใน PR เดียวกับโค้ด
  • ต้นทุน: steering always สั้น, พึ่ง compaction, Supervised เป็นค่าเริ่มต้น
ทุก ticket มีโฟลเดอร์ spec ของตัวเอง ตั้งชื่อตาม id ของ ticket commit ไปกับโค้ดเพื่อให้ เหตุผลเดินทางไปกับการเปลี่ยน เรื่องต้นทุน: การรัน Autopilot ที่พลาดเผาทั้ง run บวกเวลา รีวิว เราจึงอยู่ Supervised จนกว่างานประเภทนั้นจะน่าเบื่อเพราะเชื่อถือได้

8 · guardrails — โค้ดอ่อนไหว

  • .kiroignore วันแรก: secret, .env*, ข้อมูลลูกค้า, โฟลเดอร์ในขอบเขต compliance
  • Permissions default-deny นอก repo ที่ทำงานอยู่
  • MCP: รีวิว + pin แล้วเท่านั้น; autoApprove tool อ่านอย่างเดียว
  • เก็บงานอ่อนไหวไว้ใน IDE — Web / Mobile ส่ง context ออกนอกเครื่อง
  • เริ่มด้วย AWS Docs MCP + AWS Aurora Power
เพราะโค้ดบางส่วนของเราอ่อนไหว kiroignore และ Permissions ใส่ตั้งแต่วันแรก และเราไม่ auto-approve tool ที่เขียนหรือเรียกออกนอกเด็ดขาด ช่องทาง Web และ Mobile ส่ง context ออกนอกเครื่อง งานอ่อนไหวจึงอยู่ใน IDE AWS Docs MCP กับ Aurora Power คือจุดเริ่มร่วมกัน
