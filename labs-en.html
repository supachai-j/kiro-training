Hands-on · one per module + a capstone

Lab Guidelines

Nine labs, one per module, plus a capstone that runs the whole loop end to end. Do the module labs after reading the matching module — each turns that module's idea into something on your machine, and they build on each other: Lab 1 finds problems in your steering files, Lab 4 fixes them, and so on. Lab 9 ties it together: one feature from intent to reviewed code through every AI-DLC gate.

What you need for most labs: the Kiro IDE installed and signed in, and one real project you know well (not an empty folder). Lab 0 needs no tooling; Lab 8 is best done with your team in the room; Lab 9 uses Claude Code and an empty directory — no Kiro IDE required.

Tick a lab off when you finish — progress is saved in this browser and shows up on the home page and next to each module in the course.

Labs — 0 / 10 done
Module 0 · Lab 0

Map a real PR onto AI-DLC

⏱ 20–30 min 🔧 No tooling — a recent PR you can read + a scratch file 🎯 Feel where the Inception / Construction line falls, and find one decision that leaked into code review

Steps

  1. Open the last non-trivial pull request you reviewed or authored. Read the description and skim the diff.
  2. In a scratch file, make three headings: Inception (deciding what to build and the rules for it), Construction (how it's built), Operations (deploy / monitor).
  3. List every distinct decision or change from the PR under the phase where it should have been settled. E.g. "export is admin-only" → Inception; "stream the CSV" → Construction; "add an export metric" → Operations.
  4. Circle anything that was actually decided during review or in a follow-up fix commit. For each, write the single sentence that would have settled it in Inception.
  5. Count: of the review comments, how many were really "missing Inception" rather than "missing code quality"?

Expected result

A three-column list, at least one circled decision, and its one-sentence Inception form. That sentence is the shape of an EARS acceptance criterion — you'll write real ones in Lab 3.

If you get stuck

  • "Everything looks like Construction." Look for choices someone could have disagreed with: who's allowed, when it triggers, which format, what counts as done. Those are Inception.
  • "No decisions leaked." Re-read the PR comments and any follow-up commits with messages like "fix", "actually", "per review". That's where they hide.
Module 1 · Lab 1

First contact — install and read the steering

⏱ 20 min 🔧 Kiro IDE · a small real repo · your VS Code settings 🎯 Get Kiro installed and see how it reads your project

Steps

  1. Install the Kiro IDE and sign in with the account the org uses. When prompted, import your VS Code settings.
  2. Open a small real project you know well — not a fresh empty folder.
  3. Run Generate Steering Docs (Agent Steering panel, or the command palette). Open the new .kiro/steering/product.md, tech.md, and structure.md.
  4. Read all three. In each, mark one statement that is wrong or vague about your project.
  5. In the chat panel (vibe mode) ask: Summarise what this project does and its main entry points. Compare the answer to reality.

Expected result

Three files on disk and a written list of at least three things to correct in them. Keep that list — you fix it in Lab 4.

If you get stuck

  • No "Generate Steering Docs". Look in the Agent Steering section of the side panel, or search the command palette for "steering".
  • The generated files feel generic. That's expected — the generator gives a draft. Making it true is exactly Lab 4.
Module 2 · Lab 2

Context is everything

⏱ 15–20 min 🔧 Kiro IDE · a "wiring-up" file in your project · a runnable test suite 🎯 See, measurably, how answer quality tracks the context you provide

Steps

  1. Pick a real file that wires things together — an app entry point, a router, a DI container.
  2. Ask in vibe mode with no context provider: What are the top 3 risks in this codebase's startup path?
  3. Ask again, same question, adding: #file:<that file> #folder:<its directory> #git diff
  4. Run your tests so there's terminal output, then ask a third time adding #problems and #terminal.
  5. Compare how specific and correct each answer is. Save the best prompt as a template.

Expected result

You can point to a concrete claim in answer 3 that answer 1 got wrong or missed entirely.

If you get stuck

  • The three answers look the same. Your question is probably too generic — ask something the file you referenced actually determines.
  • #terminal is empty. Run the test suite (or any command) first so there's history to pull in.
Module 3 · Lab 3

Run a spec to the first gate

⏱ 25–35 min 🔧 Kiro IDE · a genuinely small feature you need 🎯 Experience the requirements gate and write real EARS criteria

Steps

  1. Pick a small feature you actually need — a filter, an export, a field on a form.
  2. Start a Feature Spec. Give a one or two sentence description, no more.
  3. When Kiro produces requirements.md, stop. Don't approve yet.
  4. Rewrite at least two acceptance criteria into strict EARS form (WHEN … THE SYSTEM SHALL …). Add one IF … THEN … for an error case the draft missed.
  5. Approve, and let Kiro produce design.md. Read it. Note one decision in the design you would not have thought to make explicit yourself.

Expected result

.kiro/specs/<your-feature>/ contains a requirements.md you edited and a design.md you have read. Stop there — no need to implement.

If you get stuck

  • The spec won't start / asks endless questions. Check you chose "Feature", not "Bug". If it keeps asking, your description covered too much — pick a smaller feature.
  • The requirements are huge. Same cause — scope down. One coherent feature per spec.
Module 4 · Lab 4

Teach Kiro one real rule

⏱ 25 min 🔧 Kiro IDE · the three foundation files from Lab 1 🎯 Prove steering changes behaviour, and fix the foundation files

Steps

  1. Correct the wrong / vague statements you found in product.md, tech.md, and structure.md in Lab 1.
  2. Create .kiro/steering/code-style.md with inclusion: always and 5 real rules your team argues about in review. For at least two, add a short before / after snippet and one line of rationale.
  3. In a fresh chat, ask: Write a function that fetches a user by id and returns a typed result.
  4. Check the output against all five rules. If it breaks one, tighten that rule's wording and try again.
  5. Change one rule to its opposite, re-ask, confirm the output follows the new rule — then revert.

Expected result

The same prompt produces different, rule-following code before and after your edit — that is steering working. Commit the corrected foundation files and code-style.md on a branch.

If you get stuck

  • The agent keeps ignoring a rule. Make it concrete — one sentence of rule, one before/after snippet, one line of "why".
  • A rule fights your linter's autofix. Note it and reconcile — steering and lint should say the same thing, or the agent's output will bounce.
Module 5 · Lab 5

Ship a format-on-save hook

⏱ 15–20 min 🔧 Kiro IDE · a formatter on PATH (prettier, black, gofmt…) 🎯 Watch a hook fire on an agent edit — and stay silent on your own save

Steps

  1. In the Agent Hooks panel, click + → "Ask Kiro to create a hook" and describe: run my formatter on TypeScript and JS files after the agent edits them.
  2. Check the generated JSON in .kiro/hooks/: trigger is PostFileSave, the matcher only matches your source extensions, the action is a command.
  3. Ask the agent: Add a small utility function to <some .ts file>, deliberately badly formatted.
  4. Confirm the saved file comes back formatted, with no action from you.
  5. Now hand-edit the same file with messy formatting and save it yourself. Confirm the hook does not run.

Expected result

The hook runs on step 3 (agent edit) and stays silent on step 5 (your save). Commit the hook JSON on a branch.

If you get stuck

  • The hook didn't run. Check the matcher regex actually matches your file path, and read the Output tab for errors.
  • "formatter not found". Use npx <tool> or an absolute path in the command.
Module 6 · Lab 6

Give the agent live AWS docs

⏱ 15 min 🔧 Kiro IDE · uvx installed · network access 🎯 See the agent call an MCP tool instead of guessing from training data

Steps

  1. Open the workspace MCP config: command palette → "Kiro: Open workspace MCP config (JSON)".
  2. Add an aws-docs server: 
    "aws-docs": {
  "command": "uvx",
  "args": ["awslabs.aws-documentation-mcp-server@latest"],
  "disabled": false,
  "autoApprove": ["search_documentation", "read_documentation"]
}
  3. Check the MCP Servers tab shows it connected. If not, read the Output tab.
  4. Ask a question that needs current AWS detail, e.g. What are the current default quotas for Amazon SQS FIFO queues, with a source link?
  5. Watch it call search_documentation / read_documentation. Then set "disabled": true, ask the same thing, and compare.

Expected result

One answer backed by an MCP tool call with a doc link, and a visible difference in confidence when the server is off.

If you get stuck

  • Server won't connect. Confirm uvx is installed and on PATH; the Output tab shows the launch command and error.
  • The agent doesn't call the tool. Make the question clearly need current docs — "current default quota", "latest supported version", "as of today".
Module 7 · Lab 7

Watch a Power activate

⏱ 15–20 min 🔧 Kiro IDE · one Power relevant to your stack 🎯 Confirm intelligent loading — the right Power turns on by itself

Steps

  1. From kiro.dev/powers or the IDE, install one Power that matches your stack (Supabase, AWS Aurora, Postman, Netlify…).
  2. Start a task unrelated to it (e.g. "rename this variable everywhere"). Check the Powers indicator — the Power should be idle.
  3. Start a task squarely in its domain. For Supabase: add a row-level-security policy so users only read their own orders. Watch the indicator show the Power active.
  4. Inspect the output — does it reflect the Power's guidance (a real RLS policy, generated types) rather than generic advice?
  5. Optional: sketch a plugin.json keyword list for one thing your team re-explains constantly (a service scaffold, your logging conventions).

Expected result

The Powers indicator changes between the unrelated task and the in-domain task, and the in-domain output clearly used the Power.

If you get stuck

  • The indicator never shows the Power. Your task wording may not match its keywords — name the tool or domain explicitly.
  • The output still looks generic. Try a task only that Power would know how to do well, not one any agent could answer.
Module 8 · Lab 8

Draft your team's pilot

⏱ 30–40 min — ideally with the team 🔧 Knowledge of your repos + who's available 🎯 Leave with a concrete, assignable plan — not a vague intention

Steps

  1. Name the pilot repo — one, active, with real conventions worth encoding — and the people (2–5). Write it down.
  2. Write the first paragraph of product.md for that repo by hand: what it is, who uses it, the one business goal. This is what "Generate Steering Docs" should have said.
  3. List the five rules your team argues about most in review. These become code-style-*.md.
  4. List what goes in .kiroignore for this repo: secrets, fixtures, generated dirs, compliance-scoped paths.
  5. Pick the first ticket you'll run through a spec, and who pairs on it. Put a date on the retro.

Expected result

Every row of the Module 8 rollout checklist has a name next to it, and the retro has a date. Share it with the team.

If you get stuck

  • Can't pick one repo. Choose the one with the clearest conventions and an active backlog — not the biggest.
  • The team isn't available. Do the draft solo, then book 15 minutes to confirm names and dates.
Capstone · Lab 9

One feature end to end with AI-DLC + Claude Code

⏱ 60–90 min 🔧 Claude Code CLI · git · an empty directory · the awslabs/aidlc-workflows repo 🎯 Take one small feature from intent to reviewed code through every AI-DLC gate — and see the aidlc-docs/ trail it leaves

This is the whole loop from Module 0, done once by hand. It uses the open-source AI-DLC workflow on Claude Code — not the Kiro IDE — which is the point: the process is harness-neutral (Module 7). You'll build a small Task Management API.

Steps

  1. Install the workflow. New empty folder, git init. Clone awslabs/aidlc-workflows. Copy its core workflow in as your CLAUDE.md, and its rule details into .aidlc-rule-details/. Commit both — version the process like you version code. Start claude and ask "What instructions are currently active in this project?" to confirm they loaded.
  2. Kick off Inception with the mandatory trigger: Using AI-DLC, build a REST API for task management with user authentication, task CRUD, priority levels, and due dates. Without the Using AI-DLC, prefix the rules are ignored.
  3. Workspace detection. It sees an empty dir → greenfield, skips reverse-engineering, writes aidlc-docs/inception/workspace-detection/workspace-analysis.md, and waits. Approve.
  4. Requirements. It writes requirement-verification-questions.md — multiple choice: framework (Express / FastAPI / Spring / Django), database, auth (JWT vs OAuth2), deploy target. Answer in the file, and be specific — JWT, RS256, 15-min access + 30-day refresh beats JWT. Tell it you're done; it produces requirements.md. Ask it to add one requirement (e.g. "FR-011: task tags"), confirm the file changed, approve. Enable the Security Baseline extension if offered.
  5. User stories + execution plan. INVEST stories in user-stories.md plus an execution-plan.md. Don't skip — the stories become the acceptance criteria for the tests. Review, approve.
  6. Application design. application-design.md — architecture, components, data model — reviewed before any code. Approve; the sign-off is logged to aidlc-docs/audit.md.
  7. Units. It splits the design into units/units-breakdown.md (Unit 01 Auth, Unit 02 Task CRUD, …). Approve.
  8. Construction, per unit. For Unit 01 it writes construction/unit-01/functional-design.md, then nfr-design.md. Only after you approve both does it write source (src/auth/… + tests) and log them in code-artifacts.md. Do at least Unit 01 fully.
  9. Resume from the state file. Start a fresh session and type Continue AI-DLC for this project. Check aidlc-docs/aidlc-state.md for current status. It reads the state and picks up at the next gate — a teammate on another tool could take it from here.
  10. Read the trail. Open aidlc-docs/audit.md — every gate, approval, and cross-document consistency check, in order. That's what vibe coding never leaves behind.

Expected result

Working code for at least Unit 01 that matches the approved requirements and design — no drift — and a fully populated aidlc-docs/ tree: workspace analysis, requirements, stories, design, units, per-unit functional + NFR designs, code-artifacts, plus audit.md and aidlc-state.md. You never hand-wrote a spec; you answered a structured interview and approved plans.

If you get stuck

  • Claude Code just starts coding. You dropped the Using AI-DLC, prefix, or CLAUDE.md didn't load — re-check with the "what instructions are active" question.
  • The requirements come back vague. Your answers in the questions file were vague. One concrete decision per line.
  • Context window fills mid-build. Expected — start a fresh session with the "Continue AI-DLC … check aidlc-state.md" prompt.
  • It wants 30 stages for a tiny feature. Set the depth lower or say which stages to skip — the adaptive engine takes the instruction (Module 0).
