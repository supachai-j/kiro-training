พัฒนางานด้วย AWS Kiro

คอร์สนี้พาคุณจาก "เคยได้ยินชื่อ Kiro" ไปสู่ "รันฟีเจอร์ผ่าน spec ได้, ตั้ง steering ให้ repo ของเราได้, ต่อ MCP server ได้ และติดตั้ง Power ได้" เขียนสำหรับนักพัฒนาที่เขียนโค้ดส่งงานอยู่แล้ว แต่เพิ่งเริ่มใช้ Kiro

อ่านบทเรียนตามลำดับ แต่ละบทใช้เวลา 15–20 นาที จบด้วย สรุปประเด็นสำคัญ และแบบฝึก ลองทำ สั้น ๆ ตัวอย่าง config ทุกอันคัดลอกไปใช้ได้เลย

สรุปบรรทัดเดียว Kiro คือ AI agent ตัวเดียวที่ใช้ได้ทั้ง IDE, CLI, Web และ Mobile ขับเคลื่อนด้วยโฟลเดอร์ .kiro/ ใน repo ของคุณ แนวคิดหลักคือ spec-driven development: ตกลง requirements และ design ให้เรียบร้อย ก่อน ให้ agent เขียนโค้ด เพื่อให้ผลลัพธ์ตรวจทานได้และไม่หลุดประเด็น
ความสดของข้อมูล Kiro ออกอัปเดตเร็วมาก ชื่อ trigger, flag และรายการ Powers อาจเปลี่ยนได้ ให้ใช้คอร์สนี้เป็น "แนวคิดหลัก" แล้วตรวจรายละเอียดเป๊ะ ๆ กับ kiro.dev/docs อีกครั้ง

พื้นฐาน AI-DLC

ก่อนจะถึงเครื่องมือ ต้องเข้าใจแนวคิดก่อน AI-DLC — AI-Driven Development Lifecycle คือ methodology ที่ Kiro ถูกสร้างมาเพื่อรองรับ บทนี้เป็นพื้นหลัง: มันมาจากไหน, พูดว่าอะไรจริง ๆ และทำไมบทที่เหลือของคอร์สนี้ (specs, steering) จึงคือ AI-DLC ในทางปฏิบัติ ไม่มี config ในบทนี้ — มีแค่แนวคิดหลัก

สรุปบรรทัดเดียว AI-DLC ออกแบบ software lifecycle ใหม่รอบ ๆ loop ง่าย ๆ: AI ร่างแผนและลงมือทำ มนุษย์เป็นคนตัดสินใจ ทีมเป็นคนรีวิว มันเป็น methodology ไม่ใช่ product — เผยแพร่โดย AWS และ Kiro คือการนำไปใช้จริงที่ตรงที่สุด

ประวัติสั้น ๆ — เรามาถึงจุดนี้ได้ยังไง

  1. ยุคเขียนมือ SDLC แบบคลาสสิกสร้างรอบ ๆ กระบวนการที่ขับเคลื่อนด้วยมนุษย์และใช้เวลานาน: sprint, การจัด backlog, การประเมิน, การส่งต่องานระหว่างบทบาทเฉพาะทาง มุมมองของ AWS คือทีมใช้เวลาส่วนใหญ่ไปกับ "กิจกรรมที่ไม่ใช่งานหลัก เช่น การวางแผน การประชุม และพิธีกรรม SDLC อื่น ๆ" แทนที่จะทำที่ตัวผลิตภัณฑ์
  2. AI-assisted coding (ประมาณ 2021–2023) GitHub Copilot และเครื่องมือคล้ายกันนำ autocomplete มาช่วย AI เร่งงานเฉพาะจุด — เติมโค้ด, boilerplate, docs — แต่กระบวนการรอบ ๆ ไม่เปลี่ยน AI เป็นแค่ sidecar ที่แปะเข้ากับ workflow ที่ออกแบบมาสำหรับมนุษย์
  3. "Vibe coding" (ต้นปี 2025) Andrej Karpathy ทำให้คำนี้เป็นที่รู้จักในโพสต์บน X เมื่อ 2 กุมภาพันธ์ 2025: "There's a new kind of coding I call 'vibe coding'" — บอกสิ่งที่อยากได้, รับการแก้ของ AI โดยแทบไม่อ่าน, วาง error กลับเข้าไป Karpathy ตั้งใจให้ใช้กับโปรเจกต์เล่น ๆ ช่วงสุดสัปดาห์ มันเร็วและสนุก และได้ซอฟต์แวร์ที่ไม่มี requirements, ไม่มี design ที่ผ่านการรีวิว, ไม่มีความเข้าใจร่วมกัน — โอเคสำหรับ demo แต่เป็นภาระสำหรับอะไรก็ตามที่ทีมต้องดูแล
  4. methodology แบบ AI-native — AI-DLC (กลางปี 2025) จุดยืนของ AWS คือกลยุทธ์ที่มีอยู่ทั้งสองแบบยังไม่พอ: การพัฒนาแบบ AI-assisted ขี้อายเกินไป (AI ยังเป็นแค่ผู้ช่วย) และแบบ AI-autonomous ตัดวิจารณญาณของมนุษย์ออกทั้งหมด ในคำพูดของ AWS ทั้งคู่ "ให้ผลลัพธ์ที่ไม่ดีนักทั้งด้านความเร็วและคุณภาพซอฟต์แวร์" และ "การเอา AI มาแปะเป็นผู้ช่วยเฉย ๆ ไม่เพียงจำกัดความสามารถของมัน แต่ยังตอกย้ำความไม่มีประสิทธิภาพแบบเดิม" คำตอบของ AI-DLC คือออกแบบ lifecycle เองใหม่ให้หมุนรอบ AI ที่ลงมือทำงานภายใต้การกำกับของมนุษย์อย่างต่อเนื่อง

Raja SP, Principal Solutions Architect ที่ AWS เผยแพร่คำอธิบายก่อตั้งบน AWS DevOps blog เมื่อ 31 กรกฎาคม 2025 พร้อม whitepaper นิยาม method ตามด้วยบทความเดินตัวอย่างกับ Amazon Q Developer เมื่อ 29 พฤศจิกายน 2025 และ AWS Labs ปล่อย workflow engine แบบโอเพนซอร์ส (awslabs/aidlc-workflows)

AI-DLC Principles คือกรอบแนวคิดและปรัชญาพื้นฐานที่พัฒนาโดย AWS Labs เพื่อเปลี่ยนผ่านการพัฒนาซอฟต์แวร์จากการใช้ AI เป็นเพียงผู้ช่วยแคบ ๆ (AI-Assisted) ไปสู่การให้ AI เป็นเครื่องมือหลักในการขับเคลื่อนระบบ โดยมีมนุษย์เป็นผู้ควบคุมและตัดสินใจเชิงกลยุทธ์ หลักการทั้งเก้าดึงไปสามทิศทาง: ออกแบบใหม่ ไม่ใช่แปะเพิ่ม, AI ขับเคลื่อน มนุษย์ตัดสินใจ, และ design มาก่อน เฟสน้อยและมีด่านตรวจ

หลักการความหมายตัวอย่าง
1. Reimagine workflows for the AI era — แทนที่จะ retrofitออกแบบกระบวนการทำงานใหม่หมดให้สอดรับกับความเร็วระดับ AI แทนที่จะนำ AI ไปแทรกไว้ในพิธีกรรมเดิม ๆ (เช่น สปรินต์ 2 สัปดาห์)เปลี่ยนจากการวางแผน Sprint 2 สัปดาห์ มาใช้ Bolt (รอบการทำงานระดับชั่วโมงหรือวัน) โดย AI ร่างสถาปัตยกรรมและแผนงานให้ทีมตรวจสอบทันที
2. AI orchestrates development while humans maintain controlให้ AI เป็นผู้เสนอแผนและลงมือปฏิบัติตามขั้นตอน ในขณะที่มนุษย์ทำหน้าที่ตรวจสอบ อนุมัติ (Human-in-the-loop) และควบคุมทิศทางสูงสุดเมื่อสั่งให้สร้างระบบชำระเงิน AI จะไม่เขียนโค้ดทันที แต่จะสร้างแผนและตั้งคำถามถามมนุษย์ก่อน เมื่อมนุษย์อนุมัติ (Approve) AI จึงจะเริ่มลงมือ
3. Integrate design techniques into the coreการออกแบบระบบไม่ใช่ขั้นตอนเสริม แต่เป็นแกนหลักในการสร้างบริบท (Context) ที่สมบูรณ์เพื่อให้ AI นำไปพัฒนาต่อได้อย่างแม่นยำก่อนลงมือเขียนโค้ด AI จะต้องผ่านขั้นตอนสร้าง Domain Model, NFR Design (การออกแบบประสิทธิภาพและความปลอดภัย) และโครงสร้างคอมโพเนนต์เสมอ
4. Balance AI capabilities with human expertiseปรับการทำงานให้สอดคล้องกับความเป็นจริง ใช้ประโยชน์จากจุดแข็งของ AI ในการประมวลผลงานหนัก (Heavy Lifting) ขณะเดียวกันก็ตระหนักถึงข้อจำกัดของมันAI ทำหน้าที่เขียนชุดทดสอบและสร้างโค้ดส่วนใหญ่ แต่ให้มนุษย์ที่เข้าใจบริบทธุรกิจเป็นผู้กำหนดและอนุมัติ Acceptance Tests
5. Preserve proven practices while optimizing for AI speedรักษาแนวปฏิบัติเดิมที่ดีและได้ผลไว้ (เช่น User Stories, Risk Management) แต่ปรับปรุงให้ทำงานร่วมกับความเร็วของ AI ได้อย่างราบรื่นยังคงใช้ User Stories ในการกำหนดความต้องการของลูกค้า แต่ให้ AI เป็นผู้ย่อยและวิเคราะห์ออกเป็นงานย่อย ๆ (Units of Work) ให้ในไม่กี่นาที
6. Streamline roles to minimize handoffsปรับลดความซับซ้อนของบทบาทในทีมและการส่งต่อไม้ (Handoffs) เพื่อให้กระบวนการไหลลื่น โดยที่ยังรักษาการตรวจสอบที่จำเป็นไว้ใช้การทำงานแบบ Mob Elaboration / Mob Construction ที่ Product, Developer และ QA มารวมตัวกันตรวจสอบแผนและโค้ดของ AI พร้อมกันในเซสชันเดียว แทนการส่งเอกสารข้ามแผนก
7. Simplify to three phases with strategic validation pointsลดขั้นตอนให้เหลือเพียง 3 เฟสหลักที่ชัดเจน (Inception → Construction → Operations) พร้อมกำหนดจุดตรวจรับรอง (Validation Gates) ในทุก ๆ เฟสในเฟส Inception เมื่อ AI ทำ Reverse Engineering โค้ดเก่าและวางแผนเสร็จ มนุษย์ต้องกดยืนยันผ่าน Gate ก่อนที่จะหลุดไปสู่เฟส Construction
8. Enable flexible, AI-recommended workflowsใช้เวิร์กโฟลว์ที่ยืดหยุ่น ปรับแต่งตามคำแนะนำของ AI และความเหมาะสมของแต่ละงาน แทนที่จะยึดติดกับเทมเพลตที่แข็งกระด้างถ้าเป็นการแก้ Bug ด่วน (Minimal Depth) AI จะแนะนำให้ข้ามขั้นตอน User Stories ไปที่การวิเคราะห์สาเหตุและแก้โค้ดทันที แต่ถ้าเป็นการย้ายระบบใหญ่ (Comprehensive Depth) AI จะรันครบทุกขั้นตอน
9. Build on familiar concepts to ease transitionต่อยอดจากแนวคิดและเครื่องมือที่นักพัฒนาคุ้นเคยอยู่แล้ว เพื่อให้ทีมเรียนรู้และปรับมาใช้ AI-DLC ได้อย่างรวดเร็วบังคับใช้กฎของ AI ผ่านไฟล์ข้อความธรรมดาที่คุ้นเคย (เช่น CLAUDE.md, .cursor/rules/, หรือไฟล์ Steering) โดยไม่ต้องติดตั้งซอฟต์แวร์ใหม่ซับซ้อน
หมายเหตุเรื่องรายการ จำนวนต่างกันตามบทความ whitepaper นิยาม method ระบุ ข้อที่ 10 — "No Hard-Wired, Opinionated SDLC Workflows": แทนที่จะกำหนดเส้นทางตายตัวสำหรับงานสร้างใหม่ / refactor / แก้บั๊ก ให้ AI แนะนำแผนระดับบนจาก intent ที่คุณบอก ส่วนทีมที่ทำ engine โอเพนซอร์สสรุปเป็นตัวขับการออกแบบ 5 ข้อ — adaptive execution, human-in-the-loop, methodology-first (ไม่ผูกเครื่องมือ), reproducible, no duplication (แหล่งความจริงเดียว) ให้มองทั้งหมดเป็น "รูปทรง" ของปรัชญา ไม่ใช่คัมภีร์ตายตัว

methodology กับ engine โอเพนซอร์ส

แยกสองอย่าง methodology คือ 3 เฟสและ loop ข้างบน ส่วน engine โอเพนซอร์ส — awslabs/aidlc-workflows ที่ Kiro CLI รันได้ — แปลงมันเป็น pipeline การรัน: 5 เฟส 33 stages (Initialization, Ideation, Inception, Construction, Operation), agent 14 ตัว, และด่านอนุมัติทุก stage

  • การเลือก stage เป็นแบบ binary — แต่ละ stage รันหรือข้าม ตามงาน บั๊กที่รู้สาเหตุข้าม user stories และ application design; แพลตฟอร์มใหม่รันครบ Reverse Engineering จุดเฉพาะโค้ด brownfield (ที่มีอยู่แล้ว)
  • depth ยืดหยุ่นได้ ใน stage ที่รัน มีระดับ Minimal / Standard / Comprehensive คุมว่าแต่ละ artifact มีรายละเอียดและเหตุผลมากแค่ไหน ตามความซับซ้อนและความเสี่ยง
  • กลยุทธ์ test เป็นปุ่มแยก Minimal / Standard / Comprehensive เหมือนกัน แต่แยกจาก depth — รัน bug fix แบบ depth Minimal ได้ พร้อมกับบังคับ test ความปลอดภัยและ integration แบบ Comprehensive
  • state อยู่ในไฟล์ธรรมดา engine เขียนโฟลเดอร์ aidlc-docs/ ที่มี aidlc-state.md (ความจำ session) และ audit.md (ร่องรอยทีละขั้น) เพราะเป็นแค่ไฟล์ใน repo คุณเริ่ม bolt ใน IDE หนึ่งแล้วทำต่อในอีก IDE ได้ — agent อ่าน state เดียวกัน

Kiro อยู่ตรงไหน

แยกสามระดับให้ชัด:

  • AI-DLC คือ methodology — เฟส, loop, กฎว่ามนุษย์เป็นคนตัดสินใจ
  • Spec-driven development คือ วิธีหนึ่งในการจัดโครงสร้าง artifacts ที่ AI-DLC ต้องการ
  • Kiro คือ เครื่องมือ ที่สร้างรอบโครงสร้างนั้น

requirements.md → design.md → tasks.md ของ Kiro คือ artifact trail ที่ Inception และ Construction สมมติไว้พอดี; ไฟล์ steering พก context ถาวรที่ loop นี้พึ่งพา Kiro CLI รัน aidlc-workflows ของ AWS ได้ตรง ๆ ดังนั้นบทที่ 3 และ 4 ของคอร์สนี้ — Specs และ Steering — คือเฟส Inception และ Construction ของ AI-DLC ที่ทำให้เป็นรูปธรรม

ตัวเลขที่ทุกคนชอบอ้าง

  • Amazon Bedrock — "Mantle" การ re-architecture inference engine ประเมินไว้ ~40 คน หนึ่งปี; ทีม 6 คนส่งได้ใน ~76 วันด้วย Kiro — ราว 100,000 บรรทัดของ production Rust, 40+ commit ต่อสัปดาห์ต่อคน เลือก Rust ส่วนหนึ่งเพราะ error จาก compiler ที่แม่นยำช่วยให้ AI แก้ความผิดพลาดของตัวเองได้
  • Wipro ที่ re:Invent 2025 (DVT214) AWS เล่าว่าย่นงานที่วางแผนไว้ ~3 เดือน เหลือ ~20 ชั่วโมง — mob session วันละ 4 ชั่วโมง 5 วัน
  • สถาบันการเงินในยุโรปแห่งหนึ่ง จาก 1 product owner + 12 devs ส่ง 15 features ต่อ sprint กลายเป็น 1 product owner + 3 devs ส่ง 35 features ต่อ sprint — ตัด contractor ภายนอก 9 FTE
อ่านอย่างมีวิจารณญาณ ทั้งหมดนี้เป็นตัวเลขของ AWS จากงานที่ AWS ช่วยรัน และยังไม่มีใครเผยแพร่เคสที่ล้มเหลว baseline อิสระที่ใกล้ที่สุด: การรับ AI-assistant แบบไม่มีโครงสร้างได้ราว 10–15% ไม่ใช่ 10–15 เท่า มองตัวเลขเป็นทิศทาง — บทเรียนที่นำไปใช้ได้คือ รูปทรง: ทีมเล็ก, loop ที่แน่นมาก และภาษาที่ feedback ของมัน AI เอาไปทำต่อได้

ในทางปฏิบัติ — ฟีเจอร์เล็ก ๆ หนึ่งอันผ่าน loop

โจทย์: "เพิ่มปุ่ม export CSV ในหน้า Reports"

Inception คุณให้ intent บรรทัดเดียวกับ agent มันกลับมาพร้อมคำถามที่มนุษย์ต้องตอบ: คอลัมน์ไหนบ้าง? เคารพ filter ปัจจุบัน หรือ export ทั้งหมด? คอลัมน์วันที่ใช้ time zone ไหน? ใครมีสิทธิ์ export — ทุก role หรือแค่ admin? ไม่มีใครเดา — ทีมตอบใน mob 15 นาที ผลลัพธ์: requirements.md ที่มีบรรทัด EARS เช่น "WHEN an admin clicks Export THE SYSTEM SHALL download a CSV of the currently filtered rows, dates in the workspace time zone."

Construction agent เสนอ: ใช้ ReportQuery เดิมซ้ำ, stream CSV เพื่อไม่ให้ export 200k แถวกินหน่วยความจำ, เพิ่มการเช็คสิทธิ์ reports:export มีการตัดสินใจจริงหนึ่งเรื่อง — stream vs สร้างไฟล์ในหน่วยความจำ — ทีมเลือก stream ใน 2 นาที agent เขียน endpoint, ปุ่ม และ test ใน bolt เดียว

Operations agent เพิ่ม metric ใน CloudWatch สำหรับจำนวนและเวลา export และโน้ตใน runbook ทีมรีวิวการเปลี่ยน dashboard แล้ว merge

ประเด็น: คำถามที่ทำให้ต้องแก้งานซ้ำ ("แค่ admin?") ถูกถามใน Inception ตอนที่คำตอบราคาแค่หนึ่งประโยค — ไม่ใช่ตอน code review ที่จะราคาเท่ากับเขียน endpoint และปุ่มใหม่

ข้อควรระวังอย่างตรงไปตรงมา — และช่องโหว่ด้านการกำกับ

งานเขียนเรื่อง AI-DLC ส่วนใหญ่ตอนนี้เป็นการโปรโมต คำวิจารณ์ที่คมกว่าคือ SDLC แบบเดิมฝัง control ไว้เงียบ ๆ — peer review, audit trail, release gate — และการรันแผน โค้ด และ test จบในบ่ายเดียว ละลาย control พวกนั้นเร็วกว่าที่มันสร้างของมาแทน มีสองช่องที่ควรพูดถึง

  • "verify and approve" ไม่ใช่ control methodology บอกว่ามนุษย์อนุมัติทุกด่าน แต่ไม่ได้บอกว่าใคร เทียบกับมาตรฐานอะไร บันทึกไว้ที่ไหน เติมให้ครบ: named approver ต่อหนึ่ง unit of work — และไม่ใช่คนที่สั่ง plan ออกมา — checklist หนึ่งหน้า (ระดับความลับข้อมูลที่แตะ, blast radius, เส้นทาง rollback, ส่วนที่เบี่ยงจาก steering files) และ decision log ที่ผูกกับเวอร์ชันของ spec และ steering file "ที่ประชุมเห็นด้วย" ไม่ผ่าน auditor คนไหน
  • ปัญหา self-grading ในเฟส Construction agent ตัวเดียวกันเขียนทั้งโค้ด และ test ของมัน suite ที่เขียว ๆ ที่คนเขียนโค้ดเป็นคนเขียนเอง พิสูจน์ความสอดคล้อง ไม่ใช่ความถูกต้อง — agent ที่อ่าน requirement ผิด ก็เขียน test ที่ยืนยันความผิดนั้นอย่างซื่อสัตย์ ที่ความเร็ว bolt error สะสมเงียบ ๆ จนกว่า production จะเจอ วิธีแก้: acceptance tests ที่คนรีวิว แช่แข็งไว้ตั้งแต่เฟส Inception ก่อน Construction — agent ลงมือทำโดยเทียบกับเกณฑ์ที่มันไม่ได้ตั้งเอง
  • ความเร็วไม่ใช่ความเสถียร ผลสำรวจ DORA 2025 (เน้น AI, ผู้ตอบ ~5,000 คน) พบว่าการรับ AI มาใช้ตอนนี้สัมพันธ์ เชิงบวก กับ throughput แต่ยัง เชิงลบ กับ delivery stability วัดแต่ความเร็วคือวัดแกนที่พลิกมาข้างเราแล้ว ให้ track defect-escape rate คู่กับ cycle time ไม่งั้นก็แค่ย้าย QA ไปไว้ที่ production
  • ตัวเลข productivity เป็นของ AWS ไม่ใช่ของคุณ การรับ AI-assistant แบบไม่มีโครงสร้างได้ราว 10–15%; ตัวเลข 10–15 เท่าที่อ้าง ในคำบอกเล่าของ AWS คือ "methodology" มอง benchmark ของ vendor เป็นทิศทาง — ยังไม่มีใครเผยแพร่เคสที่ล้มเหลว
  • เซสชัน Mob กิน senior attention มันต้องใช้คนซีเนียร์ที่สุดของคุณ พร้อมกัน เป็นชั่วโมง "lifecycle ใช้เวลาพิมพ์น้อยลง ใช้ความสนใจของซีเนียร์มากขึ้น" และการอนุมัติแบบตรายาง "เสื่อมเป็นการคลิกอัตโนมัติภายในสัปดาห์เดียว" ถ้าไม่มี checklist จริง
  • AI-DLC ยังใหม่ (กลางปี 2025) และยังขยับ; เป็น methodology ของ vendor (AWS ได้ประโยชน์เมื่อคุณรับมาใช้) หลักการพื้นฐาน — requirements ก่อนโค้ด, มนุษย์อยู่บนการตัดสินใจ, loop สั้น, context อยู่ใน repo — ยังใช้ได้ไม่ว่าจะใช้เครื่องมือไหน ทีมเล็กหรือทีมเดี่ยวปรับใช้โมเดล Mob ไม่ได้รันตามตัวอักษร
สรุปประเด็นสำคัญ
  • AI-DLC ออกแบบ lifecycle ใหม่รอบ ๆ AI ทำงาน มนุษย์ตัดสินใจ ทีมรีวิว — ไม่ใช่ AI แบบ autocomplete (ขี้อายเกินไป) และไม่ใช่ AI อิสระ (ไม่มีวิจารณญาณ)
  • loop: AI วางแผน → AI ถาม → มนุษย์ตรวจ → AI ลงมือ → ทีมรีวิว → วนซ้ำ
  • เฟส: Inception (Mob Elaboration) → Construction (Mob Construction) → Operations context สะสมไปข้างหน้า
  • คำศัพท์: Sprint → Bolt, Epic → Unit of work, งานเดี่ยว/async → Mob
  • AI-DLC คือ methodology; spec-driven development จัดโครงสร้าง artifacts; Kiro คือเครื่องมือ บท Specs และ Steering ของคอร์สนี้ คือ AI-DLC ในทางปฏิบัติ
  • เรื่อง 76 วัน / Rust 100k บรรทัด เป็น anecdote ของ vendor — เป็นสัญญาณที่มีประโยชน์ ไม่ใช่ผลที่ตรวจสอบแล้ว
  • มันเอา control ของ SDLC ออกเร็วกว่าที่สร้างของมาแทน — เพิ่ม named approver ต่อ unit of work, แช่แข็ง acceptance tests ใน Inception, และ track defect-escape rate ไม่ใช่แค่ความเร็ว
ลองทำ อ่านผ่าน ๆ AWS blog ก่อตั้ง (ลิงก์ด้านล่าง) แล้วดูฟีเจอร์ล่าสุดที่คุณทำ ส่วนไหนคือ "Inception" (ตัดสินว่าจะสร้างอะไร) และส่วนไหนคือ "Construction"? การตัดสินใจที่ขาดหายไปตรงไหนทำให้คุณต้องแก้งานซ้ำ? ช่องว่างนั้นคือสิ่งที่เฟส Inception มีไว้เพื่อปิด
🧪 Lab 0 — แมป PR จริงลงบน AI-DLC

เป้าหมาย: รู้สึกว่าเส้นแบ่ง Inception / Construction อยู่ตรงไหนในงานของคุณเอง และหาหนึ่งการตัดสินใจที่หลุดไปโผล่ตอน code review

  1. เปิด pull request ที่ไม่เล็กจิ๋วอันล่าสุดที่คุณรีวิวหรือเขียน อ่านคำอธิบายและ diff
  2. บนกระดาษ (หรือไฟล์ scratch) ทำสามคอลัมน์: Inception, Construction, Operations
  3. ใส่การตัดสินใจหรือการเปลี่ยนทุกอย่างจาก PR ลงในเฟสที่มัน ควร ถูกตกลง เช่น "export ให้แค่ admin" → Inception; "stream CSV" → Construction; "เพิ่ม metric export" → Operations
  4. วงกลมอันที่จริง ๆ แล้วถูกตัดสินใจ ระหว่าง code review หรือหลัง merge สำหรับแต่ละอัน เขียนหนึ่งประโยคที่จะปิดเรื่องนั้นได้ใน Inception
  5. นับดู: comment รีวิวกี่อันจริง ๆ แล้วคือ "Inception ที่ขาด" ไม่ใช่ "คุณภาพโค้ดที่ขาด"

เสร็จเมื่อ คุณมีอย่างน้อยหนึ่งการตัดสินใจที่วงไว้ พร้อมประโยค Inception หนึ่งประโยคของมัน ประโยคนั้นคือรูปทรงของ acceptance criteria แบบ EARS — คุณจะเขียนของจริงในบทที่ 3

บทที่ 1

Kiro คืออะไร และทำไม

ปัญหาที่ Kiro ถูกสร้างมาเพื่อแก้

การคุยกับ AI ไปเรื่อย ๆ จนโค้ดโผล่ออกมา — "vibe coding" — เหมาะกับการสำรวจไอเดีย แต่แย่มากสำหรับอะไรก็ตามที่ทีมต้องดูแลต่อ คุณได้ demo ที่ทำงานได้ แต่ requirements อยู่แค่ในประวัติแชต ไม่มีใครรีวิว design และการแก้ครั้งถัดไปก็พังของเดิม เพราะไม่มีความเข้าใจร่วมกันว่าฟีเจอร์นี้ควรทำอะไร

คำตอบของ Kiro คือทำให้ เอกสารการวางแผน เป็นของหลัก: requirements ที่เขียนไว้, design ที่เขียนไว้ และรายการ task ที่ agent ทำตาม — ทั้งหมดเก็บใน repo และรีวิวได้เหมือนโค้ด คุณยังเลือก vibe ได้เมื่อต้องการ แต่มีเส้นทางที่มีโครงสร้างสำหรับงานที่สำคัญ

agent เดียว ทุกช่องทาง

Kiro ไม่ได้เป็นแค่ IDE แต่เป็น agent "harness" ตัวเดียวที่เปิดให้ใช้ผ่านหลายช่องทาง:

ช่องทางไว้ทำอะไร
IDE (แอปเดสก์ท็อป)ประสบการณ์หลัก — editor, chat panel, specs, steering, UI ของ hooks
CLIสั่ง agent ตัวเดียวกันจาก terminal หรือ script / CI
Webagent บนเบราว์เซอร์ เหมาะกับงานที่ใช้เวลานาน
Mobileตามงานจากมือถือ (ไม่รองรับ MCP)

จุดสำคัญ: config .kiro/ ของคุณใช้ร่วมกันทุกช่องทาง และติดไปกับ repository ตั้ง steering ครั้งเดียว ก็มีผลไม่ว่าเพื่อนร่วมทีมจะอยู่ใน IDE หรือ CI กำลังรัน CLI

โฟลเดอร์ .kiro/

ทุกอย่างที่เฉพาะกับโปรเจกต์อยู่ในโฟลเดอร์เดียวที่ root ของ repo และ commit ได้เหมือน source อื่น ๆ:

.kiro/
├── steering/          # ความรู้ถาวรของโปรเจกต์ (บทที่ 4)
│   ├── product.md
│   ├── tech.md
│   └── structure.md
├── hooks/             # automation ตาม event เก็บเป็น JSON (บทที่ 5)
│   └── lint-on-save.json
├── specs/             # หนึ่งโฟลเดอร์ต่อหนึ่ง feature / bugfix (บทที่ 3)
│   └── checkout-refactor/
│       ├── requirements.md
│       ├── design.md
│       └── tasks.md
└── settings/
    └── mcp.json       # การเชื่อมต่อเครื่องมือภายนอก (บทที่ 6)

เริ่มต้นใช้งาน

  1. ติดตั้ง IDE (เดสก์ท็อป), CLI หรือใช้ Web agent
  2. ลงชื่อเข้าใช้ ด้วยบัญชีที่องค์กรใช้
  3. นำเข้าการตั้งค่า VS Code เมื่อระบบถาม — keybinding, theme และ extension จะย้ายตามมา ทำให้ IDE คุ้นมือตั้งแต่วันแรก
  4. เปิด repo จริง แล้วสั่ง "Generate Steering Docs" (บทที่ 4) เพื่อให้ agent มีบริบทของโปรเจกต์ก่อนที่คุณจะถามอะไร

ชิ้นส่วนเชื่อมกันยังไง

นอกเหนือจากโค้ด — Kiro CLI สำหรับงานออกแบบ

agent แบบ spec-first ตัวเดียวกันนี้ไปโผล่นอกโค้ดแอปด้วย OpenDesign เวิร์กโฟลว์ออกแบบแบบ open-source, local-first ที่ห่อ Kiro CLI ไว้เป็น "first-party adapter" สำหรับแปลง visual reference ให้เป็น UI ที่ implement แล้ว — ใช้วินัยแบบ requirements → design → tasks เดียวกับในบทนี้ แค่เล็งไปที่ pixel แทน business logic

loop ของมัน: ป้อน screenshot ของ state ที่ต้องการ (desktop, mobile, หลาย scenario); มันเขียน spec และ design doc ให้รีวิวก่อนจะ render อะไร; token และ convention ของ design system อยู่ในไฟล์ steering ทำให้ทุก run ตรงแบรนด์; แล้ว output ถูกตรวจในเบราว์เซอร์จริงข้าม breakpoint ทำซ้ำเทียบกับ reference hooks และ MCP ทำงานแบบเดียวกับตอนใช้กับโค้ด — automate ตอน save, เชื่อมเครื่องมือภายนอก

ข้อควรระวังหนึ่งข้อที่โปรเจกต์บอกตรง ๆ: "Kiro CLI ไม่มี taste ให้โดย default" ถ้าไม่มี design system และรูป reference ในไฟล์ steering output จะดูทั่วไป เวิร์กโฟลว์นี้ไม่ได้แทน design judgment — มันแค่ให้ judgment นั้นมีที่อยู่ถาวร แทนที่จะอยู่แค่ในประวัติแชต

ในทางปฏิบัติ — เริ่มใน IDE จบใน CI

โจทย์: แก้บั๊กที่ CI เป็นคนตรวจ

นักพัฒนาเปิด repo ใน IDE อธิบายบั๊ก agent เสนอ Bugfix Spec เขาอนุมัติแล้วให้ agent ลงมือแก้ — โหมด Supervised จึงมองทุกการเปลี่ยน

เขา push branch ใน CI มี pipeline step รัน kiro จาก CLI กับ repo เดียวกัน: มันอ่าน .kiro/steering/security.md ที่ commit ไว้ แล้วรัน prompt "รีวิว diff นี้เทียบกฎความปลอดภัยของเรา" agent ตัวเดียวกัน กฎเดียวกัน ไม่ต้องตั้งค่าเพิ่ม — เพราะ .kiro/ อยู่ใน repo ที่ CI checkout

ผู้รีวิวเหลือบดูการเปลี่ยนจากแอป Mobile ตอนขากลับบ้าน แล้วทิ้ง comment ไว้ agent เดียว สี่ช่องทาง แหล่งความจริงเดียว

🧪 Lab 1 — สัมผัสแรก

เป้าหมาย: ติดตั้ง Kiro และดูว่ามันอ่านโปรเจกต์คุณยังไง

  1. ติดตั้ง Kiro IDE และลงชื่อเข้าใช้ เมื่อระบบถาม ให้ import การตั้งค่า VS Code
  2. เปิดโปรเจกต์จริงเล็ก ๆ ที่คุณรู้จักดี (ไม่ใช่โฟลเดอร์เปล่าใหม่)
  3. สั่ง Generate Steering Docs เปิด .kiro/steering/product.md, tech.md และ structure.md ที่สร้างใหม่
  4. อ่านทั้งสามไฟล์ ในแต่ละไฟล์ ทำเครื่องหมายหนึ่งข้อความที่ ผิดหรือคลุมเครือ เกี่ยวกับโปรเจกต์คุณ
  5. ในแชต (โหมด vibe) ถาม: Summarise what this project does and its main entry points. เทียบคำตอบกับความจริง

เสร็จเมื่อ มีไฟล์สามไฟล์บนดิสก์ และรายการอย่างน้อยสามอย่างที่ต้องแก้ในนั้น คุณจะแก้มันใน Lab 4

สรุปประเด็นสำคัญ
  • Kiro = agent เดียว หลายช่องทาง (IDE / CLI / Web / Mobile), config .kiro/ ชุดเดียวใน repo
  • เดิมพันหลักคือ spec-driven development: requirements + design เป็นไฟล์ที่รีวิวได้ ไม่ใช่ประวัติแชต
  • ยังมีโหมด "vibe" แบบอิสระสำหรับสำรวจไอเดียและ debug
  • .kiro/ เก็บ steering/, hooks/, specs/ และ settings/mcp.json
ลองทำ ติดตั้ง IDE, เปิดโปรเจกต์เล็ก ๆ, นำเข้าการตั้งค่า VS Code แล้วสั่ง "Generate Steering Docs" อ่านไฟล์ทั้งสามที่มันสร้าง — นั่นคือมุมมองแรกว่า Kiro เข้าใจโปรเจกต์คุณอย่างไร
บทที่ 2

โหมด Vibe / Chat

agent เริ่มต้น

เมื่อเปิด chat panel คุณกำลังคุยกับ Default agent — โหมด "vibe" เป็นแบบอิสระ: อธิบายสิ่งที่ต้องการเป็นภาษาธรรมชาติ แล้ว Kiro ตอบด้วยการแก้ไฟล์ คำอธิบาย หรือคำสั่ง ไม่มีโครงสร้างบังคับและไม่มีเอกสารที่ถูกสร้างขึ้น ใช้กับ:

  • คำถามเกี่ยวกับ codebase ("เรา validate JWT ตรงไหน?")
  • debug ปัญหาเฉพาะจุด
  • การแก้เล็ก ๆ เฉพาะที่
  • ลองแนวทางก่อนตัดสินใจทำเป็น spec

Vibe vs Spec — และโหมดที่อยู่ระหว่างกลาง

โหมดผลลัพธ์ใช้เมื่อ
Vibe (Default)แก้ไข / ตอบตรง ๆ ไม่มีเอกสารคำถาม, debug, งานสำรวจ
Specrequirements.md + design.md + tasks.mdงานฟีเจอร์ที่ต้องรีวิว หรือแตะหลายไฟล์
Planแผนอย่างเดียว — ไม่แก้โค้ดอยากได้แนวทางเป็นลายลักษณ์อักษรก่อนขยับ
Bug Fixวิเคราะห์ bug → แก้บั๊กที่ทำซ้ำได้ ต้องการกันการถอยหลัง (regression)
Quick Specถามสั้น ๆ แล้วสร้าง spec ให้อัตโนมัติฟีเจอร์เล็ก ไว้ใจให้ agent เติมช่องว่าง

Autopilot vs Supervised

แยกจากโหมด คุณเลือกได้ว่าจะให้ agent อิสระแค่ไหน:

  • Supervised — คุณอนุมัติทุกการเปลี่ยนไฟล์ก่อนบันทึกจริง ช้ากว่า ปลอดภัย และเป็นค่าเริ่มต้นที่เหมาะระหว่างเรียนรู้ workflow
  • Autopilot — agent ลงมือแก้เองแล้วคุณรีวิวผลลัพธ์ เหมาะกับงานแคบ ๆ ที่ scope ชัด และเคยเห็นมันทำได้ดี
หลักคิด อยู่ Supervised จนกว่าจะเห็น agent ทำ งานประเภทนี้ ถูกต้องหลายครั้ง แล้วค่อยย้ายเฉพาะงานประเภทนั้นไป Autopilot — ไม่ใช่ย้ายทุกอย่างพร้อมกัน

Context providers — เมนู #

Kiro รู้แค่สิ่งที่อยู่ใน context ของมัน คำนำหน้า # คือวิธีดึงสิ่งเฉพาะเข้ามา:

Providerเพิ่มอะไร
#codebaseKiro ค้น repo แล้วดึงไฟล์ที่มันคิดว่าเกี่ยวข้องเข้ามา
#file / #folderไฟล์หรือไดเรกทอรีที่คุณระบุ
#git diffการเปลี่ยนแปลงที่ยังไม่ commit
#terminalผลลัพธ์คำสั่งและประวัติล่าสุด
#problemsdiagnostics / error ของไฟล์
#url · #docs · #repository · #code · #mcpหน้าเว็บภายนอก, เอกสาร, repo อื่น, code snippet หรือ resource จาก MCP

ผสมกันในข้อความเดียวได้: Fix the failing test in #problems using the pattern from #file:src/auth/session.ts

วาง รูปภาพ (สกรีนช็อต, mockup, กล่อง error) ลงในแชตเป็น context ได้โดยตรงด้วย

session ยาว: checkpoints และ compaction

  • Checkpoints / rewind — Kiro บันทึก snapshot ระหว่างทำงาน ให้คุณย้อนกลับไปจุดที่ดีอยู่แล้วได้ แทนการไล่แก้ทีละอย่าง
  • Compaction — เมื่อ session ยาวขึ้น Kiro สรุป context เก่าเพื่ออยู่ในลิมิตของโมเดลโดยไม่หลุดประเด็น

คุณอยู่โหมด vibe — นี่คือการสืบสวน ไม่ใช่ฟีเจอร์ ข้อความแรก:

ประเด็น: vibe หาสาเหตุได้เร็วเพราะคุณป้อนสามอย่างที่สำคัญให้; วิธีแก้เลื่อนขึ้นไปเป็น spec เพราะมันจะถูกรีวิว

เป้าหมาย: เห็นแบบวัดได้ว่าคุณภาพคำตอบขึ้นกับ context ที่คุณให้

บทที่ 3

Specs

spec คืออะไร

spec คือชุดเอกสารที่มีโครงสร้าง ทำให้กระบวนการสร้างฟีเจอร์หรือแก้บั๊กเป็นทางการ แทนที่จะเป็นแชตยาว ๆ คุณได้สามไฟล์ใน .kiro/specs/<name>/ โดยแต่ละขั้นมีการอนุมัติของคุณเป็นด่าน:

ไฟล์เนื้อหา

EARS notation สำหรับ requirements

Kiro เขียน acceptance criteria แบบ EARS (Easy Approach to Requirements Syntax) — ชุดเทมเพลตประโยคเล็ก ๆ ที่ทำให้ requirement ทดสอบได้และไม่กำกวม:

WHEN <trigger> THE SYSTEM SHALL <response>
WHILE <state> THE SYSTEM SHALL <response>
WHERE <feature is included> THE SYSTEM SHALL <response>
IF <condition> THEN THE SYSTEM SHALL <response>

ตัวอย่าง: WHEN a user submits the checkout form with an expired card THE SYSTEM SHALL reject the payment and display "Your card has expired". แต่ละบรรทัดกลายเป็น test ได้

design ครอบทั้ง "อะไร" และ "ดีแค่ไหน"

design.md ที่ดีแยก functional (พฤติกรรม) ออกจาก non-functional (คุณภาพ) — แบบเดียวกับที่ AI-DLC ทำให้ชัด ด้วยขั้น requirements แล้วตามด้วยขั้น design สำหรับฝั่ง non-functional:

ด้านFunctional — อะไรNon-functional — ดีแค่ไหน
Performanceผู้ใช้ค้นหาสินค้าได้ค้นหาคืนผลภายใน 200 ms ที่ p99
Securityผู้ใช้ล็อกอินได้hash รหัสผ่านด้วย bcrypt; session หมดอายุใน 24 ชม.
Scalabilityระบบประมวลผลออเดอร์รองรับออเดอร์พร้อมกัน 10k ตอน peak
Reliabilityข้อมูลถูกจัดเก็บไม่มีข้อมูลสูญหาย; RPO ต่ำกว่า 1 นาที

AI-DLC รันเป็นสองขั้นต่อหนึ่ง unit of work: NFR Requirements Assessment (ระบุ benchmark, security posture, ขอบเขต compliance) แล้ว NFR Design (แปลงแต่ละข้อเป็นการตัดสินใจรูปธรรม — Redis cache กับ CDN, multi-AZ พร้อม health check, encrypt S3 at rest และ tokenize เลขบัตร) ตอนรีวิว design.md ของ Kiro เช็คว่ามีครบทั้งสองฝั่ง — ฝั่ง non-functional คือฝั่งที่มักถูกข้ามเงียบ ๆ

การรัน task แบบ waves

Kiro วิเคราะห์ dependency ระหว่าง task แล้วสร้าง dependency graph จากนั้นรันเป็น waves:

  • Wave 1 — task ที่ไม่มี dependency รันพร้อมกัน
  • Wave 2+ — task ที่ dependency ครบแล้ว รันพร้อมกัน
  • waves รันเรียงลำดับ; task ภายใน wave เดียวกันรันขนานกัน

คุณไม่ต้องตั้งค่าเอง — เป็นอัตโนมัติ และเป็นเหตุผลที่ spec มักเสร็จเร็วกว่าสั่ง task เดียวกันทีละอันในแชต

# TypeScript conventions

## Errors
Never throw bare strings. Throw an `AppError` subclass with a `code`.
Rationale: the API error middleware maps `code` to an HTTP status and a
safe message; a bare string leaks internals and 500s.

// avoid
throw "user not found";
// prefer
throw new NotFoundError({ code: "user.not_found" });

## Async
No floating promises. Every `await`-able call is awaited or explicitly
`void`-ed with a comment saying why.

## Imports
Absolute imports from `src/` only (`@/db`, not `../../db`).

เพราะเป็น fileMatch ไฟล์นี้โหลดเฉพาะตอน agent แตะไฟล์ .ts/.tsx — นักพัฒนา Python ไม่ต้องจ่ายค่า token ของมัน และมันจะละเอียดแค่ไหนก็ได้

เสร็จเมื่อ prompt เดิมให้โค้ดที่ต่างกันและทำตามกฎ ก่อนและหลังการแก้ของคุณ — นั่นคือ steering ที่ทำงาน commit ไฟล์พื้นฐานที่แก้แล้วและ code-style.md บน branch

สรุปประเด็นสำคัญ
  • Steering = markdown ใน .kiro/steering/ ที่ให้บริบทถาวรของโปรเจกต์แก่ Kiro
  • product.md / tech.md / structure.md โหลดทุกบทสนทนา
  • front-matter inclusion คุมการโหลด: always, fileMatch, manual, auto
  • #[[file:path]] ผูกคำแนะนำเข้ากับ source จริง; AGENTS.md รวมเสมอ
  • commit steering เข้า repo และรีวิวการแก้ — เป็นพฤติกรรมที่ทีมใช้ร่วมกัน
ลองทำ เพิ่ม .kiro/steering/code-style.md ด้วยกฎจริง 5 ข้อของทีม (การตั้งชื่อ, การจัดการ error, import) และตัวอย่าง before/after หนึ่งอัน สั่ง agent เขียนฟังก์ชันเล็ก ๆ แล้วเช็กว่าทำตามครบทั้งห้าข้อ
บทที่ 5

Agent Hooks

automation ตาม event

hook รันคำสั่ง shell หรือ prompt ให้ agent โดยอัตโนมัติเมื่อมีบางอย่างเกิดใน session ของคุณ hook เป็นไฟล์ JSON ใน .kiro/hooks/ และเริ่มทำงานเมื่อ session เริ่ม — ไม่ต้อง register เอง

ประเภทของ trigger

กลุ่มTriggers
ไฟล์ (IDE)PostFileCreate, PostFileSave, PostFileDelete
การรันPreToolUse / PostToolUse (Pre บล็อกได้), PromptSubmit (บล็อกได้)
LifecycleSessionStart (IDE), AgentSpawn (CLI), AgentStop
Task (IDE)PreTaskExecution / PostTaskExecution — รอบ ๆ task ของ spec
สำคัญ trigger ประเภทไฟล์ทำงานเฉพาะกับการเปลี่ยนที่ agent เป็นคนทำ — ไม่ใช่ตอนที่คุณแก้และเซฟไฟล์เองใน editor

รูปแบบไฟล์ hook

{
  "version": "v1",
  "hooks": [
    {
      "name": "Lint on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx)$",
      "action": { "type": "command", "command": "npx eslint --fix" },
      "timeout": 60
    }
  ]
}
ฟิลด์ความหมาย
triggerประเภท event, PascalCase
matcherregex ทางเลือกเพื่อกรองว่า event ไหนจะจุด hook
action.type"command" (รันคำสั่ง shell) หรือ "agent" (แทรก prompt)
timeoutวินาทีก่อน hook ถูกฆ่า (ค่าเริ่มต้น 60)

กรณีใช้งานที่พบบ่อย

  • รัน linter, formatter หรือ type check หลัง agent แก้ไฟล์
  • สร้าง test, docs หรือคำแปลอัตโนมัติเมื่อมีไฟล์ source ใหม่
  • บล็อก tool ด้วย PreToolUse จนกว่าจะครบเงื่อนไข
  • รันการตรวจคุณภาพก่อน agent จะปิดงาน

การสร้าง hook

ใน IDE: ปุ่ม + ใน Agent Hooks panel → "Ask Kiro to create a hook" → อธิบาย automation เป็นภาษาคน แล้ว Kiro เขียน JSON ให้ ใช้ชื่อไฟล์แบบ kebab-case (lint-on-save.json); hook ที่เกี่ยวข้องกันใส่ไฟล์เดียวกันได้

trigger จุดตรงไหนใน session

ในทางปฏิบัติ — สอง hook ที่ทีมมักปล่อยก่อน

.kiro/hooks/dev-guardrails.json 
{
  "version": "v1",
  "hooks": [
    {
      "name": "Format on save",
      "trigger": "PostFileSave",
      "matcher": "\\.(ts|tsx|js|jsx|json|css)$",
      "action": { "type": "command", "command": "npx prettier --write \"$KIRO_FILE\"" },
      "timeout": 30
    },
    {
      "name": "Scaffold a test for new source files",
      "trigger": "PostFileCreate",
      "matcher": "^src/.*(?<!\\.test)\\.ts$",
      "action": {
        "type": "agent",
        "command": "A new source file was just created at $KIRO_FILE. If it exports anything testable and no sibling *.test.ts exists, create one with a failing placeholder test and a TODO listing the cases to cover. Do not implement the tests."
      },
      "timeout": 120
    }
  ]
}

อันแรกเป็น action แบบ command — shell ล้วน กำหนดผลได้แน่นอน ปลอดภัย อันที่สองเป็น action แบบ agent — ส่ง prompt กลับให้ agent มันจึงอ่านไฟล์แล้วเขียน test stub ที่สมเหตุสมผลได้ ทั้งคู่ไม่บล็อก: ถ้า Prettier ล้มเหลว workflow ก็เดินต่อ ยังไม่มี PreToolUse จนกว่าทีมจะไว้ใจสองอันนี้

เป้าหมาย: เห็น hook จุดตอน agent แก้ — และยืนยันว่ามัน ไม่ จุดตอนคุณเซฟเอง

  1. ใน Agent Hooks panel คลิก + → "Ask Kiro to create a hook" และอธิบาย: run my formatter on TypeScript and JS files after the agent edits them
  2. เช็ค JSON ที่สร้างใน .kiro/hooks/: trigger ถูก (PostFileSave), matcher ที่ match แค่นามสกุล source, action แบบ command
  3. สั่ง agent: Add a small utility function to <ไฟล์ .ts บางไฟล์>, deliberately badly formatted.

  5. ตอนนี้แก้ไฟล์เดียวกันด้วยมือให้ format เละ ๆ แล้วเซฟเอง ยืนยันว่า hook ไม่ รัน — trigger ไฟล์มีไว้สำหรับการแก้ของ agent เท่านั้น

เสร็จเมื่อ คุณเห็น hook รันตอนขั้นที่ 4 และเงียบตอนขั้นที่ 5 commit hook JSON บน branch

สรุปประเด็นสำคัญ
  • Hooks = JSON ใน .kiro/hooks/; รันคำสั่งหรือ prompt ให้ agent ตาม event
  • trigger ครอบคลุมการเปลี่ยนไฟล์, การใช้ tool, lifecycle ของ session และ task ของ spec
  • trigger ไฟล์ตอบสนองต่อการแก้ของ agent เท่านั้น ไม่ใช่การเซฟเองของคุณ
  • PreToolUse และ PromptSubmit บล็อก ได้ — ทรงพลัง จึงต้องค่อย ๆ นำมาใช้
  • ใช้ regex ใน matcher เพื่อให้ hook เจาะจงแคบ ๆ
ลองทำ สร้าง hook PostFileSave ที่รัน formatter บน \\.(ts|js)$ สั่ง agent เพิ่มฟังก์ชัน แล้วยืนยันว่าไฟล์กลับมาถูก format โดยที่คุณไม่ได้แตะ
บทที่ 6

MCP — Model Context Protocol

MCP ทำอะไร

MCP คือโปรโตคอลที่ให้ Kiro คุยกับ server ภายนอกเพื่อใช้ tools, prompts และ resources เฉพาะทางที่ไม่ได้ฝังอยู่ในโมเดล — knowledge base ภายใน, ระบบ ticket, cloud API, การค้นเอกสาร ฯลฯ

AWS Documentation MCP server เป็น server แรกที่นิยม: ให้ agent เข้าถึงการค้นเอกสาร AWS โดยตรงและได้คำแนะนำที่อ้างอิงได้และเป็นปัจจุบัน แทนการเดาจากข้อมูล training

การจัดการและแก้ปัญหา

  • ดูสถานะการเชื่อมต่อในแท็บ MCP Servers; อ่าน log ในแท็บ Output
  • Kiro แสดงกล่องยืนยันก่อนใช้ install link โดยแสดงคำสั่งและ ชื่อ env var (ซ่อนค่า)
  • ชื่อ tool ต้อง match ^[a-zA-Z][a-zA-Z0-9_]*$ และสั้นกว่า 64 อักขระ ไม่งั้นจะเจอ validation error
ความปลอดภัย ติดตั้ง MCP server จากแหล่งที่ไว้ใจได้เท่านั้น — server รันโค้ดบนเครื่องคุณและเห็น context ที่ agent ส่งให้ได้ ตรวจแพ็กเกจ, pin เวอร์ชัน และอย่า commit secret

tool call ไหลยังไง

ในทางปฏิบัติ — mcp.json ระดับ workspace ที่ตรวจแล้ว

.kiro/settings/mcp.json (commit ไว้) 
{
  "mcpServers": {
    "aws-docs": {
      "command": "uvx",
      "args": ["awslabs.aws-documentation-mcp-server@1.0.4"],
      "disabled": false,
      "autoApprove": ["search_documentation", "read_documentation"]
    },
    "eng-wiki": {
      "url": "https://mcp.internal.acme.dev/wiki",
      "headers": { "Authorization": "Bearer ${ENG_WIKI_TOKEN}" },
      "disabled": false
    }
  }
}

ข้อตกลงของทีม: server AWS pin ที่ 1.0.4 ไม่ใช่ @latest การเปลี่ยนจาก upstream จึงแก้พฤติกรรมไม่ได้โดยไม่ผ่าน PR เฉพาะสอง tool อ่านอย่างเดียวเท่านั้นที่ auto-approve; server wiki ภายในเป็น HTTP, token มาจาก environment variable (ไม่เคย commit) และไม่มี tool ไหน auto-approve เพราะมันถูกสั่งให้เขียนหน้าได้

🧪 Lab 6 — ให้ agent เข้าถึงเอกสาร AWS สด

เป้าหมาย: เห็น agent เรียก MCP tool แทนการเดาจากข้อมูล training

  1. เปิด workspace MCP config (Command palette → "Kiro: Open workspace MCP config (JSON)")
  2. เพิ่ม server aws-docs จากตัวอย่างข้างบน (pin เวอร์ชันจริงถ้าหาได้; ไม่งั้น @latest สำหรับ lab)
  3. เช็คว่าแท็บ MCP Servers แสดงว่าเชื่อมต่อแล้ว ถ้าไม่ ให้อ่านแท็บ Output
  4. ถาม agent คำถามที่ต้องใช้รายละเอียด AWS ปัจจุบัน เช่น What are the current default quotas for Amazon SQS FIFO queues, with a source link?
  5. ดูมันเรียก search_documentation / read_documentation แล้วตอบพร้อมอ้างอิง ถามเรื่องเดิมโดยตั้ง server เป็น disabled: true แล้วเทียบความมั่นใจ

เสร็จเมื่อ คุณมีคำตอบหนึ่งอันที่มี MCP tool call พร้อมลิงก์เอกสารหนุน และเห็นความต่างเมื่อปิด server

สรุปประเด็นสำคัญ
  • MCP เชื่อม Kiro กับเครื่องมือ / ข้อมูลภายนอกผ่าน mcp.json ระดับ workspace, user หรือ agent
  • server แบบ Local (stdio) และ remote (HTTP/SSE) ใช้ได้ทุกที่ยกเว้น Mobile
  • disabled ปิด server; autoApprove ควรมีแค่ tool แบบอ่านอย่างเดียว
  • commit mcp.json ระดับ workspace ที่ตรวจแล้ว เพื่อให้ทีมใช้ server ชุดเดียวกัน
  • มอง MCP server เป็นความเสี่ยง supply-chain: แหล่งที่ไว้ใจ, pin เวอร์ชัน, secret ผ่าน env
ลองทำ เพิ่ม AWS Documentation MCP server ลงใน mcp.json ระดับ workspace ถาม agent คำถามที่ต้องใช้เอกสาร AWS ปัจจุบัน แล้วดูมันเรียก tool แทนการเดา

Kiro Powers

Power คืออะไร

Power คือแพ็กเกจที่ติดตั้งได้ ซึ่งรวมทุกอย่างที่ agent ต้องใช้เพื่อทำงานกับเครื่องมือหรือ framework เฉพาะได้ดี:

ส่วนให้อะไร

dev.kiro/ส่วนขยายเฉพาะ Kiro เช่นไฟล์ steering

Powers สร้างบน Agent Plugins specification — มาตรฐานเปิดที่ไม่ผูกกับเจ้าใดเจ้าหนึ่ง หนุนโดย Amazon, Cursor, Microsoft, OpenAI และ Vercel — Power จึงไม่ล็อกกับ Kiro

สองปัญหาที่ Powers แก้

  • ความเชี่ยวชาญกระจัดกระจายในเอกสาร การทำให้ agent เข้าใจ pattern ของ framework จริง ๆ ต้องอ่านเอกสารและปรับ prompt แบบลองผิดลองถูก ซ้ำทุกเครื่องมือใหม่ Power ส่งความเชี่ยวชาญนั้นให้ล่วงหน้า — และมาจากผู้สร้างเครื่องมือเอง ไม่ใช่การตีความของบุคคลที่สาม
  • context ท่วมท้น การต่อ MCP server มากขึ้นไม่ได้ช่วยอัตโนมัติ; context ไม่มีโครงสร้างมากไปทำให้ agent ช้าและคุณภาพตก Powers แก้ด้วย intelligent loading

Intelligent loading

แทนที่จะโหลด context ของทุก Power ที่ติดตั้งไว้ตั้งแต่ต้น (ซึ่งอาจเกิน 50,000 tokens) Kiro จับคู่ คำอธิบายงาน ของคุณกับ Power ที่ติดตั้งไว้ แล้วโหลดเฉพาะตัวที่เกี่ยว พูดถึง "payment" แล้ว Stripe Power เปิดใช้; เปลี่ยนไปทำงานฐานข้อมูลแล้ว Supabase โหลดแทน คุณไม่ต้องสลับ Power เอง

การติดตั้งและจัดการ

  • ติดตั้งคลิกเดียวจาก IDE / CLI หรือ registry ที่คัดสรรแล้วที่ kiro.dev/powers
  • นำเข้า Power ของชุมชนด้วยการวาง URL ของ GitHub repo
  • Power ที่ sync กับ cloud แสดงใน Settings → Powers ใน Kiro Web และ sync ไป IDE เวอร์ชันใหม่ ๆ

Power จาก launch partner

Datadog · Dynatrace · Figma · Neon · Netlify · Postman · Supabase · Stripe · AWS Aurora — แต่ละตัวสร้างโดยบริษัทเจ้าของเครื่องมือ ตัวอย่าง:

  • Figma — ดึง design spec, ใช้ Code Connect แมป design เข้ากับ component ที่มีอยู่, ใช้ design token แทนค่า hard-code, ตรวจว่างานที่สร้างตรงกับ design
  • Supabase — บังคับ Row Level Security ทุกตาราง, สร้าง TypeScript type จาก schema, ใช้ pattern การ auth ที่ถูกต้อง, รีวิว migration หาปัญหาความปลอดภัย

🧪 Lab 7 — ดู Power เปิดใช้เอง

เป้าหมาย: ยืนยันว่า intelligent loading ทำงาน — Power ที่ถูกต้องเปิดเอง

  1. จาก kiro.dev/powers หรือใน IDE ติดตั้ง Power หนึ่งอันที่ตรงกับ stack ของคุณ (Supabase, AWS Aurora, Postman, Netlify…)
  2. เริ่มงานที่ ไม่เกี่ยว กับมัน (เช่น "rename this variable everywhere") สังเกตตัวบ่งชี้ Powers — Power ควรว่างอยู่
  3. เริ่มงานที่อยู่ในโดเมนของมันเต็ม ๆ (สำหรับ Supabase: "add a row-level-security policy so users only read their own orders") ดูตัวบ่งชี้แสดงว่า Power เปิดใช้อยู่
  4. ตรวจ output: มันสะท้อนคำแนะนำของ Power ไหม (เช่น RLS policy จริง, type ที่ generate) แทนคำแนะนำทั่วไป?
  5. ทางเลือก: ร่าง plugin.json สำหรับสิ่งหนึ่งที่ทีมอธิบายซ้ำตลอด (service scaffold, convention การ log) ไม่ต้องเผยแพร่ — แค่ออกแบบรายการ keyword

เสร็จเมื่อ คุณเห็นตัวบ่งชี้ Powers เปลี่ยนระหว่างงานที่ไม่เกี่ยวกับงานในโดเมน และ output ในโดเมนใช้ Power อย่างชัดเจน

สรุปประเด็นสำคัญ
  • Power รวม skills/ + mcp.json (ทางเลือก) + steering ใน dev.kiro/ อธิบายด้วย plugin.json
  • สร้างบน Agent Plugins spec แบบเปิด — ย้ายข้ามเจ้าได้
  • intelligent loading ดึงเฉพาะ Power ที่เกี่ยวกับงานปัจจุบัน
  • ติดตั้งจาก kiro.dev/powers, IDE หรือ URL GitHub ของชุมชน
  • แพ็กมาตรฐานของทีม + MCP ภายในเป็น Power ส่วนตัวได้
ลองทำ ติดตั้ง Power ที่เกี่ยวกับ stack ของคุณ (เช่น Supabase หรือ AWS Aurora) เริ่มงานที่พูดถึงเรื่องของมัน แล้วยืนยันว่า Power เปิดใช้เอง — ดูตัวบ่งชี้ Powers ใน editor

แผนนำไปใช้ในทีม

นี่คือแผน ของเรา — ทีมเล็ก (2–5 คน) บน GitHub ที่ส่งงาน TypeScript/Node/React, Python และ JVM/.NET/Go บน AWS ไม่ใช่เอกสาร Kiro ปรับแก้เมื่อเราเรียนรู้เพิ่ม

สัปดาห์ที่ 1 — ทุกคนเข้าร่วม

  • ทั้งทีมคือ pilot เราเล็กพอที่การมีเฟส "เริ่มบางคนก่อน" จะเพิ่มแต่ค่า coordination
  • ทุกคนติดตั้ง IDE, ลงชื่อเข้าใช้, นำเข้าการตั้งค่า VS Code
  • เลือก repo ที่ใช้งานจริงหนึ่งอัน สั่ง "Generate Steering Docs" แล้วแก้ product.md / tech.md / structure.md ใน PR จนกว่าจะตรงความจริง แล้ว merge — steering เข้าผ่านการรีวิวตั้งแต่วันแรก

steering สำหรับทีมหลายภาษา

จัดโครงสร้าง steering ให้กฎของแต่ละภาษาโหลดเฉพาะเมื่อเกี่ยวข้อง:

ไฟล์โหมดเนื้อหา
security.md, structure.md, code-review.mdalwaysกฎข้ามทีม ทำให้สั้น — กิน token ทุกเทิร์น
code-style-ts.mdfileMatch **/*.{ts,tsx}การตั้งชื่อ, การจัดการ error, React patterns
code-style-python.mdfileMatch **/*.pytyping, packaging, กฎ lint
code-style-jvm.mdfileMatch **/*.{java,kt,cs,go}convention แยกตามภาษา
infra-aws.mdfileMatch infra/**, **/*.tftagging, IAM least-privilege, กฎ region

แต่ละไฟล์เก็บกฎที่เราเถียงกันในรีวิวอยู่แล้ว พร้อมตัวอย่าง before/after หนึ่งอันและ เหตุผล ของกฎ

เมื่อไรควรใช้ spec — ตาม ticket

หลักคิดของเรา ถ้ามี ticket ก็มีโฟลเดอร์ spec ตั้งชื่อตาม ticket: .kiro/specs/PROJ-1234-checkout-retry/ ไม่มี ticket และงานเล็กจิ๋ว? vibe ได้
  • ticket ฟีเจอร์ → Feature Spec อ่านและกระชับ requirements.md ก่อนอนุมัติ design
  • ticket บั๊ก → Bugfix Spec บันทึกว่าอะไรต้อง ไม่ เปลี่ยน — การกัน regression ที่ผู้รีวิวต้องการ
  • commit โฟลเดอร์ spec ใน PR เดียวกับโค้ด เพื่อให้เหตุผลไปพร้อมกับการเปลี่ยน

วินัยด้านต้นทุน

  • ทำ steering โหมด always ให้สั้น; ผลักที่เหลือไป fileMatch / manual
  • ปล่อยให้ compaction จัดการ session ยาว ๆ แทนการเริ่มใหม่
  • Supervised เป็นค่าเริ่มต้น การรัน Autopilot ที่พลาดเผาทั้ง run บวกเวลารีวิวของคุณ ย้ายงานประเภทหนึ่งไป Autopilot เฉพาะเมื่อมันน่าเบื่อเพราะเชื่อถือได้แล้ว
  • ใช้ Quick Spec เท่าที่จำเป็น — ด่านอนุมัติคือสิ่งที่กันการเขียนใหม่ราคาแพง

guardrails — โค้ดที่อ่อนไหว

  • .kiroignore ตั้งแต่วันแรก: secret, .env*, fixture ข้อมูลลูกค้า, อะไรก็ตามที่อยู่ในขอบเขต compliance, โฟลเดอร์ generate ขนาดใหญ่
  • Permissions — จำกัดสิ่งที่ agent อ่านและรันได้; default-deny นอก repo ที่ทำงานอยู่
  • MCP: เฉพาะ server ที่รีวิวแล้ว, pin เวอร์ชัน, ใน mcp.json ระดับ workspace ที่ commit อันเดียว autoApprove เฉพาะ tool อ่านอย่างเดียว — ห้ามตัวที่เขียนหรือเรียกออกนอก
  • ระวัง การส่งต่อไป Web / Mobile — มันส่ง context ออกนอกเครื่อง เก็บงานอ่อนไหวไว้ใน IDE
  • Hooks: ไม่บล็อกเท่านั้นจนกว่าจะไว้ใจ ยังไม่ใช้ PreToolUse / PromptSubmit แบบบล็อกในช่วงแรก

governance ที่ต้องเขียนไว้ก่อน bolt แรก

AI-DLC เอา control ของ SDLC ที่เราพึ่งพาออกเร็วกว่าที่สร้างของมาแทน (บทที่ 0) พวกนี้เป็นของเราที่ต้องเพิ่ม และเขียนไว้ล่วงหน้าครั้งเดียวถูกกว่าไปยัดใส่ทีมที่วิ่งด้วยความเร็ว bolt แล้วเยอะ:

  • named approver ต่อหนึ่ง unit of work คนหนึ่งเซ็นอนุมัติ plan ที่ AI ร่าง — และ ไม่ใช่ คนที่สั่ง plan ออกมา บันทึกไว้ ไม่ใช่แค่พูดใน mob
  • review standard หนึ่งหน้า ผู้อนุมัติเช็คอะไรจริง ๆ: ระดับความลับข้อมูลที่แตะ, blast radius, เส้นทาง rollback, ส่วนที่เบี่ยงจาก steering files ถ้าไม่มี checklist การเซ็นอนุมัติ "เสื่อมเป็นการคลิกอัตโนมัติภายในสัปดาห์เดียว"
  • acceptance tests เป็นเกณฑ์ออกของ Inception Inception ไม่จบเมื่อมี requirements — จบเมื่อ test ที่คนรีวิวแล้วซึ่งจะตัดสิน Construction มีอยู่ agent ลงมือทำโดยเทียบเกณฑ์ที่มันไม่ได้ตั้งเอง (ปิดปัญหา self-grading)
  • หนึ่ง change ticket ต่อหนึ่ง unit of work รันทุก unit ผ่าน change process เดิม; artifact trail ที่ spec สร้างกลายเป็นหลักฐานของ ticket bolt ย่นเวลาพัฒนา ไม่ได้ยกเว้น change control
  • agent evals ก่อนขยายจากทีมเดียวไปหลายทีม ทีม pilot ครอบ eval harness ที่ขาดด้วยความใส่ใจได้ ห้าทีมทำไม่ได้ และตอนนั้นโค้ดที่ agent เขียนก็เกินกำลังคนอ่านแล้ว
  • track defect-escape rate คู่กับ cycle time ใน retro เร็ว 10 เท่าพร้อม escaped defect 3 เท่า ไม่ใช่เร็วขึ้น
  • pilot บน service ภายในที่ blast radius ต่ำ — ไม่ใช่ เส้นทางจ่ายเงิน — เพื่อให้ bolt ที่พลาดราคาเท่ากับความอาย ไม่ใช่รายงานเหตุการณ์

security control ที่วิ่งด้วยความเร็ว bolt

โค้ดที่พิมพ์มือไม่เคยถูก scanner จำกัดความเร็ว — คนพิมพ์ไม่ทัน SAST job ที่รันกลางคืน ภายใต้ AI-DLC สมมติฐานนั้นหายไป: ความเร็วถูกจำกัดด้วยกำลัง review, security และ governance เท่านั้น ถ้า scan รันเป็น cron กลางคืนแต่ agent ส่งงานทุกชั่วโมง ช่องว่างนั้น คือ หน้าต่างที่เปิดช่องโหว่ security ต้องวิ่งด้วยจังหวะเดียวกับ bolt

failure mode ที่ AI-DLC เพิ่มขึ้นมาจาก appsec ปกติ — เรียกชื่อไว้ให้ pilot เฝ้าระวัง:

  • โค้ดที่ผ่าน lint แต่ผิด syntax สะอาด ดูสมเหตุผล แต่มี default ที่ไม่ปลอดภัยหรือ logic flaw ซ่อนอยู่ การวิเคราะห์ครั้งหนึ่งนับได้ 4,241 CWE instance ในชุดไฟล์ที่ AI สร้าง
  • dependency hallucination ราว 20% ของ package ที่ AI แนะนำชี้ไปที่ package ที่ไม่มีอยู่จริง ผู้โจมตีจดชื่อพวกนั้นไว้แล้วรอ — "slopsquatting" agent เลือก dependency โดยข้ามขั้นตอนที่คนเคยตรวจ
  • secret รั่วเร็วขึ้น 4 ใน 5 ของ secret ที่ตรวจยืนยันแล้วซึ่งพบใน public repo เกี่ยวกับ AI — key ที่วางลงใน prompt แล้ว commit ไปพร้อมโค้ดที่ generate
  • หนึ่ง misconfig หลาย deploy bucket ที่เป็น public หรือ IAM role ที่กว้างเกินใน IaC template ที่ generate ถูกทำซ้ำในทุก environment ที่ agent แตะ ก่อนใครจะทันสังเกต
  • agent ใน pipeline มีสิทธิ์เกิน มันต้องมี credential เพื่อ build, test และ deploy ถ้ากว้างเกิน agent ที่ hallucinate หรือถูกยึดก็สร้างความเสียหายจริงทั่ว environment
  • security config ที่ดูถูกแต่ผิด IAM policy หรือ security-group rule ที่อ่านแล้วดูถูกต้อง แต่เงียบ ๆ อนุญาตมากกว่าที่ตั้งใจ
ทำไม "ทุก scan ผ่าน" ยังไม่พอ

agent สร้าง microservice เลือก base image ที่มี CVE ที่รู้กันอยู่ ตั้ง load balancer แบบ public แนบ service account ที่อ่าน data store ของ production ได้ แล้วส่งผ่าน pipeline อัตโนมัติ แต่ละ artifact ผ่าน scan แคบ ๆ ของตัวเอง แต่ การรวมกัน — เปิดสู่อินเทอร์เน็ต + มีช่องโหว่ + สิทธิ์เกิน + ห่างข้อมูลอ่อนไหวแค่ก้าวเดียว — คือ attack path ระดับวิกฤต และเห็นได้ก็ต่อเมื่อมองโค้ด, cloud, identity และ data พร้อมกัน

สิ่งที่เราวางไว้สำหรับ pilot:

  • scan ทุก stage ที่ agent แตะ ด้วยจังหวะของมัน SAST, SCA, secrets, IaC และ sensitive-data scan ใน IDE, ตอน PR, ใน CI และต่อเนื่องใน production — ไม่ใช่แค่กลางคืน
  • least-privilege ที่ตัว agent เอง credential ของ CI/CD และ cloud ที่ scope แคบ พร้อมวิธีดูว่าแต่ละ agent ทำอะไรได้ และ กำลังทำอะไร คือกฎ .kiroignore + permissions ข้างบน ขยายมาถึง pipeline
  • triage ด้วย exploitability ไม่ใช่จำนวน finding เป็นแค่ทฤษฎีจนกว่าจะรู้ว่าโค้ด deploy แล้วไหม, เปิดสู่อินเทอร์เน็ตไหม, ถือ identity อะไร, แตะข้อมูลอะไรได้ เมื่อ agent สร้าง finding วันละหลายร้อย บริบทนั้นคือสิ่งที่ทำให้คิวยังไหวอยู่
  • เก็บ trail ของ provenance ต้องย้อนจาก artifact ที่ deploy กลับไปที่ repo, agent ที่สร้าง, คนที่อนุมัติ และ steering / policy ที่กำกับได้ NIST AI RMF, EU AI Act และ SOC 2 Type II ต่างต้องการ audit trail แบบ "เครื่องเขียน vs คนอนุมัติ" — และ artifact ที่มีโครงสร้างของ AI-DLC (spec, plan, test, config) ให้เราแบบนั้นโดยปริยาย ถ้าเราเก็บมันไว้
  • ดันการตัดสินใจที่กำหนด attack surface เข้าไปใน Inception ใช้ cloud service ไหน, ข้อมูลอะไร, identity model แบบไหน — ตัดสินและ review ที่ Inception การ review security ตรงนั้นตัดความเสี่ยงทั้งกลุ่มออกก่อนที่โค้ดจะมี
ที่มา threat และ control ในส่วนนี้อิงตาม Wiz, "AI-Driven Development Lifecycle (AI-DLC)" — บทอ่านที่เน้นด้าน security ของ methodology นี้

  • AWS Documentation MCP server ใน mcp.json ที่ใช้ร่วมกัน — จุดร่วมของทุก stack ของเรา
  • ติดตั้ง Power AWS Aurora และ partner Power อื่นที่ตรงกับบริการที่เราพึ่งพา
  • เมื่อ steering นิ่งแล้ว แพ็ก convention ของเรา + MCP ภายในเป็น Power ส่วนตัว เพื่อให้ agent ของคนใหม่มีประโยชน์ตั้งแต่วันแรก

แต่ละ stage สร้าง headless agent CLI — Kiro, Claude Code หรือแบบอื่น — ขึ้นมาใน Bedrock AgentCore microVM เฉพาะของมันเอง มี filesystem ของตัวเอง คุยกับ Neptune และ DynamoDB ผ่าน stdio MCP server เท่านั้น และต่างจาก CLI harness ตรงที่ agent ไม่แตะ git เลย: engine เป็นคน clone repo, เป็นเจ้าของ branch aidlc/<title-slug> และ commit ทุกครั้งที่ stage จบ — สำเร็จ, park หรือ fail ก็ตาม

เก็บอะไรไว้จริง ๆ

graph ของ Neptune ไม่ใช่ document store ทั่วไป — มันมีความเห็นว่าโปรเจกต์ซอฟต์แวร์ประกอบด้วยอะไรบ้าง vertex แบบ authored มาจากงานของคุณตรง ๆ: Project, Intent, Artifact (markdown ต้นฉบับที่ stage ผลิตออกมา) พร้อม snapshot ArtifactVersion ที่แก้ไขไม่ได้, Question, Steering (การแก้ทิศทางของคุณ), Discussion, PullRequest และ node TeamKnowledge / LearningRule ที่ใช้ซ้ำได้ vertex แบบ derived ถูกดึงออกมาอัตโนมัติจากการ parse markdown นั้น: Section จาก heading, Requirement, Story (พร้อม persona และ acceptance criteria), Persona, Component, Decision, Contract และ UnitOfWork

edge แบ่งเป็นสามกลุ่ม — ownership (CONTAINS, HAS_SECTION, …), artifact flow (PRODUCES, CONSUMES, DEPENDS_ON, …) และ traceability จริง ๆ (COVERS, IMPLEMENTS, FOR_PERSONA, …) — ซึ่งทำให้ "โค้ดไหนตอบ requirement นี้" เป็น graph query แทนที่จะเป็นการ grep ทุก write มี provenance กำกับ: execution ไหน, stage instance ไหน, parallel lane ไหน และเมื่อไหร่

execution model

intent หนึ่งเดินผ่าน DRAFT → CREATED → RUNNING ↔ WAITING → SUCCEEDED / FAILED / CANCELLED WAITING แปลว่าจอดอยู่ที่ human gate — หลังจากช่วง grace period สั้น ๆ session เองจะหยุด run ที่รอคุณอยู่จึงใช้ compute เป็นศูนย์ และกลับมาทำงานต่อพร้อม context การสนทนาเต็มทันทีที่คุณตอบ

หลังจาก unit "walking skeleton" ตัวแรกได้รับอนุมัติ unit of work ที่เป็นอิสระต่อกันจะ fan out ไปเป็น AgentCore session ขนานกัน แต่ละอันมี branch ของตัวเอง unit ที่ fail จะหยุดแล้วถามแทนที่จะไล่พังต่อ fan-in คือการ merge แบบเรียงตาม dependency กลับเข้า branch ของ intent คุณ course-correct คำตอบที่ gate, แก้ decision ก่อนหน้า, rewind กลับไป stage ไหนก็ได้พร้อมคำแนะนำใหม่ หรือ retry ตรง ๆ ก็ได้ — ทุก action พวกนี้ถูกเติมเข้าไปใน timeline ที่ตรวจสอบได้เต็มรูปแบบและแก้ไขย้อนหลังไม่ได้

real-time collaboration ในเชิงกลไก

ระบบ sync สองตัวทำงานนี้: WebSocket channel กระจายความคืบหน้าของ agent และ discussion ส่วน Yjs (CRDT) จัดการแก้ spec พร้อมกันหลายคน แต่ละคนมีสำเนาของตัวเองที่ merge อัตโนมัติ — แก้บรรทัดเดียวกันพร้อมกันทั้งสองฝั่งถูกเก็บไว้ ไม่ใช่ last-write-wins — และทุกคนเห็น cursor ของกันและกันพร้อม label ชื่อ เหมือน doc ที่แชร์กัน

การเข้าถึงผูกกับ session: HMAC-signed token อยู่ได้ 10 นาที ดังนั้นเอาคนออกจาก project ไม่ได้ตัดการเชื่อมต่อทันที — connection ที่เปิดค้างไว้ยังใช้ได้จนหมดอายุ token ที่เหลือก่อน server จะปิดมัน discussion เป็นแบบ thread เปิดให้สมาชิกทุกคน; มีแค่ Owner กับ Admin ที่ redact ข้อความได้

Git และ tracker integration

สองแกนที่แยกจากกัน: code host (GitHub, GitLab, Bitbucket) สำหรับ clone และเปิด PR/MR และ issue tracker (GitHub Issues, GitLab Issues, Jira Cloud) สำหรับเริ่ม intent จาก ticket ที่มีอยู่แล้ว — "เลือก issue ก็ seed intent" ด้วย title, body และ comment ของมันเป็น prompt admin ลงทะเบียน OAuth app ครั้งเดียวต่อ provider จากนั้น user แต่ละคนเชื่อม account ของตัวเอง (GitHub ขอ scope repo, workflow, read:user; scope api ของ GitLab ครอบคลุม repo write รวม CI config; token refresh อัตโนมัติ) แต่ละ project เลือก auth ของตัวเองอิสระต่อกัน — ทีมหนึ่งอยู่บน GitHub อีกทีมอยู่บน GitLab ก็ได้

delivery มีสองโหมดเหมือน engine ใน Module 0: Intent PR (engine merge ทุก unit เข้า branch ของ intent แล้วเปิด PR เดียวตอนจบ) หรือ PR ต่อ unit (draft review ต่อ repository เลื่อนเป็น mergeable ตามลำดับ dependency) agent ยังไม่ถือ git credential เลย — engine เป็นเจ้าของ branch, commit และ PR

  1. ล็อกอินด้วย Cognito credentials ที่ URL ของ CloudFront ที่ deploy ไว้ แล้วสร้าง project — repo หนึ่ง, code host หนึ่ง (GitHub หรือ GitLab), เชื่อม issue tracker ได้ถ้าต้องการ
  2. สร้าง intent: ชื่อเรื่อง (ตั้งชื่อ branch aidlc/<title> ด้วย), prompt แบบ free-form บอกว่าอะไร/ใคร/ข้อจำกัด/ขอบเขต, scope (feature, bugfix, …) และจะรันด้วย agent CLI ตัวไหน
  3. เริ่มมัน orchestrator checkout repo, สร้าง branch แล้ว pipeline bar เริ่มเติมเต็ม พร้อม activity panel สตรีม output ของ agent แบบ live
  4. ตอบคำถามที่ agent ถามมาเรื่อย ๆ — เป็นปุ่มที่มีโครงสร้างบน workbench ไม่ใช่ chat ที่ต้องตีความเอง — แล้วอนุมัติหรือปรับทิศทางในแต่ละ stage review
  5. อนุมัติ unit walking-skeleton ที่เหลือ fan out ขนานกัน ดู stage duration, token ที่ใช้ และ cost ต่อ stage ใน observability view แล้วสืบ requirement ไหนก็ได้ลงไปถึง unit ที่ implement มันใน graph
  6. execution จบด้วย pull request รีวิวโค้ดคู่กับ artifact และ metric ของ intent เอง — ไม่ใช่ diff เปล่า ๆ
🧪 Lab 9 — วาง feature จริงลงบน AIDLC Collaborative

เป้าหมาย: ตัดสินใจบนกระดาษว่าเอนจิน hosted แบบหลายผู้ใช้คุ้มสำหรับทีมคุณไหม — ใช้ ticket จริงหนึ่งอันเป็นเคสทดสอบ ไม่ใช่สมมติ

  1. เลือก feature หรือ bugfix จริงหนึ่งอันที่ทีมคุณเพิ่ง ship หรือกำลังทำอยู่ บน repo จริงของคุณ
  2. อ่านหน้า architecture และ execution model ของแพลตฟอร์ม
  3. ร่าง ticket นั้นเป็น intent: scope อะไร (feature/bugfix), prompt จะเขียนว่าอะไร, จะแตกเป็น unit of work กี่อัน และ gate ทั้งสอง (อนุมัติ fan-out, รีวิว PR) จะอยู่ตรงไหน
  4. ตัดสินใจ delivery mode ให้มัน — PR เดียวจากทั้ง intent หรือ PR ต่อ unit — แล้วบอกว่าทำไม
  5. บอกคำถามด้าน traceability หนึ่งข้อเกี่ยวกับ ticket นั้นที่ aidlc-docs/ markdown trail ปัจจุบันของทีมคุณ (Module 0) ตอบเร็ว ๆ ไม่ได้ แต่ graph query ตอบได้
  6. เขียนหนึ่งย่อหน้า: adopt, pilot บน repo เดียว หรือข้ามไปก่อน — พร้อมสิ่งเดียวที่จะเปลี่ยนคำตอบของคุณ (ขนาดทีม, ค่าใช้จ่าย AWS, จำนวน repo)

เสร็จเมื่อ คุณมีข้อเสนอ go / pilot / no-go เป็นลายลักษณ์อักษรให้ทีม อ้างอิงจาก ticket ที่เดินผ่านมา

สรุปประเด็นสำคัญ
  • AIDLC Collaborative คือ reference implementation อีกตัวของ AI-DLC จาก AWS — วิธีการเดียวกัน แต่ hosted ให้หลายคนและหลาย agent ทำงาน intent เดียวกันพร้อมกันได้
  • มัน import stage/persona/sensor ต้นทางมาแบบไม่แก้ไข รันใน Bedrock AgentCore session ที่แยกจากกัน; engine เป็นเจ้าของ git ไม่ใช่ agent
  • structured data อยู่ใน graph database (Neptune) แทน markdown ได้ traceability สองทางและ context ของ agent ที่มีขอบเขต แม้โปรเจกต์ใหญ่ขึ้น
  • run ที่ park (WAITING) ใช้ compute เป็นศูนย์; steering (course-correct / revise / rewind / retry) เป็นแบบ append-only ตรวจสอบได้เต็มรูปแบบ
  • phase และ gate เดียวกับ Module 0 — นี่คือการตัดสินใจเรื่อง hosting ไม่ใช่การเปลี่ยนวิธีการ หยิบมาใช้ตอน pilot โตเกินวิศวกรคนเดียวบน CLI เดียว
