คู่มือแล็บ

สิบแล็บ บทละหนึ่งอัน บวก capstone ที่รันทั้ง loop จบ end to end ทำแล็บประจำบท หลัง อ่านบทที่ตรงกัน — แต่ละอันเปลี่ยนแนวคิดของบทนั้นให้เป็นของจริงบนเครื่องคุณ และต่อยอดกัน: Lab 1 หาปัญหาในไฟล์ steering, Lab 4 แก้มัน ต่อ ๆ กันไป Lab 10 ร้อยทุกอย่างเข้าด้วยกัน: หนึ่งฟีเจอร์จาก intent ถึงโค้ดที่รีวิวแล้ว ผ่านทุกด่านของ AI-DLC

สิ่งที่ต้องมีสำหรับแล็บส่วนใหญ่: ติดตั้ง Kiro IDE และลงชื่อเข้าใช้แล้ว และมีโปรเจกต์ จริง หนึ่งอันที่คุณรู้จักดี (ไม่ใช่โฟลเดอร์เปล่า) Lab 0 ไม่ต้องมีเครื่องมือ; Lab 8 ทำกับทีมได้ผลดีที่สุด; Lab 9 เป็นแบบฝึกบนกระดาษกับ ticket จริงหนึ่งอัน — ไม่ต้องใช้เครื่องมือ; Lab 10 ใช้ Claude Code กับโฟลเดอร์เปล่า — ไม่ต้องใช้ Kiro IDE

ติ๊กแล็บเมื่อทำเสร็จ — ความคืบหน้าบันทึกไว้บนเบราว์เซอร์นี้ และแสดงที่หน้าแรก และข้าง ๆ แต่ละบทในคอร์ส

บทที่ 0 · Lab 0

แมป PR จริงลงบน AI-DLC

⏱ 20–30 นาที 🔧 ไม่ต้องมีเครื่องมือ — PR ล่าสุดที่อ่านได้ + ไฟล์ scratch 🎯 รู้สึกว่าเส้นแบ่ง Inception / Construction อยู่ตรงไหน และหาหนึ่งการตัดสินใจที่หลุดไปโผล่ตอน code review

ขั้นตอน

  1. เปิด pull request ที่ไม่เล็กจิ๋วอันล่าสุดที่คุณรีวิวหรือเขียน อ่านคำอธิบายและกวาดตา diff
  2. ในไฟล์ scratch ทำสามหัวข้อ: Inception (ตัดสินว่าจะสร้าง อะไร และกฎของมัน), Construction (สร้างยังไง), Operations (deploy / monitor)
  3. ใส่การตัดสินใจหรือการเปลี่ยนทุกอย่างจาก PR ลงในเฟสที่มัน ควร ถูกตกลง เช่น "export ให้แค่ admin" → Inception; "stream CSV" → Construction; "เพิ่ม metric export" → Operations
  4. วงกลมอันที่จริง ๆ แล้วถูกตัดสินใจ ระหว่าง review หรือใน follow-up fix commit สำหรับแต่ละอัน เขียนหนึ่งประโยคที่จะปิดเรื่องนั้นได้ใน Inception
  5. นับดู: comment รีวิวกี่อันจริง ๆ แล้วคือ "Inception ที่ขาด" ไม่ใช่ "คุณภาพโค้ดที่ขาด"

ผลลัพธ์ที่คาดหวัง

รายการสามคอลัมน์ อย่างน้อยหนึ่งการตัดสินใจที่วงไว้ และประโยค Inception หนึ่งประโยคของมัน ประโยคนั้นคือรูปทรงของ acceptance criteria แบบ EARS — คุณจะเขียนของจริงใน Lab 3

ถ้าติด

  • "ทุกอย่างดูเป็น Construction หมด" มองหาทางเลือกที่มีคนเห็นต่างได้: ใครมีสิทธิ์, มันทริกเกอร์เมื่อไร, ฟอร์แมตไหน, อะไรนับว่าเสร็จ นั่นคือ Inception
  • "ไม่มีการตัดสินใจหลุดเลย" อ่าน comment ใน PR อีกรอบ และ commit ตามหลังที่ข้อความว่า "fix", "actually", "ตามรีวิว" — มันซ่อนอยู่ตรงนั้น
บทที่ 1 · Lab 1

สัมผัสแรก — ติดตั้งและอ่าน steering

⏱ 20 นาที 🔧 Kiro IDE · repo จริงเล็ก ๆ · การตั้งค่า VS Code ของคุณ 🎯 ติดตั้ง Kiro และดูว่ามันอ่านโปรเจกต์คุณยังไง

ขั้นตอน

  1. ติดตั้ง Kiro IDE และลงชื่อเข้าใช้ด้วยบัญชีที่องค์กรใช้ เมื่อระบบถาม ให้ import การตั้งค่า VS Code
  2. เปิดโปรเจกต์จริงเล็ก ๆ ที่คุณรู้จักดี — ไม่ใช่โฟลเดอร์เปล่าใหม่
  3. สั่ง Generate Steering Docs (Agent Steering panel หรือ command palette) เปิด .kiro/steering/product.md, tech.md และ structure.md ที่สร้างใหม่
  4. อ่านทั้งสามไฟล์ ในแต่ละไฟล์ ทำเครื่องหมายหนึ่งข้อความที่ ผิดหรือคลุมเครือ เกี่ยวกับโปรเจกต์คุณ
  5. ในแชต (โหมด vibe) ถาม: Summarise what this project does and its main entry points. เทียบคำตอบกับความจริง

ผลลัพธ์ที่คาดหวัง

ไฟล์สามไฟล์บนดิสก์ และรายการอย่างน้อยสามอย่างที่ต้องแก้ในนั้น เก็บรายการนั้นไว้ — คุณจะแก้มันใน Lab 4

ถ้าติด

  • ไม่เจอ "Generate Steering Docs" ดูในส่วน Agent Steering ของ side panel หรือค้น command palette ด้วยคำว่า "steering"
  • ไฟล์ที่ generate มารู้สึกกว้าง ๆ ปกติ — ตัว generate ให้แค่ร่าง การทำให้มันตรงความจริงคือ Lab 4 พอดี
บทที่ 2 · Lab 2

context คือทุกอย่าง

⏱ 15–20 นาที 🔧 Kiro IDE · ไฟล์ที่ "เชื่อมโยงสิ่งต่าง ๆ" ในโปรเจกต์ · test suite ที่รันได้ 🎯 เห็นแบบวัดได้ว่าคุณภาพคำตอบขึ้นกับ context ที่คุณให้

ขั้นตอน

  1. เลือกไฟล์จริงที่เชื่อมโยงสิ่งต่าง ๆ เข้าด้วยกัน — จุดเริ่มของแอป, router, DI container
  2. ถามในโหมด vibe โดย ไม่มี context provider: What are the top 3 risks in this codebase's startup path?
  3. ถามใหม่ คำถามเดิม เพิ่ม: #file:<ไฟล์นั้น> #folder:<ไดเรกทอรีของมัน> #git diff
  4. รัน test เพื่อให้มี output ใน terminal แล้วถามครั้งที่สาม เพิ่ม #problems และ #terminal
  5. เทียบว่าแต่ละคำตอบเจาะจงและถูกต้องแค่ไหน เก็บ prompt ที่ดีที่สุดไว้เป็น template

ผลลัพธ์ที่คาดหวัง

คุณชี้ได้ว่าข้อความจริงข้อหนึ่งในคำตอบที่ 3 ที่คำตอบที่ 1 ตอบผิดหรือพลาดไปเลย

ถ้าติด

  • สามคำตอบดูเหมือนกันหมด คำถามอาจกว้างไป — ถามอะไรที่ไฟล์ที่อ้างถึงเป็นตัวกำหนดจริง ๆ
  • #terminal ว่าง รัน test suite (หรือคำสั่งอะไรก็ได้) ก่อน เพื่อให้มีประวัติให้ดึง
บทที่ 3 · Lab 3

รัน spec ถึงด่านแรก

⏱ 25–35 นาที 🔧 Kiro IDE · ฟีเจอร์เล็กจริง ๆ ที่ต้องใช้ 🎯 สัมผัสด่าน requirements และเขียน EARS จริง

ขั้นตอน

  1. เลือกฟีเจอร์เล็กที่ต้องใช้จริง — filter, export, field ในฟอร์ม
  2. เริ่ม Feature Spec ให้คำอธิบายหนึ่งหรือสองประโยค ไม่มากกว่านั้น
  3. เมื่อ Kiro สร้าง requirements.md ให้ หยุด ยังไม่อนุมัติ
  4. เขียน acceptance criteria อย่างน้อยสองข้อใหม่ให้เป็น EARS เข้ม (WHEN … THE SYSTEM SHALL …) เพิ่ม IF … THEN … หนึ่งข้อสำหรับ error case ที่ร่างพลาดไป
  5. อนุมัติ แล้วให้ Kiro สร้าง design.md อ่านมัน จดหนึ่งการตัดสินใจใน design ที่คุณคงไม่ได้คิดจะทำให้ชัดเอง

ผลลัพธ์ที่คาดหวัง

.kiro/specs/<ฟีเจอร์ของคุณ>/ มี requirements.md ที่คุณแก้ และ design.md ที่คุณอ่านแล้ว หยุดตรงนั้น — ไม่ต้อง implement

ถ้าติด

  • spec ไม่เริ่ม / ถามไม่จบ เช็คว่าเลือก "Feature" ไม่ใช่ "Bug" ถ้ายังถามไม่จบ แปลว่าคำอธิบายครอบคลุมมากไป — เลือกฟีเจอร์ที่เล็กกว่า
  • requirements ยาวมาก สาเหตุเดียวกัน — ลดขอบเขต หนึ่งฟีเจอร์ที่กลมกล่อมต่อหนึ่ง spec
บทที่ 4 · Lab 4

สอน Kiro หนึ่งกฎจริง

⏱ 25 นาที 🔧 Kiro IDE · ไฟล์พื้นฐานสามไฟล์จาก Lab 1 🎯 พิสูจน์ว่า steering เปลี่ยนพฤติกรรม และแก้ไฟล์พื้นฐาน

ขั้นตอน

  1. แก้ข้อความที่ผิด / คลุมเครือที่คุณเจอใน product.md, tech.md และ structure.md ใน Lab 1
  2. สร้าง .kiro/steering/code-style.md ด้วย inclusion: always และกฎจริง 5 ข้อที่ทีมเถียงกันในรีวิว อย่างน้อยสองข้อใส่ snippet before / after สั้น ๆ และเหตุผลหนึ่งบรรทัด
  3. ในแชตใหม่ ถาม: Write a function that fetches a user by id and returns a typed result.
  4. เช็ค output เทียบกฎทั้งห้า ถ้ามันฝ่าฝืนข้อไหน กระชับถ้อยคำของกฎนั้นแล้วลองใหม่
  5. เปลี่ยนกฎหนึ่งข้อเป็นตรงกันข้าม ถามใหม่ ยืนยันว่า output ทำตามกฎใหม่ แล้ว revert

ผลลัพธ์ที่คาดหวัง

prompt เดิมให้โค้ดที่ต่างกันและทำตามกฎ ก่อนและหลังการแก้ของคุณ — นั่นคือ steering ที่ทำงาน commit ไฟล์พื้นฐานที่แก้แล้วและ code-style.md บน branch

ถ้าติด

  • agent เพิกเฉยกฎข้อหนึ่งเรื่อย ๆ ทำให้เป็นรูปธรรม — กฎหนึ่งประโยค, snippet before/after หนึ่งอัน, "ทำไม" หนึ่งบรรทัด
  • กฎชนกับ autofix ของ linter จดไว้และปรับให้ตรงกัน — steering กับ lint ควรพูดตรงกัน ไม่งั้น output ของ agent จะเด้งไปมา
บทที่ 5 · Lab 5

ปล่อย hook format-on-save

⏱ 15–20 นาที 🔧 Kiro IDE · formatter บน PATH (prettier, black, gofmt…) 🎯 เห็น hook จุดตอน agent แก้ — และเงียบตอนคุณเซฟเอง

ขั้นตอน

  1. ใน Agent Hooks panel คลิก + → "Ask Kiro to create a hook" และอธิบาย: run my formatter on TypeScript and JS files after the agent edits them
  2. เช็ค JSON ที่สร้างใน .kiro/hooks/: trigger เป็น PostFileSave, matcher match แค่นามสกุล source ของคุณ, action เป็น command
  3. สั่ง agent: Add a small utility function to <ไฟล์ .ts บางไฟล์>, deliberately badly formatted.
  4. ยืนยันว่าไฟล์ที่เซฟกลับมาถูก format โดยที่คุณไม่ได้ทำอะไร
  5. ตอนนี้แก้ไฟล์เดียวกันด้วยมือให้ format เละ ๆ แล้วเซฟเอง ยืนยันว่า hook ไม่ รัน

ผลลัพธ์ที่คาดหวัง

hook รันตอนขั้นที่ 3 (agent แก้) และเงียบตอนขั้นที่ 5 (คุณเซฟ) commit hook JSON บน branch

ถ้าติด

  • hook ไม่รัน เช็คว่า regex ใน matcher match path ของไฟล์จริง ๆ และอ่านแท็บ Output หา error
  • "formatter not found" ใช้ npx <tool> หรือ path เต็มในคำสั่ง
บทที่ 6 · Lab 6

ให้ agent เข้าถึงเอกสาร AWS สด

⏱ 15 นาที 🔧 Kiro IDE · ติดตั้ง uvx · เข้าเน็ตได้ 🎯 เห็น agent เรียก MCP tool แทนการเดาจากข้อมูล training

ขั้นตอน

  1. เปิด workspace MCP config: command palette → "Kiro: Open workspace MCP config (JSON)"
  2. เพิ่ม server aws-docs: 
    "aws-docs": {
  "command": "uvx",
  "args": ["awslabs.aws-documentation-mcp-server@latest"],
  "disabled": false,
  "autoApprove": ["search_documentation", "read_documentation"]
}
  3. เช็คว่าแท็บ MCP Servers แสดงว่าเชื่อมต่อแล้ว ถ้าไม่ อ่านแท็บ Output
  4. ถามคำถามที่ต้องใช้รายละเอียด AWS ปัจจุบัน เช่น What are the current default quotas for Amazon SQS FIFO queues, with a source link?
  5. ดูมันเรียก search_documentation / read_documentation แล้วตั้ง "disabled": true ถามเรื่องเดิม แล้วเทียบ

ผลลัพธ์ที่คาดหวัง

คำตอบหนึ่งอันที่มี MCP tool call พร้อมลิงก์เอกสารหนุน และเห็นความต่างของความมั่นใจเมื่อปิด server

ถ้าติด

  • server ไม่เชื่อมต่อ ยืนยันว่าติดตั้ง uvx และอยู่บน PATH; แท็บ Output แสดงคำสั่ง launch และ error
  • agent ไม่เรียก tool ทำให้คำถามชัดเจนว่าต้องใช้เอกสารปัจจุบัน — "current default quota", "latest supported version", "ณ วันนี้"
บทที่ 7 · Lab 7

ดู Power เปิดใช้เอง

⏱ 15–20 นาที 🔧 Kiro IDE · Power หนึ่งอันที่เกี่ยวกับ stack ของคุณ 🎯 ยืนยันว่า intelligent loading ทำงาน — Power ที่ถูกต้องเปิดเอง

ขั้นตอน

  1. จาก kiro.dev/powers หรือใน IDE ติดตั้ง Power หนึ่งอันที่ตรงกับ stack ของคุณ (Supabase, AWS Aurora, Postman, Netlify…)
  2. เริ่มงานที่ ไม่เกี่ยว กับมัน (เช่น "rename this variable everywhere") เช็คตัวบ่งชี้ Powers — Power ควรว่างอยู่
  3. เริ่มงานที่อยู่ในโดเมนของมันเต็ม ๆ สำหรับ Supabase: add a row-level-security policy so users only read their own orders ดูตัวบ่งชี้แสดงว่า Power เปิดใช้อยู่
  4. ตรวจ output — มันสะท้อนคำแนะนำของ Power ไหม (RLS policy จริง, type ที่ generate) แทนคำแนะนำทั่วไป?
  5. ทางเลือก: ร่างรายการ keyword ของ plugin.json สำหรับสิ่งหนึ่งที่ทีมอธิบายซ้ำตลอด (service scaffold, convention การ log)

ผลลัพธ์ที่คาดหวัง

ตัวบ่งชี้ Powers เปลี่ยนระหว่างงานที่ไม่เกี่ยวกับงานในโดเมน และ output ในโดเมนใช้ Power อย่างชัดเจน

ถ้าติด

  • ตัวบ่งชี้ไม่แสดง Power เลย ถ้อยคำงานอาจไม่ match keyword ของมัน — ระบุชื่อ tool หรือโดเมนตรง ๆ
  • output ยังดูทั่วไป ลองงานที่มีแต่ Power นั้นที่รู้วิธีทำได้ดี ไม่ใช่งานที่ agent ไหนก็ตอบได้
บทที่ 8 · Lab 8

ร่าง pilot ของทีมคุณ

⏱ 30–40 นาที — ทำกับทีมได้ผลดีที่สุด 🔧 ความรู้เรื่อง repo ของคุณ + ใครว่างบ้าง 🎯 ออกจากคอร์สพร้อมแผนที่เป็นรูปธรรม มอบหมายได้ — ไม่ใช่ความตั้งใจลอย ๆ

ขั้นตอน

  1. ระบุ repo pilot — หนึ่ง, ใช้งานจริง, มี convention จริงที่ควรค่าแก่การบันทึก — และ คน (2–5) เขียนลงไป
  2. เขียนย่อหน้าแรกของ product.md สำหรับ repo นั้น ด้วยมือ: มันคืออะไร ใครใช้ เป้าหมายธุรกิจหนึ่งข้อ นี่คือสิ่งที่ "Generate Steering Docs" ควรพูด
  3. ลิสต์ ห้ากฎ ที่ทีมเถียงกันในรีวิวมากสุด กฎเหล่านี้กลายเป็น code-style-*.md
  4. ลิสต์สิ่งที่จะอยู่ใน .kiroignore ของ repo นี้: secret, fixture, โฟลเดอร์ที่ generate, path ในขอบเขต compliance
  5. เลือก ticket แรก ที่จะรันผ่าน spec และใครจับคู่ ใส่วันที่ให้ retro

ผลลัพธ์ที่คาดหวัง

ทุกแถวของ checklist rollout ในบทที่ 8 มีชื่อคนกำกับ และ retro มีวันที่ แชร์กับทีม

ถ้าติด

  • เลือก repo ไม่ได้ เลือกอันที่มี convention ชัดสุดและมี backlog ที่ยังเดินอยู่ — ไม่ใช่อันที่ใหญ่สุด
  • ทีมไม่ว่าง ทำร่างคนเดียวก่อน แล้วจอง 15 นาทีเพื่อยืนยันชื่อและวันที่
บทที่ 9 · Lab 9

วาง feature จริงลงบน AIDLC Collaborative

⏱ 30–45 นาที 🔧 ticket จริงหนึ่งอันที่เพิ่ง ship หรือกำลังทำอยู่ · เอกสาร architecture และ execution model ของแพลตฟอร์ม 🎯 ตัดสินใจบนกระดาษว่าเอนจิน hosted แบบหลายผู้ใช้คุ้มสำหรับทีมคุณไหม

ขั้นตอน

  1. เลือก feature หรือ bugfix จริงหนึ่งอันที่ทีมคุณเพิ่ง ship หรือกำลังทำอยู่ บน repo จริงของคุณ
  2. อ่านหน้า architecture และ execution model ของแพลตฟอร์ม
  3. ร่าง ticket นั้นเป็น intent: scope อะไร (feature/bugfix), prompt จะเขียนว่าอะไร, จะแตกเป็น unit of work กี่อัน และ gate ทั้งสอง (อนุมัติ fan-out, รีวิว PR) จะอยู่ตรงไหน
  4. ตัดสินใจ delivery mode ให้มัน — PR เดียวจากทั้ง intent หรือ PR ต่อ unit — แล้วบอกว่าทำไม
  5. บอกคำถามด้าน traceability หนึ่งข้อเกี่ยวกับ ticket นั้นที่ aidlc-docs/ markdown trail ปัจจุบันของทีมคุณ (Module 0) ตอบเร็ว ๆ ไม่ได้ แต่ graph query ตอบได้
  6. เขียนหนึ่งย่อหน้า: adopt, pilot บน repo เดียว หรือข้ามไปก่อน — พร้อมสิ่งเดียวที่จะเปลี่ยนคำตอบของคุณ (ขนาดทีม, ค่าใช้จ่าย AWS, จำนวน repo)

ผลลัพธ์ที่ควรได้

ข้อเสนอ go / pilot / no-go สั้น ๆ เป็นลายลักษณ์อักษรให้ทีม อ้างอิงจาก ticket จริงที่เดินผ่านมา — ไม่ใช่ความเห็นทั่วไปเกี่ยวกับแพลตฟอร์ม

ถ้าติดปัญหา

  • ticket ดูเล็กเกินจะ fan out. เป็นข้อมูลที่ดี — จดไว้ในข้อเสนอของคุณ ไม่ใช่ทุก ticket ต้องการ unit ขนาน
  • บอกไม่ได้ว่า graph ช่วยอะไร. เทียบกับครั้งล่าสุดที่มีคนถามว่า "โค้ดนี้ implement อะไร" แล้วคุณต้องไปอ่านสามไฟล์ถึงจะตอบได้
Capstone · Lab 10

หนึ่งฟีเจอร์ end to end ด้วย AI-DLC + Claude Code

⏱ 60–90 นาที 🔧 Claude Code CLI · git · โฟลเดอร์เปล่า · repo awslabs/aidlc-workflows 🎯 พาหนึ่งฟีเจอร์เล็ก ๆ จาก intent ถึงโค้ดที่รีวิวแล้ว ผ่านทุกด่านของ AI-DLC — และเห็น trail ใน aidlc-docs/ ที่มันทิ้งไว้

นี่คือทั้ง loop จากบทที่ 0 ทำด้วยมือหนึ่งรอบ ใช้ AI-DLC โอเพนซอร์สบน Claude Code — ไม่ใช่ Kiro IDE — ซึ่งเป็นประเด็น: process นี้ไม่ผูก harness (บทที่ 7) คุณจะสร้าง Task Management API เล็ก ๆ

ขั้นตอน

  1. ติดตั้ง workflow โฟลเดอร์เปล่าใหม่, git init clone awslabs/aidlc-workflows คัด core workflow ของมันมาเป็น CLAUDE.md ของคุณ และคัด rule details ไปที่ .aidlc-rule-details/ commit ทั้งคู่ — version process เหมือน version โค้ด เปิด claude แล้วถาม "What instructions are currently active in this project?" เพื่อยืนยันว่าโหลดแล้ว
  2. เริ่ม Inception ด้วย trigger บังคับ: Using AI-DLC, build a REST API for task management with user authentication, task CRUD, priority levels, and due dates. ถ้าไม่มี prefix Using AI-DLC, กฎจะถูกเมิน
  3. workspace detection มันเห็นโฟลเดอร์เปล่า → greenfield ข้าม reverse-engineering เขียน aidlc-docs/inception/workspace-detection/workspace-analysis.md แล้วรอ อนุมัติ
  4. requirements มันเขียน requirement-verification-questions.md — multiple choice: framework (Express / FastAPI / Spring / Django), database, auth (JWT vs OAuth2), deploy target ตอบ ในไฟล์ และตอบให้เจาะจง — JWT, RS256, access 15 นาที + refresh 30 วัน ดีกว่า JWT บอกว่าเสร็จ มันสร้าง requirements.md ขอให้มันเพิ่มหนึ่ง requirement (เช่น "FR-011: task tags") ยืนยันว่าไฟล์เปลี่ยน อนุมัติ เปิด extension Security Baseline ถ้ามันเสนอ — มันเปิดการตรวจ OWASP Top 10, สแกนหา secret ที่ฝังในโค้ด, รีวิวช่องโหว่ของ dependency และบังคับ validate input ทั้งหมดเป็นด่านที่บล็อกได้ ไม่ใช่แค่คำเตือนที่ถูกเมิน
  5. user stories + execution plan story ใน user-stories.md ให้คะแนนตามหลัก INVEST — Independent, Negotiable, Valuable, Estimable, Small, Testable — พร้อม execution-plan.md อย่าข้าม — ครึ่ง Testable ของ INVEST คือสิ่งที่ทำให้แต่ละ story กลายเป็น acceptance criteria ที่ Construction ใช้ตรวจ story ที่เขียนหลวมจะไม่เหลืออะไรไว้ตรวจงานของ agent รีวิว อนุมัติ
  6. application design application-design.md — สถาปัตยกรรม, component, data model — รีวิว ก่อนมีโค้ด อนุมัติ; การเซ็นถูก log ไปที่ aidlc-docs/audit.md
  7. units มันแบ่ง design เป็น units/units-breakdown.md (Unit 01 Auth, Unit 02 Task CRUD, …) อนุมัติ
  8. Construction ต่อ unit สำหรับ Unit 01 มันเขียน construction/unit-01/functional-design.md แล้วตามด้วย nfr-design.md — การแยกนี้สำคัญ: functional design ตอบว่า unit นี้ทำอะไร (interface, ข้อมูลเข้า/ออก, edge case), NFR design ตอบว่าทำได้ดีแค่ไหน (latency, auth, rate limit, observability) — ครึ่งที่การพรอมป์ธรรมดามักลืม เพราะ "เพิ่ม login endpoint" ไม่ได้บอกใบ้เรื่อง rate limit เลย หลังคุณอนุมัติทั้งสองเท่านั้น มันถึงเขียน source (src/auth/… + test) และ log ไว้ใน code-artifacts.md ทำ Unit 01 ให้ครบอย่างน้อยหนึ่งอัน
  9. resume จาก state file เปิด session ใหม่แล้วพิมพ์ Continue AI-DLC for this project. Check aidlc-docs/aidlc-state.md for current status. มันอ่าน state แล้วทำต่อที่ด่านถัดไป — เพื่อนร่วมทีมบนเครื่องมืออื่นรับช่วงต่อจากตรงนี้ได้
  10. อ่าน trail เปิด aidlc-docs/audit.md — ทุกด่าน ทุกการอนุมัติ ทุก cross-document consistency check เรียงตามลำดับ นั่นคือสิ่งที่ vibe coding ไม่เคยทิ้งไว้

ผลลัพธ์ที่คาดหวัง

โค้ดที่ทำงานได้อย่างน้อยของ Unit 01 ที่ตรงกับ requirements และ design ที่อนุมัติ — ไม่มี drift — และ aidlc-docs/ tree ที่เต็ม: workspace analysis, requirements, stories, design, units, functional + NFR design ต่อ unit, code-artifacts บวก audit.md และ aidlc-state.md คุณไม่เคยเขียน spec ด้วยมือ คุณตอบการสัมภาษณ์ที่มีโครงสร้างและอนุมัติแผน

คุ้มตอนไหน — และไม่คุ้มตอนไหน

แล็บนี้ใช้เวลา 60–90 นาทีสำหรับฟีเจอร์เล็กหนึ่งอัน ในขณะที่พรอมป์ธรรมดาจะได้โค้ดใน 5 นาที ต้นทุนที่เพิ่มขึ้นซื้ออะไรบางอย่างที่เจาะจง ดังนั้นต้องเลือกใช้อย่างมีสติ:

  • คุ้มเมื่อ: โค้ดที่คนอื่นจะดูแลต่อ, อายุใช้งานเป็นเดือนไม่ใช่สัปดาห์, มีข้อกำหนด compliance/security จริง, เป็น brownfield ที่ไม่มีใครในห้องรู้ข้อจำกัดทั้งหมด หรืองานที่ต้องอธิบายให้คนอื่นฟังทีหลัง
  • ไม่คุ้มเมื่อ: สคริปต์ใช้ครั้งเดียว, prototype ที่ตั้งใจจะทิ้ง, บั๊กที่รู้วิธีแก้อยู่แล้ว หรืองานสำรวจแบบ "นี่คืออะไรกันแน่" — vibe ก่อน แล้วค่อยรัน AI-DLC ตอนรู้แล้วว่ากำลังสร้างอะไรจริง ๆ

สองกับดักที่ควรระวัง: gate จะได้ผลก็ต่อเมื่อคนที่กดผ่านอ่าน artifact จริง ๆ — กด approve รัวทุกด่านโดยไม่อ่านคือ vibe coding ที่มีเอกสารสวยกว่าเดิม และเอกสารเยอะไม่ได้แปลว่าเอกสารดีขึ้นอัตโนมัติ — application-design.md ที่ไม่มีใครอ่านแย่กว่าการไม่มี design doc เลย เพราะมันดูเหมือนความรัดกุมที่ไม่มีใครใช้จริง

ถ้าติด

  • Claude Code เริ่มเขียนโค้ดเลย คุณลืม prefix Using AI-DLC, หรือ CLAUDE.md ไม่โหลด — เช็คซ้ำด้วยคำถาม "what instructions are active"
  • requirements กลับมากว้าง ๆ คำตอบในไฟล์คำถามกว้างไป หนึ่งการตัดสินใจที่เจาะจงต่อบรรทัด
  • context window เต็มกลางทาง ปกติ — เปิด session ใหม่ด้วย prompt "Continue AI-DLC … check aidlc-state.md"
  • มันจะรัน 30 stage สำหรับฟีเจอร์เล็ก ๆ ตั้ง depth ให้ต่ำลงหรือบอกว่าจะข้าม stage ไหน — engine แบบ adaptive รับคำสั่ง (บทที่ 0)
  • ไม่อยากให้ CLAUDE.md อยู่ที่ root ของ repo (เช่น มีไฟล์ของทีมอยู่แล้ว) ติดตั้งที่ .claude/CLAUDE.md แทนได้ — โฟลเดอร์ rule details เดียวกัน ผลลัพธ์เดียวกัน แค่ตำแหน่งที่ Claude Code อ่านต่างไป
